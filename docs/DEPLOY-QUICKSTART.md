# Запуск и развёртывание

Полная платформа состоит из веб-приложения, PostgreSQL и отдельного Node.js worker. Веб принимает задания и показывает результаты; worker исполняет фоновую очередь. Один веб-сервер с подключённой базой не завершает новые фоновые операции.

## 1. Требования

| Компонент | Назначение |
|---|---|
| Node.js 20.19+ в ветке 20, 22.12+ в ветке 22 либо 24+ | Совместимость с установленным Prisma, Next.js и worker |
| PostgreSQL 16+ | Каталог, проекты, снимки расчётов, очередь и ключи идемпотентности |
| `DATABASE_URL` | Одна логическая база для web и worker |
| `AUTH_SECRET` | Секрет входа; задайте собственное значение для публичного стенда |
| Применённые миграции и сев | Схема БД, справочники, нормативы и демонстрационные аккаунты |
| Одинаковый fingerprint движка | Совместимость выпуска web и worker |

Миграции выполняют по прямому соединению. Для serverless web обычно используют рекомендованный провайдером пул соединений; проверьте режим подключения у своего PostgreSQL-провайдера. Прямое соединение позволяет не зависеть от сохранения блокировок миграций транзакционным пулом.

## 2. Docker Compose

Нужны Docker с Compose v2 и сеть для первой сборки.

```bash
docker compose up --build
```

Откройте http://localhost:3000.

| Сервис | Что делает | Проверка |
|---|---|---|
| `db` | PostgreSQL; данные в томе `rrp_pgdata` | TCP `pg_isready` |
| `migrate` | `prisma migrate deploy`, затем сев | Завершение с кодом 0 |
| `app` | Веб-приложение Next.js | `GET /api/health` |
| `worker` | Исполнение сохранённых расчётов | Процесс запущен; `calculation_worker_started` в логах; контрольный job завершился |

```bash
docker compose logs worker
curl http://localhost:3000/api/health
```

Ответ health подтверждает web и БД, но не наличие живого worker. После входа создайте контрольный проект и убедитесь, что операция проходит QUEUED → RUNNING → SUCCEEDED/PUBLISHED. При остановленном worker очередь сохраняется и ожидает исполнителя.

Настройки `.env` для Compose:

| Переменная | Назначение |
|---|---|
| `AUTH_SECRET` | Собственный секрет публичного стенда |
| `DEMO_USER_PASSWORD`, `DEMO_ADMIN_PASSWORD` | Пароли демо-аккаунтов при севе |
| `ADMIN_API_TOKEN` | Необязательный доступ администратора API |
| `APP_PORT`, `DB_PORT` | Порты хоста; по умолчанию 3000 и 5433 |
| `CALCULATION_ENGINE_RELEASE` | Одинаковая дополнительная метка выпуска web/worker; не заменяет встроенный хэш кода |

Порт PostgreSQL на хосте опубликован только на `127.0.0.1:${DB_PORT:-5433}`. Контейнеры web и worker обращаются к базе по внутреннему адресу `db:5432`.

Для локальной демонстрации сев создаёт `demo@demo.local` / `demo-user-2026` и `admin@demo.local` / `demo-admin-2026`. На публичном стенде замените пароли. Общий демо-проект доступен для чтения; сохранение правок выполняйте в копии.

При ошибке запуска сначала проверьте `docker compose logs migrate`, затем логи `app` и `worker`. После изменения кода используйте `--build`, чтобы обновились оба образа. `docker compose down` сохраняет БД; `docker compose down -v` удаляет данные тома.

Compose не устанавливает публичный TLS-прокси. Для внешнего доступа используйте HTTPS и корректные forwarded headers. Настройка адреса входа сама по себе не настраивает транспортную безопасность.

## 3. Локально без Docker

Скопируйте `.env.example` в `.env`, задайте `DATABASE_URL` и `AUTH_SECRET`.

```bash
npm ci
npx prisma migrate deploy
npm run db:seed
npm run build
npm start
```

Во втором терминале из того же каталога:

```bash
npm run worker
```

Worker читает `.env` через `dotenv/config`; переменные, уже заданные окружением процесса, имеют приоритет. Проверьте, что оба процесса используют одну базу и одинаковую метку выпуска. `npm run build` последовательно собирает автономные 3D-страницы, worker и Next.js.

Для разработки запускайте `npm run dev` и отдельно `npm run worker:dev`. После изменения расчётного кода пересоберите и перезапустите соответствующие процессы; не смешивайте production web со старым worker.

Применяйте миграции из текущего дерева и проверяйте `npx prisma migrate status`; фиксированное количество миграций не является критерием готовности. На пользовательской базе не выполняйте `prisma migrate reset` или `prisma db push` вместо миграций.

## 4. Проверка чистого экземпляра

```bash
npm run build
npm run check:fresh -- --dry-run
npm run check:fresh
```

`scripts/fresh-instance-check.ts` создаёт временную локальную БД, выполняет миграции и сев, запускает web и проверяет health, главную и гостевую демку. Он останавливает созданный сервер и удаляет временную базу. Этот smoke проверяет bootstrap web/БД, **не полный lifecycle фоновой очереди**.

Отдельно проверьте настоящий worker на изолированной базе: контрольный enqueue, завершение, отмену, остановку после claim и восстановление тем же jobId после истечения lease. Критерии и контракты — [CALCULATION_JOBS.md](./CALCULATION_JOBS.md). Не используйте пользовательскую БД для тестов и принудительного истечения lease.

## 5. Проверки перед передачей

```bash
npx tsc --noEmit
npm run test:unit
npm run test:db
npm run lint
npm run build
npm run check:3d
npx playwright install chromium
npm run test:e2e
```

DB-тестам нужна отдельная БД с миграциями и тестовыми данными. Стандартный Playwright сам запускает web и worker; сборка web изолирована в `.next-e2e`. Если порт 3000 занят, проверка откажется подхватывать посторонний сервер — освободите его либо используйте явно настроенный изолированный конфиг.

Записывайте версии и результаты фактического прогона текущей сборки. Количество тестов, маршрутов и миграций из прежнего выпуска не подтверждает текущий выпуск. Существующие CI smoke-checks не заменяют проверку отмены, восстановления и совместимости worker.

## 6. Раздельное размещение web и worker

Web можно разместить на Vercel с отдельной PostgreSQL-базой, в том числе Neon. **Vercel+БД сами по себе размещают только web-контур.** Постоянный worker необходимо запустить отдельно — например, отдельным Node-процессом или контейнером на сервере с доступом к той же БД. Платформенный cron и короткий HTTP callback не заменяют этот процесс.

1. Создайте отдельную базу стенда. Настройте подходящие строки подключения: runtime web/worker и прямую строку для миграций.
2. Примените миграции и сев вручную по прямому соединению. Перед изменением существующей пользовательской базы сделайте проверяемую резервную копию и используйте [регламент](./DEPLOY.md).
3. Настройте web: `DATABASE_URL`, собственный `AUTH_SECRET`, при необходимости `ADMIN_API_TOKEN` и одинаковую дополнительную метку `CALCULATION_ENGINE_RELEASE`.
4. Соберите web и worker из одного исходного выпуска и lockfile. Сравните `engineRelease` в `dist-worker/engine-release.json` обоих артефактов; один commit ID не заменяет проверку fingerprint фактической сборки.
5. Разместите worker bundle с его runtime-зависимостями и запустите `node dist-worker/calculation-worker.cjs` (или `npm run worker` из каталога проекта) под менеджером процессов/контейнером с restart policy. Укажите ту же логическую БД и метку выпуска.
6. Проверьте вход, архивные проекты/отчёты и полный цикл нового фонового расчёта. `GET /api/health` и открывающийся каталог не подтверждают worker.

Миграции и сев не добавляйте в автоматически повторяемую preview-сборку. Переменные внешнего стенда держите отдельно от локальной тестовой `.env`, чтобы тесты не попали в пользовательскую БД.

При rollout сначала завершите/согласованно остановите очередь либо сохраните реально совместимый worker. Автоматического выбора исполнителя для разных версий движка нет; несовместимый запуск не должен считаться новым кодом молча. Откат только web без согласованного worker и схемы не является полным откатом платформы.

Сроки выполнения функций, соединения и ресурсы выбранного хостинга проверяйте отдельно, особенно для оставшихся гостевых/совместимых HTTP-расчётов. Тарифы и ограничения облачных провайдеров здесь не фиксируются как гарантия ёмкости.
