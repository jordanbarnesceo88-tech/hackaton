# Deployment Runbook

> Актуальный быстрый запуск — [DEPLOY-QUICKSTART.md](./DEPLOY-QUICKSTART.md). Полная платформа требует web, PostgreSQL и отдельного worker. Docker Compose поднимает все компоненты; при раздельном размещении worker устанавливают отдельно.
>
> Для фоновой очереди, версий, отмены и восстановления используйте [CALCULATION_JOBS.md](./CALCULATION_JOBS.md). Vercel с БД без отдельного исполнителя обслуживает web, но не завершает queued-операции.
>
> Раздел 3 и приложения содержат регламент перехода прежней модели с пользовательскими данными. Их описание исторического состояния не заменяет проверку текущей схемы и резервной копии перед миграцией.

Требования установленного Prisma к Node.js: 20.19+ в ветке 20, 22.12+ в ветке 22 либо 24+. Минимальная версия только для Next.js не определяет совместимость всей платформы.

## 1. Provision a managed Postgres  **[needs your account]**
Настройте PostgreSQL для выбранного контура. Для serverless web используйте подходящее runtime-соединение с пулом провайдера; для отдельного Node worker допустимо соединение, соответствующее его лимиту подключений. Оба процесса должны видеть одну логическую базу. `prisma migrate deploy` запускайте по прямому соединению: транзакционный пул не обязан сохранять необходимые сессионные блокировки миграций.

## 2. Environment variables
Set on the host (Vercel project settings, or the Docker runtime):
- `DATABASE_URL` — runtime-соединение с одной логической БД для web и worker; режим пула зависит от хостинга. Для миграций используйте прямое соединение.
- `AUTH_SECRET` — generate once: `openssl rand -base64 32`.
- `AUTH_URL` — your production URL (e.g. `https://example.com`) if not auto-detected.
- `DEMO_USER_PASSWORD`, `DEMO_ADMIN_PASSWORD` — пароли демо-аккаунтов `demo@demo.local` и
  `admin@demo.local`. Их читает только сев (`npm run db:seed`), приложению при работе они не
  нужны. Не заданы — `demo-user-2026` и `demo-admin-2026`; на стенде, доступном извне, задайте
  свои и передайте жюри отдельно.
- `ADMIN_API_TOKEN` — необязательно: запись через API v1 заголовком
  `Authorization: Bearer …`. Не задан или короче 16 символов — вход по токену выключен.

## 3. Миграция + сев на боевую, где УЖЕ ЕСТЬ данные

> Если база пустая (первый деплой в чистый инстанс) — достаточно шагов 3.5 и 3.6, всё
> остальное проверяет то, чего там нет. `npm run preflight:deploy` сам скажет «проверять
> нечего».

Исторические миграции и полный сев содержат преобразования с удалением строк. Для базы
без подтверждённой истории применяется ручной порядок ниже. Не запускайте полный сев
как побочный эффект каждой сборки.

Для штатного Vercel Production миграции выполняет ограниченный deploy-скрипт из раздела
4a: только после проверки исторической базы, по прямому соединению и с остановкой
сборки при ошибке. Preview не запускает миграции. Ручной путь ниже остаётся для
первичной подготовки, исторических баз и других способов размещения.

### 3.1 Взять ПРЯМУЮ строку подключения
Не pooled. `migrate deploy` берёт advisory lock, транзакционный пул его роняет — миграция
зависает или падает на середине. Preflight проверяет это первым пунктом и предупредит.

```bash
export PGDIRECT="postgresql://…@…неpooler…/…"   # direct, из шага 1
```

### 3.2 Прогнать preflight — он ТОЛЬКО ЧИТАЕТ
```bash
DATABASE_URL="$PGDIRECT" npm run preflight:deploy
```
Ненулевой выход = есть пункты `[СТОП]`. **Разобрать каждый до продолжения.** Что он показывает:

| Пункт | Что это значит |
|---|---|
| Застрявшие миграции | `migrate deploy` откажется бежать (P3009) и деплой упадёт, не сделав ничего |
| `global_categories` даёт конфликты имён | Миграция бросает `RAISE EXCEPTION` и откатывается: деплоя не будет |
| `saved_analysis_solution_fk` удалит N расчётов | Удаление защитимо, но решение принимает владелец, а не миграция |
| Чистка сева удалит N решений | **Единственное необратимое действие сева.** Список печатается поимённо |
| После сева останется N дубликатов | Строку не опознать по `slug`'у, а удалить её чистка не может (ссылки из расчётов или `ORGANIZER`). **Повторный сев не чинит** — только ручное слияние, приложение B.4 |
| Сев обновит на месте N решений | `[ВНИМ]`, не стоп: переезд между категориями или переименование по `slug`'у. Вторая строка НЕ появится — в этом и смысл М-2. Но числа и место в каталоге изменятся |
| N строк со `slug`'ом `legacy-…` | `[ВНИМ]`: бэкфилл миграции их не опознал, и ни один источник их не обновляет. `SEED`/`PARSED` без ссылок удалит чистка, остальные — руками, приложение B.4 |
| Сев перепишет N значений допущений | Каждое участвует в каждом расчёте — все числа на экране изменятся |
| Категории есть в базе, но нет в источнике | Останутся с пустым названием-задачей на экране сравнения |

**До миграции трёх пунктов про `slug` в выводе НЕ БУДЕТ ВООБЩЕ** — «После сева останется N
дубликатов», «Сев обновит на месте N решений» и «N строк со `slug`'ом `legacy-…`». Они не
приблизительны, они не печатаются: все три стоят за проверкой наличия колонки
`Solution.slug`, а её заводит `20260913120000_solution_slug`, и на боевой её ещё нет.

Вместо них на шаге 3.2 появится один пункт, которого нет в таблице выше:

> `[ВНИМ] N решений лежат не в той категории — исход решит миграция`

Пока колонки нет, признак один — имя, и переезд между категориями неотличим от настоящего
дубликата. Поэтому пункт идёт предупреждением, а не `[СТОП]`: блокировать выкат за операцию,
которую `slug` как раз и разрешает, было бы неверно. Точный ответ даёт шаг 3.5a — после
миграции, когда колонка есть и вопрос решается по `slug`'у, а не по имени.

### 3.3 Снять дамп
```bash
pg_dump --no-owner --no-acl --format=custom "$PGDIRECT" > backup-$(date +%F-%H%M).dump
ls -lh backup-*.dump   # не ноль байт
```
**Отката миграций нет.** `prisma migrate deploy` не умеет down, а `global_categories` удаляет
колонку. Единственный откат — восстановление из этого дампа.

### 3.4 Закрыть трафик или объявить окно
Совместимой точки между старой и новой схемой НЕ СУЩЕСТВУЕТ, и это не осторожность, а факт:
`global_categories` делает `DROP COLUMN "SolutionCategory"."facilityTypeId"`, а старая сборка
читает именно её. Значит:

* **Старая сборка + новая схема** (миграция прошла, промоут ещё нет) → 500 на каждом экране
  визарда: колонки нет.
* **Новая сборка + старая схема** (промоут прошёл, миграция ещё нет) → 500 там же: нет таблицы
  `FacilityTypeCategory`, нет `taskLabel`, нет `workloadStream`.
* **Между `migrate deploy` и `db:seed`** схема новая, а данные старые: у всех категорий
  `taskLabel = ''` (экран сравнения задач показывает безымянные строки), поток нагрузки у всех
  `OPERATION_FLOW` кроме двух slug'ов, которые проставляет сама миграция, а **ставка труда в
  базе остаётся старой** — то есть все числа в этом окне неверны, но выглядят обычно.

Vercel отдаёт трафик всё это время. Поэтому:

```bash
vercel deploy --prod --skip-domain     # собрать, НЕ переключая домен
# …шаги 3.5–3.8…
vercel promote <deployment-url>        # переключить домен, когда база готова
```
Если такой возможности нет — объявить окно и увести домен на страницу-заглушку. Молча выкатить
поверх живого трафика нельзя: это несколько минут пятисоток и, что хуже, окно, в котором
показываются правдоподобные неверные числа.

### 3.5 Миграции
```bash
DATABASE_URL="$PGDIRECT" npx prisma migrate deploy
DATABASE_URL="$PGDIRECT" npx prisma migrate status   # ждём "up to date"
```

### 3.5a Preflight ещё раз — между миграцией и севом
```bash
DATABASE_URL="$PGDIRECT" npm run preflight:deploy
```
**Единственный момент, когда предсказание про решения точно.** Колонка `Solution.slug` уже
есть (её только что завела миграция), а сев ещё не бежал — значит preflight видит ровно то,
с чем сев столкнётся: какие строки он обновит на месте, какие задвоит, и какие `legacy-…`
достались базе от бэкфилла. До миграции он про это только догадывался по именам.

Читать три пункта:

* **«Сев обновит на месте N решений»** — переезды и переименования. Это норма, но список
  стоит сверить: здесь видно, что именно поедет.
* **«После сева останется N дубликатов»** — `[СТОП]`. Строку не опознать по `slug`'у, а
  удалить нельзя. Сев её не починит ни сейчас, ни с третьего раза: слить руками до или после
  сева (приложение B.4), иначе в каталоге навсегда останутся два одинаковых товара.
* **«N строк со `slug`'ом `legacy-…`»** — полный список того, что бэкфилл не опознал. Строки
  `SEED`/`PARSED` без ссылок чистка удалит сама (они уже в её списке); остальные не обновляет
  никто и никогда.

Если на этом шаге появился `[СТОП]`, которого не было на 3.2, — это не регресс, а тот самый
точный ответ. Дамп со шага 3.3 снят, база ещё не севшая: можно спокойно останавливаться.

### 3.6 Сев
```bash
DATABASE_URL="$PGDIRECT" npm run db:seed 2>&1 | tee seed-$(date +%F-%H%M).log
```
**Читать весь вывод, а не только код возврата.** На ПОЛНОМ прогоне сев печатает
`УДАЛЯЕТСЯ …` до удаления, `удалено строк …` после, `оставлено «…»` про замороженные строки,
`ДУБЛИКАТ: …` про то, что чистка тронуть не может, перечень строк `ORGANIZER` и предупреждения
про категории и связи, которых нет в источнике. Код возврата про них молчит.

**На прогоне, где сработал предохранитель чистки, из этого печатается ТОЛЬКО список
`УДАЛЯЕТСЯ …`.** Предохранитель — это `throw`, и он стоит РАНЬШЕ всего остального: ни
`оставлено «…»`, ни `ДУБЛИКАТ: …`, ни список `ORGANIZER` до вывода не доходят. Судя по строке
«Чистка сева удалит N решений» из шага 3.2, первый боевой прогон предохранитель и сработает —
то есть отсутствие `ДУБЛИКАТ:` в этом логе НЕ означает, что дубликатов нет. Про них к этому
моменту уже сказал preflight (шаг 3.5a), и он же скажет после (шаг 3.7).

Если сев остановился на предохранителе (`чистка хочет удалить N решений — больше порога 10`):
**ничего не удалено, всё остальное посеяно.** Сверить список и повторить один раз с:

| Переменная | Что делает |
|---|---|
| `SEED_PRUNE=force` | Удалить всё из списка |
| `SEED_PRUNE=off` | Не удалять ничего (строки останутся в каталоге) |
| `SEED_PRUNE_LIMIT=N` | Сдвинуть порог |
| `SEED_KEEP_ASSUMPTION_VALUES=1` | Обновить подписи и обоснования допущений, **значения не трогать** |

Сев идемпотентен: повторный запуск не задваивает строки и не роняет чужие данные.

### 3.7 Preflight ещё раз
```bash
DATABASE_URL="$PGDIRECT" npm run preflight:deploy
```
Часть `[ВНИМ]` здесь — штатный итог, а не хвост работы. На населённой боевой базе ожидаемы:
«Пользовательские данные в базе»; «N устаревших решений останутся: на них ссылаются расчёты»;
«N строк `ORGANIZER`»; и — если бэкфилл миграции опознал не всё — «строки со `slug`'ом
`legacy-…`», которые чистка удалить не смогла. Ни один из них не мешает выкату.

`[СТОП]` в норме не остаётся ни одного — **с единственным исключением ниже**, где красный
пункт правилен и снимается только руками. Оставшийся `[СТОП]` означает одно из двух, и
лечение у них РАЗНОЕ:

| Пункт | Что это | Что делать |
|---|---|---|
| «Чистка сева удалит N решений» | Сев остановился на предохранителе — чистка не выполнилась | Повторить сев с `SEED_PRUNE=force` (или `=off`, тогда пункт останется красным осознанно) |
| «После сева останется N дубликатов» | Строку нельзя опознать по `slug`'у и нельзя удалить: на неё ссылаются расчёты либо это `ORGANIZER` | **Повторный сев не поможет — не повторять.** Слить руками: приложение B.4. До слияния пункт красный, и это верно |
| что угодно ещё | Сев действительно чего-то не доделал | Читать лог сева со шага 3.6 |

Разница существенна: в первом случае повторный запуск — лечение, во втором он ничего не
меняет, и нужно понимать это до, а не после третьей попытки.

### 3.8 Промоут и дымовая проверка
Переключить домен, затем на боевом URL:
1. Главная → выбор отрасли → тип объекта → экран занятости показывает **названия задач**, а не
   пустые строки.
2. Сравнение решений: у каждой строки есть цена и подпись происхождения.
3. Открыть расчёт: панель допущений показывает **ставку труда 6,7** и обоснование под каждым
   из шестнадцати полей.
4. Войти существующим пользователем и открыть уже сохранённый расчёт — он должен открыться,
   а не отдать 404.
5. `/methodology` считается на запросе — открыть и убедиться, что цитаты живы.

## 4a. Раздельное размещение: Vercel web и отдельный worker

В репозитории `vercel.json` задаёт `node scripts/vercel-build.mjs` как Build Command. При `VERCEL=1` и `VERCEL_ENV=production` скрипт сначала запускает **только `prisma migrate deploy`**, затем существующий `npm run build`. Ошибка миграции останавливает сборку. Это исправляет выкладку нового Prisma Client поверх старой схемы, в частности ошибку `P2022: Project.revision`: колонку добавляет `20261017170000_project_revision`. Сев, `db push` и reset автоматически не запускаются.

В Vercel Production задайте `DATABASE_URL` для web и `DIRECT_URL` для миграций **к той же логической базе**. `DIRECT_URL` передаётся как `DATABASE_URL` только дочернему процессу Prisma; исходное runtime-соединение и окружение отдельного worker не меняются. Если `DIRECT_URL` отсутствует, используется `DATABASE_URL`, который в таком случае обязан быть прямым соединением. Явные адреса pooler/pgbouncer отклоняются. Неизвестное или отсутствующее окружение Vercel останавливает скрипт до команд.

Перед DDL production-скрипт читает историю миграций: пустая схема допускает первоначальную установку, а населённая должна содержать успешно применённую цепочку до `20260924120000_tz_v2`. При пропущенной исторической миграции сборка останавливается и требуется ручной preflight из раздела 3. Это предохраняет населённую базу без полной истории от автоматического запуска прежних разрушительных преобразований. Скрипт не восстанавливает и не подделывает историю миграций.

При `VERCEL_ENV=preview` или `development` выполняется **только сборка, без обращения к миграционному соединению и без DDL**. Для рабочего preview нужна отдельная подготовленная БД; preview-деплой не обновляет общую production-схему. Убедитесь, что в настройках проекта не остался ручной Build Command, обходящий `vercel.json`. После production redeploy проверьте вход, открытие проектов и выполнение контрольного задания; эта конфигурация ещё не применяет миграции к вашей базе сама по себе до запуска деплоя.

Vercel размещает Next.js web-контур. Подключение PostgreSQL не запускает постоянный процесс `npm run worker`; его необходимо установить отдельно с доступом к той же логической БД. Без исполнителя новые задания остаются QUEUED, даже если health, каталог и архивы открываются.

Соберите оба артефакта из одного выпуска, сравните встроенный `engineRelease` и задайте одинаковую дополнительную метку CALCULATION_ENGINE_RELEASE. Миграции выполняет описанная production-сборка либо отдельный согласованный deploy-шаг, сев остаётся отдельной операцией; preview не выполняет ни то ни другое. После установки проверьте контрольный job до SUCCEEDED/PUBLISHED, а не только web health. Пошаговый порядок — [DEPLOY-QUICKSTART.md](./DEPLOY-QUICKSTART.md), раздел 6.

## 4b. Docker одной командой (ТЗ §4.2.3)

```bash
docker compose up --build        # → http://localhost:3000
```

`docker-compose.yml` описывает четыре сервиса:

| Сервис | Что делает | Когда готов |
|---|---|---|
| `db` | Postgres 16, данные в томе `rrp_pgdata`; проверка здоровья `pg_isready -h 127.0.0.1` (по TCP: проверка через сокет отвечает «готово» ещё на временном сервере первого старта) | `pg_isready` отвечает |
| `migrate` | стадия `migrate` `Dockerfile`: `prisma migrate deploy`, затем `scripts/seed.ts`; разовый, `restart: "no"` | завершился с кодом 0 |
| `app` | стадия `runner`: standalone-сервер Next.js с `HOSTNAME=0.0.0.0 PORT=3000`; проверка здоровья — `GET /api/health` | 200 |
| `worker` | стадия `worker`: отдельный Node-процесс расчётов, очередь в PostgreSQL | процесс запущен; лог `calculation_worker_started`; `/api/health` его не проверяет |

`app` стартует, только когда база здорова и `migrate` завершился успешно: ошибка миграции или
сева намеренно не даёт показать пустой каталог. Первая сборка — ориентировочно 5–10 минут и
требует сети (`npm ci`, шрифты `next/font/google`). Демо-аккаунты, переменные (`AUTH_SECRET`,
`DEMO_*`, `ADMIN_API_TOKEN`, `APP_PORT`, `DB_PORT`) и частые ситуации — в
[DEPLOY-QUICKSTART.md](./DEPLOY-QUICKSTART.md), раздел 2.

`AUTH_SECRET` в compose имеет демонстрационное значение по умолчанию: без секрета Auth.js в
production отдаёт 500 на каждой странице. На стенде, доступном извне, задайте свой. `AUTH_URL`
намеренно не передаётся (`trustHost`), HTTPS compose не настраивает — на публичном стенде
нужен обратный прокси с TLS.

При запуске отдельных Docker-образов база, миграции, сев и оба процесса остаются вашей ответственностью:

### Фоновые расчёты: обязательный второй процесс

Сборка `npm run build` выпускает 3D-страницы, `dist-worker/calculation-worker.cjs` и Next.js. Вне Compose запустите `npm run worker` отдельно от `npm start`, с той же базой и меткой CALCULATION_ENGINE_RELEASE. При разработке используйте `npm run worker:dev`. Один только standalone web-сервер не исполняет сохранённую очередь.

Fingerprint движка встраивается при сборке в web и worker из одного `dist-worker/engine-release.json`. Метка выпуска не заменяет хэш кода. Несовместимый queued job завершается ENGINE_VERSION_UNAVAILABLE, а не молча исполняется новым движком. Перед rollout завершите очередь либо сохраните совместимый worker; автоматического маршрутизатора разных версий движка сейчас нет.

После миграций проверяйте не только `GET /api/health`, но и реальный цикл: enqueue → RUNNING → SUCCEEDED/PUBLISHED. Проверьте остановку worker после claim и восстановление того же задания новым процессом. Запуск worker без применённой схемы должен завершаться ошибкой. Отдельного readiness-регистра idle-worker пока нет; QUEUED не подтверждает наличие исполнителя.

История технических запусков ограничена 200 на владельца / 2000 всего и удаляется явно владельцем. Архив Project при этом сохраняется; маленькие ключи идемпотентности остаются. Резервные копии и восстановление должны включать все таблицы очереди вместе с проектами. Старые процессы worker после restore надо остановить, затем проверить совместимость движка и lease. ## 5. Security hardening before real production traffic  **[required before public launch]**
The auth code is correct for the current stage (bcrypt passwords, JWT sessions, strictly
user-scoped saved analyses — no cross-user access), but a few hardening steps are deliberately
deferred to deploy time because they need production infrastructure or config:
- **Rate-limit login & signup.** DONE — a DB-backed fixed-window limiter (`lib/auth/rate-limit.ts`,
  `RateLimit` table) throttles signup (5 / IP / 15 min, in `lib/auth/actions.ts`) and login
  (10 / email+IP / 15 min, in `auth.ts`'s `authorize`; для адресов `@demo.local` — 100, чтобы
  жюри под общими демо-аккаунтами не упиралось в лимит). Because it's Postgres-backed it works on
  both a single Docker instance and serverless/multi-instance — no Upstash/Redis needed. A per-IP
  login cap (50 / 15 min) backstops the per-account cap against password-spray. IP is read from
  `X-Forwarded-For`. **Your proxy MUST overwrite (not append) the inbound `X-Forwarded-For`** —
  else a client can spoof the leftmost hop and rotate it to bypass the limiter. Vercel handles
  this; nginx: use `proxy_set_header X-Forwarded-For $remote_addr;` (overwrite), NOT
  `$proxy_add_x_forwarded_for` (append); Cloudflare/most CDNs overwrite by default. The limiter
  fails open on a DB error (never locks users out on an infra hiccup). **Prune old rows** on a
  schedule (one row per key accumulates; login attempts with random emails/IPs can add many):
  `DELETE FROM "RateLimit" WHERE "windowStart" < now() - interval '1 day'` via a daily cron.
- **Security headers.** DONE — `next.config.ts` `headers()` sets CSP, HSTS, X-Frame-Options,
  X-Content-Type-Options, and Referrer-Policy on all routes (audit SEC1). The CSP still allows
  `'unsafe-inline'` scripts for Next's inline hydration bootstrap; tighten to nonce-based CSP
  when convenient.
- **(Optional) Email verification** on signup, if any future feature (password reset,
  notifications) will trust email ownership. Not needed for the current feature set.

| Таблица | Как пишется | Что бывает с чужими строками |
|---|---|---|
| `Assumption` | upsert по `key` | **Значение перезаписывается.** Это и есть смысл выката (ставка труда 15 → 6,7), но правку оператора он снесёт: `SEED_KEEP_ASSUMPTION_VALUES=1` сохраняет значения. Ключи, которых нет в модели, НЕ удаляются и НЕ читаются движком — сев про них предупреждает |

| `Solution` | upsert по `slug` | Переименование и переезд между категориями **обновляют существующую строку**: `name` и `solutionCategoryId` лежат в `update`, а не только в `create` (М-2 закрыт, `6c04d60` + `65c604d`). Строку, чей `slug` источникам неизвестен (`legacy-…` от бэкфилла миграции), upsert не найдёт и заведёт каноническую рядом — приложение B.4 |
| `Solution` (чистка) | `deleteMany` | Удаляет `source ∈ (SEED, PARSED)`, чьего **`slug`'а** нет ни в одном источнике (`2ac701f`; до него сверялось имя, и осиротевшая строка переезда оставалась жить незамеченной). `ORGANIZER` не трогает — проверено по условию. Строку, на которую ссылается сохранённый расчёт, не трогает (FK `Restrict`, попытка уронила бы весь сев) |
| `User`, `SavedAnalysis`, `RateLimit` | не пишутся | Сев их не касается вообще |

**Что чистка НЕ защищает.** Защита ровно одна — `savedAnalyses > 0`, и других ссылок на
`Solution` в схеме нет, так что от падения по FK она полна. Но:

* Строка, спасённая ссылкой, остаётся в каталоге **навсегда и без обновлений**: цена и
  производительность в ней заморожены на дате последнего сева, который её знал, а на экране она
  неотличима от актуальной.
* Между `findMany` (счёт ссылок) и `deleteMany` есть окно. Если в него влезет сохранение
  расчёта на удаляемое решение, `deleteMany` упадёт по FK и **уронит сев целиком** — теперь уже
  после того, как всё остальное записано, потому что чистка стоит последней. Вероятность мала,
  но она ровно поэтому и есть причина закрывать трафик на шаге 3.4.
* Сев **не транзакционен**. Падение на середине оставляет базу частично обновлённой. Все шаги
  до чистки идемпотентны, поэтому лечение — повторный запуск; чистка стоит последней именно
  затем, чтобы «повторный запуск» всегда оставался достаточным лечением.

## Приложение B. М-2 — стабильный `slug` у решения (ПРИМЕНЕНО в этой ветке)

**Личность решения — `Solution.slug`, глобально уникальный.** Так с `6c04d60`; раздел ниже —
проект, по которому это делалось, и он сохранён как история: по нему сверяется, что именно
обещано и что из этого выполнено. Что изменилось по сравнению с первой редакцией раздела:

| было (до этой ветки) | стало |
|---|---|
| Личность — пара «категория + имя», `upsert` по `solutionCategoryId_name` | `upsert` по `slug` (`6c04d60`), `name` и `solutionCategoryId` — в `update` (`65c604d`) |
| Схема ветки не менялась, миграция откладывалась | Миграция `20260913120000_solution_slug` **входит в эту ветку** и применяется на шаге 3.5 |
| Переименование в источнике заводило вторую строку | Обновляет существующую |
| Чистка и итоговая проверка сверяли имя | Сверяют `slug` (`2ac701f`) |

Что `slug` НЕ чинит — B.4; строки `legacy-…` на населённой боевой остаются работой оператора,
и preflight теперь их перечисляет.

Исходная постановка, ради истории: личность была парой «категория + имя», поэтому
переименование в источнике создавало вторую строку, старую спасал от чистки сохранённый
расчёт, обновлять её было некому, и обе стояли рядом в каталоге. Схема этот сценарий
предвидела и закрывала ровно половину: тихое удаление предотвращено (`onDelete: Restrict`),
дубликат — нет.

### B.1 Схема — применена, `prisma/schema.prisma`
```prisma
model Solution {
  id   String @id @default(cuid())
  slug String @unique   // ← идентичность. Стабильна при переименовании И при смене категории
  name String           // ← обычное поле, свободно меняется
  ...
  @@unique([solutionCategoryId, name])   // ОСТАВИТЬ
}
```
`slug` глобально уникален, а не в пределах категории: решение, переехавшее в другую категорию,
обязано остаться собой — иначе М-2 просто переезжает в новую форму.

`@@unique([solutionCategoryId, name])` **сохраняется**: без него ничто не помешает двум
визуально одинаковым строкам в одной категории. Побочный эффект — обмен именами между двумя
решениями одной категории в одном прогоне сева упрётся в индекс; это лечится двумя коммитами и
встречается примерно никогда.

### B.2 Миграция (одна, с бэкфиллом) — применена, `20260913120000_solution_slug`

Файл миграции **не редактируется никогда**: его список пар описывает историю, а не текущие
данные. Ниже — та же SQL, что лежит в дереве.
```sql
-- 1. Сначала nullable: NOT NULL на живой таблице требует значения для каждой строки.
ALTER TABLE "Solution" ADD COLUMN "slug" TEXT;

-- 2. Бэкфилл по парам, известным источникам НА МОМЕНТ ЭТОГО КОММИТА. Список описывает
--    ИСТОРИЮ, а не текущие данные: после применения его не редактируют никогда, иначе
--    миграция начнёт означать не то, что сделала.
UPDATE "Solution" s SET "slug" = v.slug
FROM (VALUES
  ('class-amr-transport',   'AMR: транспортировка и подбор (класс)', 'class-amr-transport'),
  ('class-palletizer',      'Робот-паллетайзер (класс)',             'class-palletizer'),
  ('class-sorter',          'Сортировочный робот (класс)',           'class-sorter'),
  ('class-cleaning',        'Робот-уборщик промышленный (класс)',    'class-cleaning'),
  ('class-cobot-pickplace', 'Кобот: pick-and-place (класс)',         'class-cobot-pickplace'),
  ('class-service-delivery','Сервисный робот доставки (класс)',      'class-service-delivery'),
  ('class-ai-inspection',   'ИИ-инспекция качества (класс)',         'class-ai-inspection'),
  ('class-cleaning',        'Gausium Scrubber 75',                   'gausium-scrubber-75'),
  ('amr',                   'HaiPick A42T',                          'haipick-a42t'),
  ('asrs',                  'Exotec Skypod (станция)',               'exotec-skypod-station'),
  ('asrs',                  'AutoStore (порт)',                      'autostore-port')
) AS v(cat, nm, slug), "SolutionCategory" sc
WHERE sc.id = s."solutionCategoryId" AND sc.slug = v.cat AND s.name = v.nm;

-- 3. Всё остальное — строки организатора и замороженные переименованные — получает
--    заведомо неканонический, но стабильный и уникальный slug. Префикс виден глазом:
--    'legacy-' в каталоге означает «эту строку не обновляет ни один источник».
UPDATE "Solution" SET "slug" = 'legacy-' || "id" WHERE "slug" IS NULL;

-- 4. Теперь ограничения.
ALTER TABLE "Solution" ALTER COLUMN "slug" SET NOT NULL;
CREATE UNIQUE INDEX "Solution_slug_key" ON "Solution"("slug");
```

Миграция обратно-совместима в одну сторону: старая сборка колонки не знает и продолжает
работать, поэтому её **можно** применить до промоута — в отличие от `global_categories`.

| 1 | `VendorSolutionSeed` и `CuratedSolution` получают поле `slug: string` (`SolutionClassSeed` его уже имел) | сделано, `6c04d60` |
| 2 | Все три `upsert` — на `where: { slug }`, а `name` и `solutionCategoryId` — из `create` в `update` | сделано, `6c04d60` + `65c604d` |
| 3 | Чистка: `slug: { notIn: [...все slug'и источников] }` вместо `name: { notIn: … }` | сделано, `2ac701f` |
| 4 | Итоговая проверка сверяет `slug`, а не пару `категория / имя` | сделано, `2ac701f` |
| 5 | Тест на уникальность slug'ов — на все три источника разом | сделано, `scripts/seed-data/seed-data.test.ts` |
| 6 | Предохранитель чистки (`SEED_PRUNE_LIMIT`) остаётся | не трогали |

**Отступление от п. 3, сознательное.** Проект обещал, что вместе с чисткой по имени исчезнут
предупреждение `ДУБЛИКАТ:` в севе и одноимённая проверка в preflight. Они оставлены, потому
что обещание было неполным: чистка удаляет не всё, что задваивается. Строку `ORGANIZER` она не
трогает по построению, а строку со ссылками из сохранённых расчётов — не может (FK `Restrict`).
Обе переживают сев рядом с канонической, и `slug` их с ней не сопоставляет никак — у них
`legacy-<id>`. Единственный оставшийся признак — имя, поэтому обе проверки сверяют его и
дальше; страховка от ложных срабатываний — тест «имена уникальны сквозь все три источника»
в `seed-data.test.ts`, где сказано, зачем он нужен. Оба сообщения переписаны: они называют
причину, по которой строка уцелела, и говорят прямо, что повторный сев её не починит.

**Чего в проекте не было и что добавлено по ходу:** preflight перечисляет строки `legacy-…`
поимённо и различает «сев ОБНОВИТ на месте» (переезд, норма) от «после сева останется
дубликат» (ручное слияние). Без этого на населённой боевой — единственной среде, где строки
`legacy-…` вообще существуют, — про них не сообщал никто.

### B.4 Что этим НЕ чинится
Строка, переименованная или переехавшая **до** появления `slug`'а, уже разъехалась: бэкфилл
ищет её по паре «категория + имя» из своего списка, не находит и выдаёт `legacy-<id>`, а сев
заводит рядом каноническую. Такие пары сливаются **руками** — ни сев, ни повторный сев этого
не делают.

Чем их найти:

| инструмент | когда |
|---|---|
| preflight, «N строк со `slug`'ом `legacy-…`» — полный список с пометкой «ИМЯ ЕСТЬ В ИСТОЧНИКЕ» | после миграции: шаги 3.5a и 3.7 |
| preflight, «После сева останется N дубликатов» (`[СТОП]`) | там же; это подмножество, которое чистка удалить не может |
| preflight, «N решений лежат не в той категории» (`[ВНИМ]`) | до миграции, шаг 3.2 — приблизительно, по именам |
| `ДУБЛИКАТ: …` в логе сева | полный прогон сева; **на прогоне, где сработал предохранитель чистки, не печатается** (см. 3.6) |

Как слить: перенести `SavedAnalysis.solutionId` со строки-проигравшей на выжившую (каноническую,
с правильным `slug`'ом), затем удалить проигравшую. После этого пункт `[СТОП]` в preflight
гаснет сам — иначе он останется красным навсегда, и шаг 3.7 будет неисполним.

Строки `legacy-…` с `source ∈ (SEED, PARSED)` и без ссылок сливать не нужно: их удаляет чистка
в том же прогоне, где заводит каноническую (`2ac701f`). До этой правки чистка сверяла имя,
находила его у только что заведённой строки и оставляла осиротевшую жить — молча.
