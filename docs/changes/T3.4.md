### Added — НОВАЯ МОДЕЛЬ tz-1.0.0 — админка: каталог, характеристики, нормативы, параметры, обновление данных (числа не меняются)

Раздел администратора `/admin` (ТЗ §3.1.1, §3.1.4, §3.3.5, §3.3.6, §3.5.4, §4.4.1).
**МЕНЯЕТ ЧИСЛА: нет.** Код не меняет ни одного значения по умолчанию. Числа расчёта меняются
только после явной правки администратора, и каждая такая правка пишется в журнал.

- **Доступ.** `app/(admin)/admin/layout.tsx` вызывает `requireAdmin()` — это оптимистичная
  проверка. Каждая страница и каждое серверное действие вызывают `requireAdmin()` ещё раз:
  layout не защищает действия, до них можно достучаться прямым POST-запросом. Роль
  перечитывается из базы. Гость уходит на `/login`, пользователь без роли ADMIN получает 404,
  даже если в устаревшем токене записан ADMIN. Каждая страница начинается с
  `await connection()`, h1 на странице ровно один.
- **`/admin` — «Администрирование».** Состав каталога по глубине описания («Обогащённый»,
  «Примеры решений», «Идентификация»). Отдельно показаны число продуктов, которые требуют
  проверки, лежат в архиве, заведены администратором или правлены им. Ниже — число правленых
  нормативов и параметров, последний выпуск данных организатора, последние 10 действий и
  ссылки в разделы. Навигация по разделам: «Обзор», «Каталог», «Нормативы», «Параметры
  объектов», «Данные и журнал».
- **`/admin/catalog` — список и создание.**
  - Поиск по названию, производителю, описанию и slug. Регистр кириллицы и «ё» сворачиваются.
  - Отбор: действующие, требуют проверки, с правками администратора, заведены
    администратором, в архиве, все. По 100 строк на страницу.
  - Чипы строки: «администратор», «правка», «архив», «исключён», «требует проверки».
  - Форма «Создать продукт»: название, производитель, страна, тип решения, статус, описание,
    процессы. Продукт получает `origin ADMIN` и slug `admin-<транслит названия>`. Префикс
    исключает совпадение со slug'ами данных организатора. Идентификационные характеристики
    пишутся с происхождением «администратор», после создания форма переходит в карточку.
- **`/admin/catalog/[slug]` — карточка.**
  - Идентификация: название, производитель, страна, тип решения, статус, «Исключить из
    подбора» с обязательной причиной, «В архиве». Сохранение ставит продукту `editedByAdmin`.
    Изменённое поле идентификации записывается и в характеристику, которая повторяет его в
    карточке (название → «Наименование (модель)», производитель, страна → «Страна
    происхождения», тип решения, статус → «Статус доступности»), строкой администратора.
    Очищенное поле очищает и характеристику. Затем пересчитываются «Качество данных» и
    вынесенные колонки. После переименования заголовок карточки и строка «Наименование
    (модель)» совпадают.
  - Характеристики — все ключи словаря ТЗ §3.3.4 по шести группам, включая незаполненные.
    Рядом со значением стоит бейдж источника, цитата «как в источнике» и другие найденные
    значения. «Изменить» или «Заполнить» открывает форму. Поля формы зависят от вида ключа:
    - для числа и диапазона — значение, «от», «до», оговорка «до/от/≈», к чему относится
      (на робота, станцию, канал или парк) и единица;
    - для текста — текст, для перечня — пункты по одному на строку. Разделитель — только
      перевод строки: внутри пункта бывает «;» («Wi-Fi 5 ГГц 802.11 a/c/n; открытое API…»),
      и «;» как разделитель разрезал бы такой пункт на два;
    - у всех видов — ссылка на первоисточник, дата проверки (`<input type="date">`),
      «Подтверждено первоисточником» и примечание.

    Начальные значения формы (`charEditorDefaults` в `components/admin/format.ts`) — ровно
    сохранённые. Единица существующей строки — её собственная, даже пустая, а единица
    словаря показывается подсказкой. Новой строке пустая единица означает единицу словаря.
    «Сохранить» без правок отвечает «Изменений нет» по всем 2 615 строкам каталога в базе,
    это проверяет тест. Раньше 89 перечней с «;» внутри пункта и строки без единицы при
    единице в словаре сохранялись как изменённые: строка становилась правкой администратора,
    а цитата и основание источника стирались.

    Сохранённая строка получает `origin 'admin'` и `sourceType 'admin-edit'`, продукт —
    `editedByAdmin`. Вынесенные колонки (цена, производительность, полнота, доля
    подтверждённых, «требует проверки») пересчитываются функцией `promoteColumns`, той же,
    что у синхронизации. Перед ними пересчитываются производные строки «Качества данных» по
    формулам генератора данных: «Подтверждение» — «N из M подтверждены» (`confirmed / всего`,
    остальные части текста остаются), «Дата проверки» — `max(date)`. Строки, которые правил
    администратор, пересчёт не трогает. Если изменилось значение или ссылка, цитата и
    основание прежнего значения очищаются. Новое или изменённое значение с отметкой
    «Подтверждено» без ссылки на первоисточник не принимается. Значение, уже подтверждённое
    по месту в данных организатора (`sourceRef`), при правке только даты или примечания
    сохраняет отметку и без ссылки. Иначе, например, у цены Ronavi H1500 пришлось бы снять
    отметку ради примечания, и продукт стал бы «требует проверки».
  - Сводка: цена, производительность в расчёт, полнота, доля подтверждённых и причины
    «требует проверки» (`verificationReasons`).
  - «В архив» и «Вернуть из архива». Архивный продукт пропадает из каталога и подбора,
    снимки в сохранённых проектах остаются.
  - «Вернуть данные организатора» спрашивает подтверждение. Затем в одной транзакции
    удаляются характеристики `origin 'admin'`, снимается `editedByAdmin` и выполняется
    `syncOrganizerData(tx, { only: [slug] })`. Продукт возвращается к данным организатора
    поле в поле (кроме id строк и `updatedAt`), тест это проверяет.
  - Удаление разрешено только продуктам `origin ADMIN`, с отметкой «Подтверждаю удаление».
    Продукт организатора удалить нельзя: «Удалить нельзя: данные организатора — используйте
    «В архив»». Продукт, выбранный в сценарии проекта, тоже не удаляется. Сценарий хранит
    продукт в JSON, поэтому ссылка проверяется запросом `jsonb_path_exists`. Код Prisma
    P2003 переводится в «используется в проектах — переведите в архив».
  - История правок продукта — последние 30 записей журнала.
- **`/admin/norms` — нормативы расчёта.** Нормативы идут по группам. У каждого показано
  значение, допустимый диапазон, значение по умолчанию, происхождение, источник и
  обоснование (`SourceBadge`). Можно указать основание правки. Значение вне диапазона
  прижимается к границе норматива из кода — той же, что в `resolveNorms`, — и сообщение
  называет сохранённое число (0,99 → 0,85 для `utilization`). «Сбросить к умолчанию» — правка
  одной строки: значение из `NORM_DEFS`, `editedByAdmin = false`. Синхронизация с
  `respectAdminEdits: false` сбросила бы все нормативы сразу.
- **`/admin/params` — параметры объектов.** Выбор объекта: склад, аэропорт или
  медучреждение. Описания параметров сгруппированы по разделам датасета организатора. Правятся
  базовое значение, минимум, максимум, «обязательный», подсказка, пример и основание правки.
  Базовое значение приводится функцией `coerce`, той же, что ввод пользователя, и
  проверяется по новым границам. При смене границ пересчитывается признак «зафиксирован»
  (min = max). Строка получает `editedByAdmin`.
- **`/admin/data` — данные и журнал.**
  - Выпуски данных (`DataRelease`): версия, дата загрузки, состав, источники, отметка текущей
    версии приложения.
  - Кнопка «Обновить каталог» вызывает `syncOrganizerData(prisma, { respectAdminEdits: true })`.
    Отчёт по-русски: создано, обновлено, пропущено (правки администратора), в архив,
    устаревших источников (> 180 дней), плюс построчный отчёт `formatSyncReport`.
    Синхронизация переписывает производные строки «Качества данных» значениями из данных
    организатора и у продуктов с правками администратора. Поэтому после неё у таких продуктов
    эти строки пересчитываются заново, и отчёт добавляет строку «„Качество данных“
    пересчитано по правкам администратора: продуктов N».
  - Надпись «Обновление по запросу; плановое автообновление — в плане развития».
  - Журнал: последние 100 записей `ChangeLog` вне проектов (`projectId = null`) — когда, кто,
    объект, поле, было, стало, основание.
- **Серверные действия `lib/admin/actions.ts`** (`'use server'`, только асинхронные функции,
  форма `useActionState`): `updateProductAction`, `updateCharacteristicAction`,
  `createProductAction`, `archiveProductAction`, `deleteProductAction`, `revertProductAction`,
  `updateNormAction`, `resetNormAction`, `updateParamDefinitionAction`, `refreshCatalogAction`.
  Каждое работает по одной схеме:
  1. `requireAdmin()`, вне try.
  2. Проверка ввода. Неверное значение отклоняется с сообщением «что не так и как
     исправить», а не подчищается.
  3. Запись в `$transaction` вместе со строками `ChangeLog`: `entity`, `entityId`, `field`,
     `oldValue`, `newValue`, `autoValue` для нормативов, `unit`, `reason`, `userId`.
  4. `revalidatePath`.

  Правка без изменений возвращает «Изменений нет». Об успешном сохранении сообщения говорят
  «Записано: …», а не «Сохранено»: e2e v1 ищут «Сохранено» строго.
- **Компоненты `components/admin/*`:**
  - `admin-form.tsx` — общий `useAdminForm`. Действие вызывается в `startTransition`, поэтому
    при ошибке введённое не теряется, а после успеха поля перемонтируются с сохранёнными
    значениями. Там же `FormStatus` (`role=status`/`alert`);
  - `admin-nav.tsx`, `product-form.tsx`, `characteristic-row.tsx`, `product-actions.tsx`,
    `create-product-form.tsx`, `norm-row.tsx`, `param-row.tsx`, `refresh-catalog.tsx`;
  - `change-table.tsx` — журнал;
  - `format.ts`, `styles.ts` — подписи, время МСК, значения журнала по-русски.

  Чтение журнала для страниц вынесено в `app/(admin)/admin/_lib/changes.ts`. Любая
  экспортируемая функция файла `'use server'` становится доступным действием, поэтому запросы
  туда не кладутся.

### Changed
- **Шапка сайта (`components/site-header.tsx`).**
  - Название «Платформа оценки роботизации» ведёт на `/`, а не на `/onboarding`.
  - Навигация: «Проекты» (после входа), «Каталог» (`/catalog`), «Методика» (`/methodology/tz`),
    «API» (`/api-docs`), «Админка» (`/admin`).
  - «Админка» видна, если роль ADMIN записана и в сессии, и в базе (`isAdminSession`).
    Пользователь, которого понизили, ссылку не видит.
  - «Мои расчёты» убраны: прежняя модель v1 доступна со страницы «Проекты».
  - Почта, «Выйти», «Войти» и «Регистрация» на месте, перенос строк на телефоне сохранён.
  - h1 в шапке нет, текстов «Рассчитать», «Далее», «Откуда цифры» тоже нет.

### Tests
- `lib/admin/actions.test.ts` (набор db, 11 тестов, около 7 с, пользователи `tzt-t34-…`;
  подменены только `@/auth`, `next/navigation` и `next/cache`):
  - все 10 действий отказывают пользователю без роли ADMIN в базе (метка 404) и отправляют
    гостя на `/login`. Состояние базы и журнал после отказов не меняются;
  - `updateNormAction`: 0,99 прижимается к 0,85 и пишется в журнал с `autoValue`. Мусор и
    неизвестный ключ отклоняются. `resetNormAction` возвращает значение по умолчанию;
  - правка характеристики ставит `editedByAdmin` и пересчитывает `priceRub` и «Подтверждение»
    (подтверждённых на одно больше). Переименование и страна меняют `modelName` и
    `countryOfOrigin`, неизменённый производитель остаётся строкой организатора.
    `syncOrganizerData` сохраняет правку, архив и страну. `refreshCatalogAction` снова
    пересчитывает «Подтверждение» по правкам. `deleteProductAction` для продукта организатора
    отказывает. `revertProductAction` возвращает продукт к исходному снимку поле в поле;
  - продукт администратора создаётся со свободным slug (`…`, `…-2`), характеристики получают
    происхождение «администратор», удаление идёт только с подтверждением и пишется в журнал.
    Пока продукт выбран в сценарии проекта, удаление отказывает («используется в проектах»),
    после удаления проекта проходит — так проверяется запрос `jsonb_path_exists`;
  - форма правки характеристики: начальные значения каждой строки каталога организатора
    отправляются без правок, и каждая отвечает «Изменений нет». В данных есть и перечни с «;»
    внутри пункта, и строки без единицы. Новый перечень с пунктом «…; открытое API»
    сохраняется одним пунктом. Правка примечания у строки без единицы сохраняет пустую
    единицу, цитату и основание. Правка примечания у подтверждённой цены H1500 без ссылки
    сохраняет отметку, цитату, «Подтверждение» и `needsVerification`. Новое число с
    отметкой без ссылки получает отказ. Все правки демо-продуктов идут в транзакции, которая
    откатывается: база не меняется ни на миг;
  - границы параметра проверяются. Правка подсказки ставит `editedByAdmin` и пишет журнал с
    основанием;
  - `refreshCatalogAction` отдаёт отчёт по-русски и пишет строку журнала.

  Всё затронутое восстанавливается в `finally` и `afterAll`: продукт `agrobot` (вне подбора),
  норматив `utilization`, параметр склада `totalAreaM2`, тестовые продукты, пользователи и
  журнал.
