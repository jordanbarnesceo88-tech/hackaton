### Added
- **Роли USER и ADMIN в сессии (ТЗ §3.1.1).** Гость — это отсутствие сессии, отдельной роли
  для него нет. `authorize` в `auth.ts` читает `User.role` из базы (колонка из миграции
  `20260924120000_tz_v2`). Колбэк `jwt` при входе кладёт в токен `id` и `role`, колбэк
  `session` переносит роль в `session.user.role`. Токен, выданный до этого изменения, поля
  role не содержит и читается как USER. Посторонние значения тоже дают USER. Типы описаны в
  `types/next-auth.d.ts`: `Session.user.role`, `User.role?` и `JWT { id?, role? }` через
  `@auth/core/jwt`.
- **Охранные функции `lib/auth/guards.ts`** по паттерну «слой доступа к данным» из
  документации Next.js. Проверка стоит в каждой странице, серверном действии и обработчике
  API, `proxy.ts` не нужен (ТЗ §4.4.1, §4.4.2):
  - `getSessionUser()` возвращает `{ userId, email, role }` или null, без перенаправления;
  - `requireUser()` отправляет гостя на `/login`;
  - `requireAdmin()` отправляет гостя на `/login`. Затем роль **перечитывается из базы**:
    токен живёт до истечения и о понижении прав не узнаёт. Без роли ADMIN в базе ответ 404
    (`notFound()`), даже если в токене стоит ADMIN;
  - `getAdminUser()` проверяет то же без исключений: администратор или null. Нужна
    обработчикам API, которые отвечают 401/403, а не страницей 404;
  - `isAdminSession()` решает, показывать ли элементы администратора. Роль тоже берётся из
    базы, поэтому ссылка «Админка» видна ровно тогда, когда `/admin` откроется. Ошибка базы
    даёт false с записью в журнал: шапка не ломается.

  Роль из базы кэшируется через React `cache()` на один проход рендера, так что шапка, layout
  и страница делают один запрос. `forbidden()` и `unauthorized()` не используются: им нужен
  `experimental.authInterrupts`.
- **Тесты `lib/auth/guards.test.ts`** (набор unit, без базы, 19 случаев):
  - гость → `/login`;
  - USER → 404;
  - ADMIN в базе при USER в токене → допуск;
  - ADMIN в токене при USER в базе или без пользователя в базе → 404;
  - ошибка базы не превращается в допуск.

  Там же `auth.ts` проверяется целиком при подменённом next-auth: роль в `authorize`, колбэки
  `jwt` и `session`, лимиты входа.

### Changed
- **Переход после входа: `/projects` вместо `/onboarding`.** Путь жюри по ТЗ §5.4 начинается
  со списка проектов. Страница `/projects` появится в задаче T3.1 (волна W3); до неё
  вошедший пользователь видит 404. Регистрация по-прежнему ведёт в мастер v1 `/onboarding`:
  этот переход проверяют `e2e/wizard.spec.ts` и `e2e/auth-report.spec.ts`. Ни один e2e не
  проходит через `/login`.

### Security
- **Лимит входа для демо-аккаунтов (ТЗ §8.2.5).** Для адресов на `@demo.local` лимит
  попыток на пару «почта + IP» поднят с 10 до 100 за 15 минут. Жюри входит под общими
  демо-аккаунтами, часто из одной сети, а ограничитель считает и успешные входы. Одиннадцатый
  вход отклонялся бы с текстом «Неверный email или пароль». Пароли демо-аккаунтов известны
  жюри, так что защищать их от перебора незачем.
  - Лимит 50 попыток на IP за 15 минут **не изменился** и действует для всех адресов. Жюри
    за одним NAT упирается сначала в него: 50 входов за 15 минут на всю сеть. Это нужно
    указать в README и в инструкции для жюри (задача T4.2).
  - Для остальных адресов лимит прежний: 10 на пару «почта + IP».
  - Похожий чужой домен, например `@demo.local.evil.io`, лимит не поднимает.

Числа модели не меняются: задача не трогает ни расчёт v1, ни расчёт новой модели.
