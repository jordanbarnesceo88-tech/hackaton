### Added — НОВАЯ МОДЕЛЬ tz-1.0.0 — синхронизация данных организатора и сев (числа не меняются)

- **Синхронизация данных организатора — `lib/catalog/sync.ts`** (ТЗ §3.3.2, §3.3.5, §3.3.6).
  `syncOrganizerData(db, { respectAdminEdits = true, only?, now? })` переносит данные
  генератора T1.1 в таблицы модели. Её вызывают сев и (в T3.4) кнопка администратора
  «Обновить каталог». Шаги:
  - типы решений (SOLUTION_TYPE_DEFS) и процессы (PROCESS_DEFS) — upsert по slug;
  - связи «тип объекта — процесс» с порядком Process.order; тип объекта, которого нет в БД,
    пропускается с предупреждением, лишние связи не удаляются;
  - описания параметров (PARAM_SPECS → ParamDefinition, склад 52 / аэропорт 41 /
    медучреждение 59) по (тип объекта, ключ); строка с `editedByAdmin` не трогается;
  - нормативы (NORM_DEFS → Norm, 48): подпись, границы, основание и источник обновляются
    всегда, значение — только без правки администратора;
  - продукты каталога (188), каждый в своей транзакции:
    - характеристики пишутся через `sourcedToCharRow` → `toCharacteristicData` (T1.8);
    - строки с origin `admin` сохраняются;
    - неадминские строки с исчезнувшим ключом удаляются;
    - у продукта с правкой администратора меняются только organizerCatalogId,
      organizerRows и dataVersion, а его процессы не переписываются;
    - вынесенные колонки пересчитываются `promoteColumns` из итогового набора
      характеристик, включая правки администратора, поэтому колонка каталога всегда
      совпадает с характеристиками;
  - продукт организатора, которого больше нет в данных, уходит в архив, а не удаляется.
    Кандидаты — только строки, которые синхронизация уже записывала (непустой
    dataVersion). Поэтому тестовые строки других наборов и ручные вставки в архив
    не уходят;
  - выпуск данных (DataRelease) записывается один раз на версию, момент первого сева
    не переписывается.
- **Повторный прогон идемпотентен.** Запись идёт только при отличии от БД: сравнивается
  канонический JSON, порядок ключей jsonb не влияет. Второй сев на тех же данных даёт
  отчёт из нулей, updatedAt строк не меняется.
- **Отчёт `SyncReport` по-русски (`formatSyncReport`).** Для каждой таблицы: «создано /
  обновлено / пропущено (правки администратора) / в архив». Отдельно: отклонённые
  характеристики (ключ вне словаря ТЗ или дата не ГГГГ-ММ-ДД — продукт при этом
  записывается), неудавшиеся продукты (остальные продукты пишутся дальше), «устаревших
  источников (> 180 дней)» и предупреждения.
- **Версия выпуска данных — `organizerReleaseVersion()`.** Это хэш версий выгрузок
  организатора и полного содержимого нормативов, параметров, процессов, типов решений
  и каталога.
- **Другие экспорты модуля.** `syncProducts(db, seeds, opts)` пригоден для импорта
  каталога через API (T3.5). Функции принимают и транзакционный клиент.

- **Сев v2 — `scripts/seed-v2.ts`** (ТЗ §4.2.7, §8.2.5). `scripts/seed.ts` вызывает
  `seedV2(prisma)` после сева v1; строка итога v1 не изменилась («12 industries, 47 facility
  types, 15 solution categories, 11 solutions, 16 assumptions»).
  - Печатает отчёт синхронизации и итог «изменений нет» / «изменено записей — N».
  - Демо-аккаунты: `demo@demo.local` (USER, «Демо-пользователь») и `admin@demo.local`
    (ADMIN, «Демо-администратор»).
    - Пароли — из `DEMO_USER_PASSWORD` / `DEMO_ADMIN_PASSWORD`. Если переменная не задана
      или пуста, берутся `demo-user-2026` / `demo-admin-2026`.
    - Пароль длиннее 72 байт — ошибка сева: bcrypt обрезал бы его молча.
    - Роль приводится к заданной. Пароль перехэшируется, только если текущий хэш к нему
      не подходит, поэтому повторный сев не меняет строку.
  - Если синхронизация не записала хотя бы один продукт, сев завершается ошибкой после
    печати отчёта.
  - Демо-проект — `scripts/seed-demo.ts`, в этой волне заглушка `seedDemoProject`
    (реализуется в T3.6).

- **Проверка перед деплоем — `scripts/preflight-deploy.ts`.** Новый блок «слой модели ТЗ»:
  12 таблиц миграции `20260924120000_tz_v2` и колонка `User.role`.
  - Слоя нет, миграция ещё не применена — «ВНИМ.»: его создаст `migrate deploy`. Проверки
    v1 при этом идут дальше: на отставшей боевой это законное состояние.
  - Слой есть частично, или миграция числится применённой без таблиц — «СТОП».
  - Когда слой есть, скрипт показывает:
    - демо-адреса, занятые аккаунтом с другой ролью: сев отобрал бы у владельца доступ;
    - не заданные демо-пароли;
    - сколько правок администратора сохранит сев;
    - какие продукты сев отправит в архив;
    - продукты администратора, занявшие slug продукта организатора;
    - какой выпуск данных запишется.

    организатора, продукт администратора с тем же slug, архивация только своих строк;
  - демо-пароли и повторный сев без смены хэша.
