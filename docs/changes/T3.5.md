### Added — НОВАЯ МОДЕЛЬ tz-1.0.0 — API v1 для интеграций, описание OpenAPI 3.1, страница `/api-docs`, описание интеграций (числа не меняются)

API для внешних систем (ТЗ §3.8.1–§3.8.3, §3.8.5, §4.2.5): каталог с провенансом, нормативы,
параметры объектов, расчёт без сохранения и проекты пользователя. Машиночитаемое описание —
`GET /api/v1/openapi.json`, человекочитаемое — страница `/api-docs`, сценарии интеграции с
WMS, ERP, 1С, мониторингом и аналитикой ФЦ БАС — `docs/INTEGRATIONS.md`.
**МЕНЯЕТ ЧИСЛА: нет.** API не содержит своей арифметики. Расчёт вызывает ту же функцию
`lib/projects/recalc.resultsFromInputs` на тех же живых данных (`loadLiveInputs`), что и
«Новый проект», а создание проекта вызывает тот же `lib/projects/queries.insertProject`.
Проверено на засеянной базе (выпуск 72eb7f93): `POST /api/v1/calculate {"facility":"warehouse"}`
даёт те же сценарии, версию данных расчёта и NPV каждого сценария, что раздел «Новый проект со
сценариями по умолчанию» в выводе `scripts/print-demo-numbers.ts`. Числа здесь не приводятся:
их печатает только этот скрипт.

- **Маршруты** (`app/api/v1/**`). Все ответы — JSON с `Cache-Control: no-store`. Ошибка всегда
  имеет вид `{ error, details? }`, где `error` — по-русски: что не так и как исправить.
  Экспорта `runtime` нет, `params` типизированы как `Promise`.
  - `GET /api/v1/catalog` — гость. Фильтры `facility`, `process`, `solutionType`, `status`,
    поиск `q`, `page` по спецификации, плюс `level`, `sort`, `confirmedOnly`, `raas` (те же
    фильтры, что у страницы `/catalog`). Неизвестный параметр или значение — 422 со списком
    ошибок, а не пустой список: интеграция узнаёт об опечатке. В ответе — страница
    `getCatalogList` и выпуск данных (`dataRelease`).
  - `GET /api/v1/catalog/{slug}` — гость. Карточка `getCatalogProduct`: шесть групп
    характеристик ТЗ §3.3.4, у каждой источник, цитата, дата проверки, подтверждение и
    альтернативы. Неизвестный slug — 404.
  - `GET /api/v1/norms` — гость. Нормативы с метаданными: значение, значение по умолчанию из
    кода, итоговое значение расчёта после `resolveNorms`, границы, происхождение, обоснование,
    источник. Пока таблица пуста, отдаются нормативы из кода (`source: "code"`), как их и
    считает расчёт.
  - `PUT /api/v1/norms` — администратор. Тело `{ values: { <ключ>: <число> }, reason? }`.
    - Правило то же, что у страницы администратора: значение прижимается к [min, max]
      (`clamped: true` и сообщение), строка получает `editedByAdmin`.
    - Каждое изменение пишется в `ChangeLog` (entity `norm`, было, стало, значение по
      умолчанию, пользователь, причина). Все значения записываются одной транзакцией.
    - Неизвестный ключ, не-число или лишнее поле — 422, ничего не записано.
  - `GET /api/v1/facility-types/{slug}/params` — гость. Описания параметров из
    администрируемой таблицы `ParamDefinition`, пока она пуста — из кода. Неизвестный тип —
    404.
  - `POST /api/v1/calculate` — гость, без записи в БД.
    - Тело `{ facility, params?, scenarios? }`. Без `params` берутся базовые значения
      организатора, без `scenarios` — сценарии по умолчанию из подбора.
    - Параметры проверяет `validateParamValues` с `origin: "api"` (лишний ключ — ошибка):
      ошибки — 422 с `ParamIssue[]`, выход за диапазон организатора — предупреждения в
      `warnings`. Сценарии проверяет `validateScenarioSpecs` — та же проверка, что при
      сохранении проекта.
    - Лимит `rateLimit("api:calc:ip:<ip>", 60 за 15 мин)` → 429 «Слишком много запросов,
      повторите через N с» с заголовком `Retry-After`.
    - Ответ: `versions` (модель, имитация, хэш данных, версии выгрузок организатора, откуда
      взяты описания параметров), `summary` (по строке на сценарий: CAPEX, OPEX, эффект,
      окупаемость, ROI, NPV, TCO, состав оборудования, вердикт имитации, отказ с причиной),
      `conclusion`, `warnings` и полный `results`.
  - `POST /api/v1/projects` — пользователь по сессии.
    - Тело `{ name, facility, params?, objectName?, scenarios? }` проходит ту же проверку, что
      в расчёте. Название — `sanitizeProjectName`.
    - Проект записывается через `insertProject` с `paramsSource: { kind: "api" }`.
    - Ответ 201 с заголовком `Location: /api/v1/projects/{id}` и телом `{ id, url, versions,
      summary, conclusion, warnings, results }`.
    - Лимит 30 проектов за 15 минут на пользователя. Пользователя из сессии нет в базе (P2003) →
      401 «Сессия устарела».
  - `GET /api/v1/projects/{id}` — пользователь, только владелец: чужой проект неотличим от
    несуществующего (404). В ответе параметры, сценарии и сохранённые результаты, а также
    `liveDataVersion`, `dataChanged` и `modelChanged` — сравнение с текущими данными и моделью
    (§3.1.5).
  - `POST /api/v1/catalog/import[?dryRun=1]` — администратор. Тело — список `ProductSeed`,
    не больше 200.
    - Проверка строгая и всё-или-ничего: любая ошибка — 422 с ошибками по позициям, ничего не
      записано. Неизвестные поля — ошибка.
    - Провенанс каждой характеристики — по правилам Sourced: organizer → `sourceRef`; research →
      ссылка http(s), цитата `asInSource` и дата; estimate, derived, choice → `basis`; derived →
      `formula`; оценка не бывает подтверждённой. Тип источника должен соответствовать
      происхождению.
    - Запись идёт по правилам синхронизации. Характеристики конвертируются через
      `sourcedToCharRow` и `toCharacteristicData`, вынесенные колонки считает `promoteColumns`,
      характеристики с правкой администратора (`origin: "admin"`) не перезаписываются,
      повторный импорт того же входа ничего не меняет.
    - Продукт пишется с `origin: ADMIN`. Slug из данных организатора импорт не принимает (отказ
      по позиции с подсказкой: дополнять в админке).
    - `dryRun=1` — проверки без записи. Ответ — отчёт по каждой позиции.
  - `GET /api/v1/openapi.json` — документ OpenAPI 3.1.
- **Доступ** (`lib/api/auth.ts`).
  - `checkApiAdmin(req)` и `apiAdmin(req)`. Если передан заголовок `Authorization`, решает
    только он: `Bearer <ADMIN_API_TOKEN>` сравнивается в постоянном времени (SHA-256 и
    `crypto.timingSafeEqual`). Неверный токен — 401 без запасного пути через сессию.
  - Переменная не задана, пустая или короче 16 символов — вход по токену выключен целиком.
  - Без заголовка — сессия с ролью ADMIN, перечитанной из БД (`getAdminUser` из
    `lib/auth/guards`, без исключений): гость — 401, пользователь — 403. Ошибка базы уходит в
    обработчик и даёт 503.
  - `apiUser()` возвращает id вошедшего пользователя или null.
- **Общие ответы** (`lib/api/http.ts`). `readJsonBody` принимает только
  `Content-Type: application/json` (415): это закрывает подделку запроса с чужого сайта для
  записей по cookie. Размер тела ограничен и по `Content-Length`, и по фактически прочитанным
  байтам (413). Пустое тело или не-JSON — 400. Там же `apiJson`, `apiError`,
  `tooManyRequests`, `dbUnavailable` (503, причина только в лог сервера).
- **Описание API** (`lib/api/openapi.ts`). Объект `OPENAPI` (OpenAPI 3.1) с русскими описаниями,
  схемами, примерами запросов и ответов и расширением `x-access` (гость, пользователь,
  администратор). Кроме v1 описаны `/api/health` и `/api/templates/{facility}`. Примеры не
  выдумывают чисел:
  - карточка каталога и пример импорта собраны из данных организатора по Ronavi H1500 с их
    источниками;
  - нормативы и параметры взяты из кода модели, пример зарплаты — верхняя граница диапазона
    организатора;
  - примеры ошибок получены вызовом тех же функций проверки, что работают в обработчиках;
  - числа расчёта в примерах ответов заменены заглушками `<число, ₽>`.
- **Страница `/api-docs`** (h1 «API платформы»). Строится на сервере из `OPENAPI`, поэтому не
  может разойтись с `/api/v1/openapi.json`. На странице:
  - разделы «Доступ» и «Ошибки и ограничения»;
  - сводная таблица методов (метод, путь, доступ, назначение) со ссылками на разделы;
  - по каждой операции — описание, параметры и примеры запросов и ответов в `<pre>`.

  Swagger UI не подключён: CSP сайта не пускает скрипты со сторонних CDN. Ссылка «API» в шапке
  уже есть (T3.4).
- **`docs/INTEGRATIONS.md`**:
  - состав API и коды ответов;
  - WMS, ERP и 1С: сопоставление полей внешних систем с ключами склада, с пометкой, какие ключи
    влияют на расчёт перемещения паллет; пример `curl`; как серверная интеграция входит под
    пользователем;
  - обновление каталога через импорт и правила импорта;
  - нормативы;
  - мониторинг через `/api/health`;
  - аналитика ФЦ БАС: выгрузка каталога и воспроизводимость расчётов;
  - безопасность: роли, сессия, токен, CSRF, изоляция проектов, лимиты, размер тела, HTTPS на
    стенде;
  - что не построено, с метками §5.7.

    - в документе и на странице нет строк, зарезервированных за e2e v1, и на странице одно h1;
    - примеры проходят настоящие проверки и не выдумывают чисел.
  - `auth.test.ts`: разбор `Bearer`, сравнение токена, отсутствующая, пустая и короткая

  - `http.test.ts`, `norms.test.ts`, `import.test.ts`: разбор тела, лимиты, строка запроса

**Отклонения от плана задачи.**

- Функция записи импорта называется `importProducts(db, seeds, { dryRun })`, а не
  `syncProducts(db, seeds)`: в `lib/catalog/sync.ts` уже есть экспорт `syncProducts` с другой
  семантикой.
- Подсказка W2 (T2.1) предлагала вызвать `lib/catalog/sync.syncProducts` напрямую. Это не
  сделано: та функция пишет продукт с `origin: ORGANIZER`, и следующая синхронизация
  (`archiveVanished`) отправила бы в архив каждый импортированный продукт, slug которого не
  входит в данные организатора. Поэтому импорт повторяет её правила записи (те же
  `promoteColumns`, `sourcedToCharRow`, `toCharacteristicData`, защита правок администратора),
  но пишет `origin: ADMIN` и не принимает slug организатора.
- `apiAdmin(req)` возвращает объект администратора (`via: session | bearer`, userId для
  журнала) или null, а не `true`/`false`: журналу нужен автор изменения.
- Сверх спецификации:
  - фильтры каталога `level`, `sort`, `confirmedOnly`, `raas`;
  - `?dryRun=1` у импорта;
  - поля `objectName` и `scenarios` у создания проекта и лимит 30 проектов за 15 минут;
  - описание `/api/health` и `/api/templates/{facility}` в OpenAPI.
