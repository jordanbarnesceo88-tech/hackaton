### Added — НОВАЯ МОДЕЛЬ tz-1.0.0 — доступ к данным каталога (числа не меняются)

- **Снимок продукта для расчёта — `lib/catalog/product-for-calc.ts` (чистый модуль).**
  - `fromCharacteristics(meta, chars)` собирает `ProductForCalc` из строк
    ProductCharacteristic, `productForCalcFromSeed(seed)` — из данных генератора
    организатора (`ProductSeed`, T1.1). Ядро одно. Тест набора db записывает продукт из
    данных генератора в БД так же, как синхронизация (`sourcedToCharRow` →
    `toCharacteristicData`, колонки — `promoteColumns`), и сверяет снимок из БД со снимком
    из данных целиком, включая продукт с несколькими процессами.
  - Порядок процессов продукта — один во всех путях (`sortProcessSlugs`): как в PROCESS_DEFS
    (склад → аэропорт → медучреждение), процессы вне кода — в конце по slug. Колонка
    Process.order для этого не годится: номер задан внутри своего типа объекта (уборка
    склада — 6, уборка терминала — 3, уборка больницы — 2), и у 15 продуктов с процессами
    разных объектов (например, r2b-mark-2-se) порядок из БД и из данных расходился.
  - Правила «какое число идёт в расчёт» записаны в одном месте:
    - число — `valueNum`, то есть `typical` диапазона источника;
    - производительность «до X» без нижней границы и значение «на весь парк» в расчёт
      не идут (`throughputPerH = null`), но оговорка, единица и область сохраняются —
      по ним интерфейс объясняет, почему паспортной цифры нет в расчёте;
    - «цена подтверждена» и «производительность подтверждена» — флаг `confirmed` самой
      характеристики; отсутствующее значение подтверждённым не бывает;
    - NaN и ±∞ в снимок не попадают, отсутствующее значение — null, а не ноль.
  - `sources[]` — все характеристики в порядке словаря ТЗ §3.3.4 с русской подписью,
    значением строкой («80–100 паллет/ч (на робота)», «от 100 000 ₽/мес», «до 10 кг»),
    происхождением, ссылкой, датой и признаком подтверждения — для «Откуда число» (§3.5.8).
  - `sourcedToCharRow` раскладывает `Sourced`-значение по полям ProductCharacteristic
    (с группой ТЗ) — синхронизация T2.1 может писать в БД ровно то, из чего собирается снимок.
    Как есть в БД эта форма не пишется: запись — через `toCharacteristicData` (queries.ts),
    см. ниже.
  - Строки из БД сужаются осторожно: неизвестное происхождение — «оценка», неизвестный
    статус — «пилот» (зрелость не доказана, но и ложной причины «НИОКР» нет), неизвестная
    пометка качества отбрасывается.

- **Вынесенные колонки — `lib/catalog/promote.ts` (чистый модуль).**
  - `promoteColumns(chars, { flags })` → `priceRub`, `raasRubMonth`, `throughputPerH`,
    `throughputUnit`, `payloadKg`, `speedMps`, `completenessPct`, `confirmedSharePct`,
    `needsVerification`. В колонку попадает то же число, что и в расчёт: «до X» и «на весь
    парк» не выносятся, поэтому сортировка каталога по производительности их не поднимает.
  - Пометки продукта (`flags`) — обязательный аргумент `promoteColumns` и
    `verificationReasons`: без них помеченный продукт получил бы needsVerification = false,
    и колонка каталога разошлась бы с подбором. Продукт без пометок передаёт `{ flags: [] }`.
  - Полнота — по 31 обязательному ключу ТЗ §3.3.4 (`completenessPct` из
    `lib/tz/characteristics`); пустые строки не повышают полноту.
  - «Требует проверки» (ТЗ §3.4) — с причинами по-русски, без повторов
    (`verificationReasons`): любая пометка качества, неподтверждённая или неопубликованная
    цена, производительность без подтверждения или непригодная для расчёта, полнота ниже
    60 %, расхождение источников.
    - Пометки — текстами подбора (`FLAG_NOTES`, T1.4), а не английскими идентификаторами;
      неизвестная пометка отбрасывается и проверку не включает.
    - Расходящиеся характеристики названы по-русски («источники расходятся: Цена
      оборудования»), в порядке словаря.
    - Непригодная производительность объяснена по случаю: «указана только текстом»
      (11 продуктов организатора, например «2400-6000 м²/ч» или «высокоскоростная
      сортировка»), «без типичного значения» (есть только границы), «указан только предел
      («до 1 000 м²/ч (на робота)»)», «указана на весь парк».
    - Порог 60 % — решение модели из утверждённого плана (раздел 4 «Подбор»); подбор T1.4
      применяет тот же порог.
    - Расхождение — другое найденное числовое значение отличается больше чем на 10 % или
      записано в другой единице. Допуск 10 % — решение модели: тот же допуск, по которому
      генератор T1.1 признаёт значение организатора подтверждённым. Текстовые альтернативы
      расхождением не считаются.

- **Запросы — `lib/catalog/queries.ts`.** Каждая функция принимает клиент БД первым
  аргументом (`Db = PrismaClient | Prisma.TransactionClient`) и не импортирует общий клиент
  приложения: сев передаёт свой PrismaClient, синхронизация и админка — транзакцию.
  Импорты только относительные.
  - `getParamDefinitions(db, facility)` → `ParamSpec[]` из администрируемой ParamDefinition
    в порядке показа (§3.2, §3.2.4).
  - `getNormRows(db)` — строки Norm с метаданными в порядке NORM_DEFS; `getNorms(db)` —
    `resolveNorms(rows)`, повторно нормативы не исправляются.
  - `getProcessesFor(db, facility)` — процессы объекта из БД в порядке связей, соединённые
    с PROCESS_DEFS: модель спроса, единицы и ограничения — из кода, название и описание —
    из БД, «расчёт/имитация реализованы» — только если это верно и в коде, и в БД.
  - `getCalcProducts(db, facility)` → `ProductForCalc[]`: не в архиве, глубина enriched или
    examples, связь хотя бы с одним процессом объекта; исключённые продукты возвращаются
    с причиной — подбор показывает, почему они исключены.
  - `getCatalogList(db, filters)` — список каталога по вынесенным колонкам (§3.3.7):
    поиск, тип объекта, процесс, тип решения, статус, глубина описания, «только
    подтверждённые», «есть RaaS»; сортировка по цене, производительности, полноте, названию
    (без значения — в конце); страницы по 50. Архивные продукты в список не попадают.
    - «Только подтверждённые данные» (`confirmedOnly`) — продукты, у которых хотя бы одна
      характеристика подтверждена первоисточником (`confirmedSharePct > 0`). Это не
      «проверка не нужна»: на выгрузке организатора проверки требуют все 188 продуктов
      (у 184 цена не подтверждена первоисточником, у 167 нет производительности, у 146
      полнота ниже 60 %), и фильтр `needsVerification = false` всегда давал бы пустой
      список. С новым смыслом фильтр оставляет 43 из 188 продуктов, 29 из 40 складских,
      13 из 16 в перемещении паллет (Ronavi H1500 — 26 % подтверждённых — в их числе).
    - Поиск находит все слова запроса в любом поле и порядке, без учёта регистра и
      с «ё» = «е». Регистр сворачивается в JS, а не через ILIKE: локальная база развёрнута
      с локалью C, где ILIKE и lower() не сворачивают кириллицу («альфа» не находила бы
      «Альфа»).
  - `getCatalogProduct(db, slug)` / `getCatalogProducts(db, slugs)` — карточка (§3.3.4):
    характеристики по шести группам ТЗ, у каждой — значение строкой, «как в источнике»,
    происхождение, ссылка, дата, подтверждение, альтернативы и признак расхождения;
    звенья иерархии «отрасль → тип объекта → процесс → тип решения → продукт» (§3.3.1).
    Архивный продукт открывается с признаком архива — на него может ссылаться проект.
  - `latestDataRelease(db)` — последний выпуск данных (§3.1.5).
  - `toCharacteristicData(row)` — строка `CharRowFull` → данные записи ProductCharacteristic
    для синхронизации T2.1: дата YYYY-MM-DD → полночь UTC (при чтении возвращается та же
    строка), `alternatives: null` → `Prisma.DbNull`, ключ вне словаря (группа неизвестна)
    и дата не в формате ГГГГ-ММ-ДД — ошибка, а не тихая запись.

- **Тесты.** `product-for-calc.test.ts` и `promote.test.ts` (unit, 48 тестов) на фикстурах
  характеристик; `queries.test.ts` (набор db, 30 тестов) заводит собственные строки
  с префиксом `tzt-t18-` (процессы склада и аэропорта, тип решения, семь продуктов, один
  из них записан из данных генератора, параметры, норматив, выпуск данных), проверяет
  фильтры, сортировку, поиск по кириллице, раскладку по группам, порядок процессов,
  совпадение снимков из БД и из данных, работу внутри транзакции и удаляет свои строки до
  и после прогона. Прижатие норматива к границам проверяется всегда — в транзакции, которая
  откатывается: общая строка `utilization` в базе не меняется и не видна другим читателям
  даже на время теста.

**Числа не меняются.** Задача добавляет только доступ к данным; расчёт v1 и нормативы
tz-1.0.0 не затронуты.
