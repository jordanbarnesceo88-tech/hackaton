### Added — НОВАЯ МОДЕЛЬ tz-1.0.0 — сборка модели проекта, проекты с версиями и журналом, печать демо-чисел (МЕНЯЕТ ЧИСЛА только в новой модели)

- **Сборка модели проекта — `lib/tz/model.ts`** (ТЗ §2.2 шаги 2–7, §3.1.5, §3.6.2). Чистая
  функция `buildProjectModel({facility, params, paramDefs, scenarios, products, norms, sims?})`
  без React, Prisma и часов. Её вызывают сервер (сохранение, API, сев, печать чисел) и браузер
  (кнопка «Пересчитать»). Результат — `ProjectModel`: всё, что сохраняется в `Project.results`,
  кроме `calculatedAt` и `sim`, плюс планировка `layout` и входы имитации `simInputs`. Шаги:
  1. Параметры проверяются (`validateParamValues`), пропуски заполняются базовыми значениями
     (`applyDefaults`). Если в параметрах есть ошибка, **все** сценарии получают отказ
     `invalid_inputs` со списком полей `param:<key>`. Подбор при этом показывается без
     экономики.
  2. Для складоподобного объекта строится `buildWarehouseLayout` (активная зона, проезды,
     ворота) и `expectedLegsM`. Для каждого мобильного продукта со скоростью считается
     `cycleThroughputPerH` с временем захвата `handlingSecFor(класс, нормативы)`. Экономика и
     имитация работают на одной геометрии.
  3. Экономика сценариев — `computeScenarios`. Параметры организатора передаются как
     `paramBounds`, подписи — как `paramLabels`.
  4. Подбор выполняется по каждому процессу объекта на `relevantProducts(process, facility,
     products)` — **до** экономики сценариев. NPV покупки для балла берётся из временного
     сценария покупки на каждого кандидата: один прогон ядра на процесс. Строки сравнения
     (§2.2 шаг 4) — рекомендуемый и кандидаты плюс продукты из сценариев, у добавленных
     вручную стоит отметка. Решение сценария, которое подбор исключил жёстким правилом R1–R6,
     помечается как добавленное вручную, даже если клиент этого не сделал, а сценарий с ним не
     рекомендуется (см. «Исправления по ревью»).
  5. Входы имитации: `toSimInput` при расчётном (или ручном) N и при N по паспортной норме.
     N по норме — та же формула ТЗ, но только по норме. Рядом лежат `assumedUtilPct` и
     «Откуда параметры» (`provenance`).
  6. Если переданы сводки имитации, к рассчитанным сценариям добавляются риски
     `SIM_NOT_CONFIRMED` (высокий: «Имитация не подтвердила расчёт: достигнуто {a} из {r}
     пал./ч; узкое место — {b}», плюс минимальный устойчивый парк) или `SIM_OVERSIZED`
     (низкий). Сводка учитывается, только если её парк и пиковый поток совпадают с текущим
     расчётом: устаревшая сводка рисков не даёт.
  7. Вывод `buildConclusion`. Снимки берутся только для продуктов из сценариев.
     `dataVersion = dataVersionOf({productSnapshots, normsUsed, paramDefs, organizer:
     ORGANIZER_DATA_VERSION})`, где `paramDefs` — поля описаний параметров объекта, влияющие
     на расчёт. Формула вынесена в `projectDataVersion`, её же использует проверка
     расхождения с живыми данными.
  - Вспомогательные функции: `withSnapshotProducts` (снимки подменяют одноимённые живые
    продукты, исчезнувшие из каталога добавляются в конец), `storedPartOf`,
    `PROJECT_SIM_SEED = 1`.
- **`lib/tz/timing.ts`** — `timed(fn, now)` возвращает `{value, ms}`. Часы передаёт
  вызывающий код (`performance.now`), поэтому правило чистоты рендера не нарушается.
- **Сценарии по умолчанию — `lib/projects/defaults.ts`** (ТЗ §3.5.5). Набор:
  - «Как есть» (`asis`);
  - «Покупка — {лучшее}» (`p1`);
  - «Услуга (RaaS) — {лучшее}» (`r1`). Если у лучшего нет ставки, берётся следующий кандидат
    со ставкой, а если ставки нет ни у кого, остаётся лучшее и расчёт объяснит, что заполнить;
  - «Покупка — {второе}» (`p2`).

  Лучшее — рекомендуемый подбором продукт; если рекомендации нет (аэропорт, медучреждение),
  берётся первый кандидат. Сценариев всегда не меньше трёх. В названиях — короткое имя
  продукта без хвоста в скобках: «Ronavi H1500 (грузоподъемность до 1 500 кг)» → «Ronavi
  H1500». `initialScenarios(...)` строит набор пробной сборкой с одним «Как есть».
- **Проверка ввода — `lib/projects/validate.ts`** (отклонить, а не подчистить).
  - `validateScenarioSpecs`: от 3 до 10 сценариев, ровно один «Как есть» без позиций;
    уникальные ключи `^[a-z0-9-]{1,40}$` и названия (1–80 символов, без учёта регистра);
    не больше одной позиции на процесс; процесс — из процессов объекта, продукт — из каталога
    или снимка проекта; ручные значения конечны и больше нуля (сервис — не меньше нуля),
    число роботов — целое от 1 до 500; переопределения нормативов — только известные
    `NormKey` в допустимом диапазоне норматива (значение вне диапазона отклоняется с
    диапазоном, а не прижимается молча); неизвестные поля отклоняются. Сообщения — по-русски:
    подписи ручных значений, названия видов сценария, процессов и типа объекта вместо ключей.
  - `validatePendingChanges`: белый список полей `param:`, `item:<процесс>:quantity|price|
    throughput|service|raasRate|manual`, `norm:`, `scenario:add|remove`; значения — JSON до
    4000 символов; не больше 300 изменений за одно сохранение.
  - `sanitizeProjectName`: 1–120 символов.
- **Журнал корректировок — `lib/projects/changes.ts`** (ТЗ §3.5.4).
  - `toChangeLogRows` пишет строки ChangeLog: entity `project` для параметров объекта,
    `scenario` для позиций, состава сценариев и нормативов, изменённых в сценарии (с ключом
    сценария; без ключа норматив пишется как изменение проекта).
  - `serverAutoFrom(model, defs)` даёт автоматическое значение по расчёту **сервера**: Nавто,
    цену из снимка, min(норма; цикл), сервис из карточки или по нормативу, ставку RaaS, базовое
    значение параметра, норматив проекта. Значение `auto`, присланное браузером,
    игнорируется.
  - `changeFieldLabel` — подпись поля по-русски.
- **Пересчёт на сервере — `lib/projects/recalc.ts`** (импорты относительные, клиент БД —
  параметром).
  - `loadLiveInputs(db, facility)` возвращает описания параметров, продукты и нормативы. Если
    таблица ParamDefinition пуста, описания берутся из кода, и это отмечено в
    `paramDefsFrom`.
  - `runProjectSims(model)` для каждого сценария роботизации запускает имитацию при расчётном
    N и при N по норме и ищет `minStableFleet` в диапазоне [1; 2N] с бюджетом 20 с на
    сценарий и общим бюджетом 40 с на проект (`PROJECT_MIN_FLEET_BUDGET_MS`). Когда общий
    бюджет исчерпан, подбор пропускается и `minStableFleet` = null. Одинаковые входы,
    например покупка и услуга одного продукта, прогоняются один раз.
  - `resultsFromInputs` и `computeProjectResults(db, {facility, params, scenarios?,
    snapshot?})`: модель, имитация, модель с рисками имитации, `calculatedAt`. Без сценариев
    подставляются сценарии по умолчанию.
  - `liveDataVersion` показывает расхождение с живыми данными (баннер «Пересчитать на
    актуальных данных»).
  - `reproduceModel(live, stored)` воспроизводит модель страницы проекта из снимка.
  - `initialProject(live, facility)` готовит гостевой `/demo` со временем расчёта.
- **Проекты в БД — `lib/projects/queries.ts`** (ТЗ §3.1.3, §4.4.2).
  - Чтение: `listProjects` (число сценариев, лучшая окупаемость — считается в Postgres по
    jsonb, без загрузки полного снимка расчёта), `getProject` (`findFirst where {id, userId}`,
    сценарии по порядку), `getProjectChanges` (журнал с подписями полей; чужой проект — null).
  - Запись: `insertProject` (расчёт на сервере; необязательный фиксированный id — для
    демо-проекта сева) и `storeProjectCalculation`. Вторая в одной транзакции пишет параметры,
    результаты с версиями, сценарии (удаление отсутствующих ключей, upsert остальных, временные
    имена при обмене названиями) и журнал.
- **Серверные действия — `lib/projects/actions.ts`** (`"use server"`, экспортируются только
  асинхронные функции). Порядок в каждом: `auth()` → проверка → владелец → try/catch →
  `{ok | reason, message}`. `redirect` вызывается вне try, после записи —
  `revalidatePath('/projects')` и `revalidatePath('/projects/[projectId]', 'page')`.
  - `createProjectAction(prev, formData)` — форма «Новый проект» (демо-данные, ручной ввод или
    файл, который проверяется заново). Сценарии по умолчанию, расчёт на сервере, переход в
    проект.
  - `saveProjectAction(projectId, {name?, params, scenarios, changes})` — пересчёт на снимке
    сохранённого расчёта, запись сценариев и журнала. Результаты браузера не принимаются.
  - `recalcProjectAction(projectId)` — пересчёт на живых данных.
  - `copyProjectAction(projectId)` — «{название} (копия)», без журнала, с `copiedFromId`.
  - `deleteProjectAction(projectId)` — каскадное удаление и переход к `/projects`.
  - Демо-проект (`isDemo`, общий демо-аккаунт жюри) нельзя сохранить, пересчитать или
    удалить: `reason: 'invalid'` с подсказкой «скопируйте проект». Копировать можно.
- **Печать демо-чисел — `scripts/print-demo-numbers.ts`** (ТЗ §5.6). Скрипт читает живые
  данные БД: базовые параметры склада и сценарии «Как есть», покупка и RaaS Ronavi H1500,
  покупка DMR Carrier P. Он печатает:
  - таблицу сценариев: состав, CAPEX, OPEX, эффект, окупаемость с интервалом, ROI по ТЗ, NPV,
    дисконтированную окупаемость, TCO, имитацию;
  - парк: λпик, норму, цикл, плечи, Nточн, N, N по норме, вердикты имитации, минимальный
    устойчивый парк;
  - три сильнейших рычага каждого сценария и вывод;
  - второй блок «Новый проект со сценариями по умолчанию» — те же таблицы и вывод для
    проекта, который получит член жюри по §5.4 («Новый проект» → демо-данные, сценарии
    выбирает подбор). Если подбор предлагает те же сценарии, блок сводится к одной строке.

  Ключ `--markdown` оставляет только Markdown. Вывод детерминирован (без даты и длительностей),
  поэтому повторный прогон даёт тот же файл. Ключ `--offline` берёт данные из кода — это
  проверка до сева. Код выхода 1 — неожиданный отказ или имитация не выполнена, 2 — неверные
  аргументы.

(риски: цена не подтверждена, пилотная эксплуатация), при горизонте ≤ 4 лет — услуга H1500;
порог зарплаты 110 939 ₽/мес. Презентация (демонстрация с Carrier P) рекомендует услугу H1500.
Закрепить ли вторую покупку склада или показывать оба блока — решение владельца на шлюзе W2.

**Решения, принятые в реализации (отличия от спецификации задачи):**
- При ошибке в параметрах отказ получает и «Как есть», а не только сценарии роботизации.
  Иначе на экране остались бы ФОТ и TCO, посчитанные на базовых значениях, подставленных
  вместо ошибочных, — числа, которых пользователь не вводил.
- Ручной сервис (`serviceRubYearOverride`) может быть 0 («входит в цену»), как допускает
  движок T1.2. Остальные ручные значения должны быть больше нуля.
- Снимки — только продукты сценариев (как в спецификации). Подбор при повторном открытии
  видит живой каталог, а продукты сценариев подменяются снимком (`withSnapshotProducts`).
  Сценарии и вывод воспроизводятся бит-в-бит. Подбор и сравнение совпадают, пока каталог не
  менялся; изменение каталога видно по `liveDataVersion`.
- Сохранение из рабочей области считает на снимке сохранённого расчёта — те же данные, что
  видел пользователь. `recalcProjectAction` считает на живых данных.
- Процессы берутся из кода (`processesForFacility`), а не из таблицы Process. Иначе
  переименование процесса администратором меняло бы воспроизводимый расчёт.
- Запись проекта вынесена из действий в `lib/projects/queries.ts` (`insertProject`,
  `storeProjectCalculation`), чтобы API (T3.5) и сев демо-проекта (T3.6) не дублировали
  логику.
- `ScenarioSimInputs` дополнен полями `assumedUtilPct` (загрузка из нормативов сценария для
  сводки имитации) и `provenance` («Откуда параметры» адаптера toSimInput — для экрана
  имитации T2.3).
- `print-demo-numbers --markdown` не печатает дату генерации: T4.3/T6.1 сверяют файл через
  `git diff --exit-code`, а дата сделала бы файл неповторяемым. В заголовке — версии модели,
  имитации и данных и выпуск данных БД.
- Добавлен ключ `--offline` (данные из кода) — для проверки до сева. Он явно помечен в
  заголовке вывода.
- Если у проекта удалить сценарий, его прежние записи журнала удаляются каскадом (так задана
  схема T0.2: `ChangeLog.scenarioId … onDelete: Cascade`). Сама запись `scenario:remove`
  сохраняется: у неё нет ссылки на сценарий, ключ записан в `entityId`.

#### Исправления по ревью T2.2

- **Исключённое подбором решение больше не проходит «молча»** (ТЗ §3.4: «не рекомендовать,
  если ключевое ограничение делает применение невозможным»; план §4: ⚠ сопровождает ручное
  добавление везде). `buildProjectModel` выполняет подбор до экономики. Если в сценарии стоит
  решение со статусом подбора «исключён» (правила R1–R6, в том числе продукт не для этого
  процесса) и клиент не пометил его как добавленное вручную, модель сама ставит
  `manuallyAdded: true` и причину подбора с хвостом `AUTO_MANUAL_SUFFIX` («… [отмечено
  автоматически]»). Отсюда риск MANUAL_ADD, ⚠ в сравнении, отчёте и XLSX. Отметка сохраняется
  в сценариях проекта, идемпотентна и снимается, когда решение снова проходит подбор (например,
  после правки массы паллеты); пометку и причину пользователя платформа не трогает. Правило
  одно для браузера, `saveProjectAction`, `insertProject` (API T3.5, сев T3.6) и пересчёта на
  живых данных.
- **Сценарий с исключённым решением не рекомендуется**, даже при наибольшем NPV — и при
  пометке пользователя тоже. Вывод строится по остальным сценариям, первым пунктом
  объясняется: «„Покупка — DMR 600“ не рекомендуется: подбор исключил решение (DMR 600 —
  грузоподъёмность 600 кг < масса груза 800 кг); расчёт показан только для сравнения». Если
  исключены все решения роботизации — «Рекомендации нет: … выберите применимое решение».
- **Планировка склада не строится → отказ, а не парк по паспортной норме.** Площадь не задана
  или больше 1 000 000 м², проезд или проход не шире 0 м, ворот меньше одного — сценарии с
  мобильными роботами на процессе с расчётом получают отказ `invalid_inputs` с полем
  (`param:receivingDocksCount` и т. п.) и подсказкой, как исправить. «Как есть» считается.
  Строки сравнения таких роботов остаются без парка и NPV, смена вывода по горизонту их не
  пересчитывает.
- **Версия данных учитывает описания параметров** объекта (ключ, подпись, единица, вид,
  варианты, базовое значение, min/max, фиксация, обязательность): правка администратором
  границ или умолчаний параметра зажигает баннер «Пересчитать на актуальных данных».
  Подсказки и примеры в версию не входят. `projectDataVersion(snapshots, norms, defs)` и
  `liveDataVersionFrom` считают одинаково; БД после сева и код дают одну версию.
- **Журнал:** норматив, изменённый в сценарии (`norm:<key>` с ключом сценария), пишется как
  запись сценария со ссылкой на него; без ключа — как запись проекта.
- **Проверка сценариев:** переопределение норматива вне диапазона отклоняется («норматив
  „Коэффициент загрузки робота“ — укажите от 0,7 до 0,85 (доля), сейчас 5»), а не прижимается
  движком молча. Сообщения без английских ключей: «цена робота, ₽ — укажите число больше
  нуля», «вид сценария — „Как есть“ (asis), „Покупка“ (purchase) или „Услуга (RaaS)“ (raas)»,
  названия процессов и типа объекта по-русски.
- **Демо-проект защищён:** сохранение, пересчёт и удаление `isDemo`-проекта отклоняются с
  подсказкой скопировать проект.
- **Имитация при сохранении:** общий бюджет подборов минимального парка 40 с на проект
  (плюс 20 с на сценарий), чтобы синхронный расчёт укладывался в 60 с ТЗ §4.3.3 и при 9
  сценариях роботизации.
- **Список проектов** читает из jsonb только вид, статус и окупаемость сценариев (`$queryRaw`),
  а не весь снимок расчёта (≈150 КБ на проект).
- **`print-demo-numbers`** печатает второй блок — новый проект со сценариями по умолчанию.

**Решения по ревью (отличия от предложенного):**
- Из двух вариантов для исключённого решения выбрана автоматическая отметка в модели, а не
  отказ сохранения: отказ ломал бы пересчёт на живых данных и сохранение после правки
  параметров, когда решение становится исключённым не по вине клиента. Дополнительно (сверх
  предложенного) такой сценарий не рекомендуется.
- Статус подбора «не хватает данных» отметкой не считается: без производительности расчёт сам
  откажет (`throughput_required`), а с производительностью, заданной пользователем, расчёт
  законен и помечен источником «задано вами».
- Для планировки выбран отказ, а не риск CYCLE_UNAVAILABLE: парк по норме на реальных плечах
  занижен в разы, и показывать его числом — значит показывать заведомо неверный расчёт.
- Ключ сценария у `norm:`-изменения не сделан обязательным: без ключа запись принимается как
  изменение проекта, чтобы ошибка клиента не срывала сохранение на демонстрации.
- Вторая покупка склада по умолчанию не закреплена: это решение владельца. Вместо этого
  `print-demo-numbers` печатает числа нового проекта вторым блоком.
