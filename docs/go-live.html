What this app actually needs

Read this before choosing a host — it rules two popular options out.

01

Prove the tree is green

cd ~/robotization-roi-platform
docker compose up -d                       # local DB on host port 5433
lsof -ti:3000 | xargs kill -9 2>/dev/null  # a stale dev server makes e2e test the OLD build

npx tsc --noEmit                    # 0 errors
npx --yes vitest run < /dev/null    # 238 passing / 24 files
npm run lint -- --max-warnings=0    # silent = pass
npm run build                       # 0 errors
npx playwright test                 # 4 passing
This one bites

Both comments on the first two lines are load-bearing. A dev server left on :3000 is reused by Playwright, which then tests a build from an hour ago and reports failures that have nothing to do with your change. And < /dev/null on vitest is not decoration — without it the runner waits on stdin and looks hung.

02

Decide what ships

The work is 44 commits on refactor-pass, unmerged — the branch rule requires sign-off before a --no-ff merge. Pick one:

# (a) sign off and merge — deploy master
git checkout master && git merge --no-ff refactor-pass && git checkout refactor-pass

# (b) or leave master alone and point the host at the branch
#     Vercel → Settings → Git → Production Branch → refactor-pass

Option (b) is the honest one for a review deploy: peers see the branch, master stays the last signed-off state.

03

Push to GitHub needs your account

There is no remote configured yet — which is also why CI has never actually run.

git push -u origin master          # and/or: git push -u origin refactor-pass

Nothing secret is in the tree: .env* is gitignored and .env.example holds placeholders. Confirm before pushing anyway —

git ls-files | grep -E '^\.env'    # expect only .env.example
Already handled

.github/workflows/ci.yml starts running the moment the remote exists. It has been inert this whole time, so the first push is also the first real CI run — expect it to reproduce the §01 gate exactly.

04

Provision Postgres needs your account

neon.tech → new project → copy both connection strings.

StringRecognise it byUsed for
Pooledhost contains -poolerDATABASE_URL on the host — what the running app uses
Directno -poolermigrations and the seed, run from your laptop
This one bites

They are not interchangeable. @prisma/adapter-pg opens a connection pool per serverless instance, so the runtime needs the pooler. But prisma migrate deploy takes advisory locks that a transaction-mode pooler can drop, so migrations must not go through it. Using the wrong one fails in a way that looks like a network flake.

DATABASE_URL="<DIRECT url>" npx prisma migrate deploy
DATABASE_URL="<DIRECT url>" npm run db:seed
DATABASE_URL="<DIRECT url>" npx prisma migrate status   # expect "up to date"

Both are idempotent: the seed upserts, and it skips pruning any demo row a saved analysis references rather than tripping the onDelete: Restrict foreign key. Safe to re-run.

05

Deploy on Vercel needs your account

  1. vercel.com/new → import the repo. The framework preset auto-detects as Next.js; change nothing in Build & Output Settings.
  2. Add two environment variables, to Production and Preview:
NameValue
DATABASE_URLthe pooled Neon URL
AUTH_SECRETopenssl rand -base64 32 — generate a fresh one, don’t reuse the dev value

AUTH_URL is not needed: auth.ts sets trustHost: true and Vercel supplies the host. Then deploy.

Already handled — don’t configure these

postinstall: prisma generate runs on every install, so Vercel’s dependency cache can’t serve a stale Prisma client. That is the classic Vercel + Prisma failure and it is closed.

output: "standalone" in next.config.ts exists for the Docker image; Vercel’s builder produces its own output and ignores it. If a build ever objects, deleting that single line is the entire fix — nothing but the Dockerfile depends on it.

CSP, HSTS, X-Frame-Options, X-Content-Type-Options and Referrer-Policy ship from next.config.ts rather than host config, so they survive a change of host.

Don’t

Do not add prisma migrate deploy to the Build Command. It would run on every preview deploy, against the pooled URL — both of the things §04 says not to do. Migrations stay manual and deliberate: there is one migration path and you decide when it runs.

06

Netlify, and why not GitHub Pages

Netlify works, with one caveat worth weighing before spending an evening on it. Next’s own deployment docs — the copy shipped inside the installed package, at node_modules/next/dist/docs/01-app/01-getting-started/17-deploying.md — list Vercel and Bun as verified adapters that run the full Next.js compatibility suite, and place Netlify under “not built on the public Adapter API and not verified by the Next.js team, so feature support and compatibility may vary.” This app is Next 16.3.1, new enough that runtime lag is a live risk rather than a theoretical one.

If you deploy there anyway: import from GitHub, build command npm run build, publish directory .next, let Netlify install its Next.js runtime plugin, same two environment variables. Then smoke-test login specifically — cookie handling on Server Actions in a Lambda-backed runtime is where an unverified adapter breaks first.

Not possible

GitHub Pages cannot host this app. It serves static files, and every route here renders on the server. GitHub’s role in this stack is the git remote and CI.

07

Smoke-test the live URL

Five minutes. Do all four — two of them exercise paths that only break in production.

/ loads and the industry picker renders Environment variables are set and the database is reachable.
/compare/warehouse lists solutions The seed ran. An empty table here means §04 was skipped, or it ran against a different database.
Sign up, log out, log back in AUTH_SECRET is set and cookies work over HTTPS. Logging in is the half that fails; signing up alone proves nothing.
Calculate → «Сохранить расчёт» → «Открыть отчёт» → print preview The report must print light even with the OS in dark mode, and its figures must match the calculator panel exactly. Both have regressed before; both are now covered by tests, and this is the human check on top.
08

Two chores, once

Verify the cited figures before showing anyone

npm run check:sources     # non-zero if any citation is older than 180 days

docs/data-provenance.md promises every real figure is checked before it is shown; this is that gate. It is deliberately not in CI — a check that fails when a date rolls over would turn the build red for something no commit caused.

Schedule a prune of the rate-limit table

One row accumulates per (email + IP) and per IP. A credential-stuffing burst against random addresses can add a great many.

DELETE FROM "RateLimit" WHERE "windowStart" < now() - interval '1 day';

Daily is plenty. Neon can run it as a scheduled query; a Vercel Cron hitting a small protected route works too.

If you put a proxy in front

The limiter reads the client IP from X-Forwarded-For, so your proxy must overwrite that header, not append to it — otherwise a client spoofs the leftmost hop and rotates it to walk straight past the limit. Vercel and most CDNs overwrite by default. On nginx that means proxy_set_header X-Forwarded-For $remote_addr;, not $proxy_add_x_forwarded_for.

09

Rolling back

Vercel keeps every deployment: Deployments → the previous one → Promote to Production. Instant, no rebuild.

This one bites

That rolls back code, not the database. If the deploy included a migration, roll the code back first and decide about the schema separately. One migration in the history is destructive by design — 20260903172455_saved_analysis_solution_fk deletes orphaned rows before adding the foreign key — and re-running an older build does not undo it.

—

For reviewers

Three judgment calls in here are arguable. If you disagree with any of them, that is the useful feedback.

  • Migrations are manual, not in the build command. The trade is a deliberate human step against the risk of preview deploys migrating production over a pooler. On a team with more than one deployer, the calculus changes.
  • Netlify is documented but not recommended. Based on Next 16’s own verified-adapter list rather than a failure I actually reproduced. If someone has shipped Next 16 on Netlify recently, that beats the docs.
  • Vercel Hobby forbids commercial use. If this gets shown to paying clients, that is the Pro plan — not a technicality to wave through. Neon’s free tier and Vercel Hobby otherwise carry this comfortably.

One known cosmetic gap, tracked and open: the visualization canvas has a fixed 720×360 backing store displayed at roughly 470 px, so it is about 1.5× oversampled — sharper than 1× but soft on a 2× display. It affects no figure the app reports.
