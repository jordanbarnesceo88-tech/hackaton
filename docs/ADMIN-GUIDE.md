# Руководство администратора

> Руководство для ТЗ §6.7 и §6.6: как вести каталог и характеристики с источниками, нормативы
> и параметры по умолчанию, как обновлять данные организатора и читать журнал. Правки
> администратора меняют числа расчёта новых и пересчитанных проектов, поэтому каждая из них
> пишется в журнал (ТЗ §3.3.5, §3.5.4). Руководство пользователя —
> [USER-GUIDE.md](./USER-GUIDE.md).
>
> Места для снимков экрана помечены «[Снимок N: …]».

## 1. Доступ

- Демо-аккаунт администратора: `admin@demo.local` / `demo-admin-2026`. Пароль задаётся при
  севе переменной `DEMO_ADMIN_PASSWORD`; на стенде, доступном извне, задайте свой и передайте
  жюри отдельно (раздел 9).
- Ссылка «Админка» появляется в шапке, только если роль ADMIN записана и в сессии, и в базе.
- Каждая страница `/admin/*` и каждое действие администратора заново проверяют роль по базе.
  Гость уходит на страницу входа, пользователь без роли ADMIN получает 404 — даже с
  устаревшим токеном, в котором записан ADMIN.
- Интерфейса назначения ролей нет. Роль ADMIN получает демо-аккаунт при севе. Назначить её
  другому пользователю может только владелец базы запросом
  `UPDATE "User" SET role = 'ADMIN' WHERE email = '<почта>';`.

Разделы админки: «Обзор», «Каталог», «Нормативы», «Параметры объектов», «Данные и журнал».

## 2. Обзор (`/admin`)

Состав каталога по глубине описания («Обогащённый», «Примеры решений», «Идентификация»);
сколько продуктов требуют проверки, лежат в архиве, заведены администратором или правлены
им; сколько нормативов и параметров правлено; последний выпуск данных организатора; последние
10 действий в журнале.

## 3. Каталог (`/admin/catalog`)

**Список.** Поиск по названию, производителю, описанию и slug (регистр и «ё» не важны).
Отборы: действующие, требуют проверки, с правками администратора, заведены администратором,
в архиве, все. Чипы строки: «администратор», «правка», «архив», «исключён», «требует
проверки». По 100 строк на страницу.

**Создать продукт.** Форма: название, производитель, страна, тип решения, статус
(эксплуатация, пилот, НИОКР), описание, процессы. Продукт получает происхождение «Администратор»
и slug вида `admin-<название латиницей>`, который не пересечётся с продуктами организатора.
После создания открывается карточка: заполните характеристики, без производительности и цены
продукт не посчитается в сценарии.

### 3.1 Карточка продукта (`/admin/catalog/[slug]`)

**Идентификация**: название, производитель, страна, тип решения, статус, «Исключить из
подбора» с обязательной причиной, «В архиве». Изменённое поле записывается и в
соответствующую характеристику (название → «Наименование (модель)», страна → «Страна
происхождения» и т. д.), поэтому заголовок карточки и характеристики не расходятся.

**Характеристики** — все ключи ТЗ §3.3.4 по шести группам: идентификация, технические
характеристики, требования к инфраструктуре, экономика, применимость, качество данных.
Незаполненные тоже показаны — «Заполнить». У заполненных — значение, бейдж источника, цитата
«как в источнике» и другие найденные значения. «Изменить» открывает форму; поля зависят от
вида характеристики:

| Вид | Поля |
|---|---|
| Число или диапазон | значение, «от», «до», оговорка («до», «от», «≈»), к чему относится (на робота, станцию, канал или парк), единица |
| Текст | текст |
| Перечень | пункты, по одному на строку (разделитель — только перевод строки: внутри пункта бывает «;») |
| Все виды | ссылка на первоисточник, дата проверки, «Подтверждено первоисточником», примечание |

Правила сохранения характеристики:
- Сохранённая строка получает происхождение «Администратор», продукт — отметку «правка».
- Если изменились значение или ссылка, цитата и основание прежнего значения очищаются: они
  относились к другому числу.
- Новое или изменённое значение с отметкой «Подтверждено первоисточником» без ссылки не
  принимается. Исключение — значение, уже подтверждённое по месту в данных организатора: при
  правке только даты или примечания отметка сохраняется.
- Сохранение без правок отвечает «Изменений нет» и ничего не пишет.
- После записи пересчитываются вынесенные колонки (цена, производительность в расчёт,
  полнота, доля подтверждённых, «требует проверки») той же функцией, что у синхронизации, и
  строки «Качества данных» («Подтверждение» — «N из M подтверждены», «Дата проверки»).

**Какое число идёт в расчёт.** Производительность попадает в расчёт парка, только если она
дана на один робот или одну станцию, в единицах процесса и не как «до X». Значение «на весь
парк» показывается, но в расчёт не идёт. Сводка карточки показывает, что именно пойдёт в
расчёт, и причины «требует проверки».

**Действия с продуктом:**
- «В архив» и «Вернуть из архива». Архивный продукт пропадает из каталога и подбора, снимки
  в сохранённых проектах остаются.
- «Вернуть данные организатора» (с подтверждением) удаляет правки администратора и
  возвращает продукт к данным организатора поле в поле.
- Удаление — только для продуктов, заведённых администратором, с отметкой «Подтверждаю
  удаление». Продукт организатора удалить нельзя («Удалить нельзя: данные организатора —
  используйте «В архив»»). Продукт, выбранный в сценарии проекта, тоже не удаляется
  («используется в проектах — переведите в архив»).
- История правок продукта — последние 30 записей журнала.

### 3.2 Поля провенанса

У каждой характеристики (таблица `ProductCharacteristic`) хранится:

| Поле | Смысл |
|---|---|
| Происхождение | «Организатор», «Открытый источник», «Оценка», «Расчёт», «Наш выбор», «Администратор» |
| Тип источника | датасет, каталог или «Примеры решений» организатора; сайт производителя; документ производителя; дилер; агрегатор; пресса; расчёт; оценка команды; правка администратора |
| Ссылка / место | https-ссылка на первоисточник или место у организатора («Датасеты_хакатон.xlsx › Склад › стр. 4», «каталог организатора › id …») |
| Дата проверки | когда значение сверено с источником |
| Подтверждено | значение совпадает с документом или сайтом производителя |
| Уверенность | высокая, средняя, низкая — по проверке находки |
| Как в источнике | дословная цитата |
| Основание, формула | для оценок и расчётных значений |
| Область | на робота, на станцию, на канал, на парк |
| Альтернативы | другие найденные значения с их источниками; «⚠ есть расхождения», если они отличаются больше чем на 10 % |

Правила выбора основного значения — в [data-provenance.md](./data-provenance.md), раздел
«Организатор: датасеты, каталог, примеры; исследование svod + found_batch».

## 4. Нормативы (`/admin/norms`)

Нормативы сгруппированы: режим и загрузка, труд, CAPEX, OPEX, финансы, интерпретация,
имитация, подбор. У каждого — значение, допустимый диапазон, значение по умолчанию,
происхождение, источник и обоснование.

- Новое значение вводится с «Основанием правки».
- Значение вне диапазона прижимается к границе, и сообщение называет сохранённое число
  (например, загрузка 0,99 сохранится как 0,85).
- «Сбросить к умолчанию» возвращает значение из кода и снимает отметку правки для одной
  строки.
- Веса балла подбора после правки нормируются к сумме 1; «долгая» граница окупаемости не
  становится ниже «быстрой».

Новый норматив действует на новые расчёты. Сохранённые проекты хранят снимок нормативов и не
меняются; у них появляется баннер «Пересчитать на актуальных данных».

## 5. Параметры объектов (`/admin/params`)

Выбор объекта: склад, аэропорт, медучреждение. Параметры сгруппированы по разделам датасета
организатора. Правятся базовое значение, минимум, максимум, «обязательный», подсказка, пример
и основание правки. Базовое значение проверяется так же, как ввод пользователя, и по новым
границам; при смене границ пересчитывается признак «зафиксирован» (минимум равен максимуму).

Изменения сразу действуют в форме параметров, шаблонах Excel/CSV, проверке загрузки и API.
Правка границ или значения по умолчанию меняет версию данных, и сохранённые проекты покажут
баннер «Пересчитать на актуальных данных». Подсказки и примеры на версию не влияют.

Добавить новый параметр или тип объекта через интерфейс нельзя — только через данные
генератора и сев ([ARCHITECTURE.md](./ARCHITECTURE.md), §12).

## 6. Данные и журнал (`/admin/data`)

**Выпуски данных**: версия, дата загрузки, состав выгрузок организатора, отметка текущей
версии.

**«Обновить каталог»** запускает синхронизацию данных организатора, которые лежат в сборке
(`lib/data/organizer`), с базой. Правки администратора сохраняются. Отчёт по-русски: сколько
записей создано, обновлено, пропущено из-за правок администратора, отправлено в архив;
сколько источников старше 180 дней; построчные подробности. Продукт организатора, которого
больше нет в данных, уходит в архив, а не удаляется.

Обновление — по запросу администратора (ТЗ §3.3.6). Планового автообновления нет.

**Журнал**: последние 100 действий администратора — когда (МСК), кто, объект, поле, было,
стало, основание. Корректировки внутри проектов пользователей — в журнале самого проекта.

## 7. Как обновить данные организатора

Если организатор прислал новые файлы или исследование дополнено:
1. Выгрузите нужные листы в JSON в папку вне репозитория (формат —
   [data-provenance.md](./data-provenance.md)).
2. `ORGANIZER_DATA_DIR=<папка> npm run gen:organizer` — перегенерирует
   `lib/data/organizer/*.generated.*`. Без переменной генератор скажет, что указать; если
   файлов не хватает, перечислит их.
3. Проверка и сборка: `npx vitest run lib/data/organizer`, затем `npm run build`.
4. `npm run db:seed` на стенде или «Обновить каталог» в админке после выкладки сборки.
5. `npx tsx scripts/print-demo-numbers.ts` — если демо-числа изменились, это изменение
   «МЕНЯЕТ ЧИСЛА», его фиксируют в CHANGELOG с было/стало.

Оригиналы организатора (xlsx, csv, docx) в репозиторий не добавляются.

## 8. API для администратора

- `PUT /api/v1/norms` — запись нормативов с тем же прижатием к диапазону и журналом.
- `POST /api/v1/catalog/import?dryRun=1` — проверка списка продуктов без записи;
  без `dryRun` — запись. Проверка строгая: любая ошибка — ответ 422 с ошибками по позициям,
  ничего не записано. Провенанс каждой характеристики проверяется по правилам: у значения
  организатора — место, у найденного в источнике — https-ссылка, цитата и дата, у оценки —
  основание.
- Доступ: сессия администратора или заголовок `Authorization: Bearer <ADMIN_API_TOKEN>`
  (переменная окружения не короче 16 символов; без неё вход по токену выключен).

Описание — `/api-docs` и [INTEGRATIONS.md](./INTEGRATIONS.md).

## 9. Демо-аккаунты

| Аккаунт | Роль | Пароль по умолчанию | Переменная |
|---|---|---|---|
| `demo@demo.local` | пользователь | `demo-user-2026` | `DEMO_USER_PASSWORD` |
| `admin@demo.local` | администратор | `demo-admin-2026` | `DEMO_ADMIN_PASSWORD` |

- Аккаунты создаёт `npm run db:seed` (в Docker — сервис `migrate`). Повторный сев приводит
  роль к заданной и перехэширует пароль, только если он изменился.
- Пароль длиннее 72 байт — ошибка сева.
- На стенде, доступном извне, задайте свои пароли переменными и передайте их жюри отдельно,
  не в репозитории.
- Лимит входа для адресов `@demo.local` — 100 попыток за 15 минут на пару «почта + адрес»;
  общий лимит на один адрес — 50 за 15 минут.
- Демо-проект «Склад организатора (демо)» (`demo-warehouse`) принадлежит `demo@demo.local`,
  пересоздаётся при каждом севе и защищён от сохранения, пересчёта и удаления — жюри
  копирует его.
