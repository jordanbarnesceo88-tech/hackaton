# Интеграции и API платформы

Документ описывает, как платформа обменивается данными с внешними системами (ТЗ §3.8.1–§3.8.5,
§4.2.5): что уже работает через API v1, как подключить WMS, ERP и 1С, мониторинг и аналитику
ФЦ БАС, как устроена безопасность и что пока не построено.

- **Описание для людей:** страница `/api-docs` — все методы с доступом, параметрами и примерами
  запросов и ответов.
- **Машиночитаемое описание:** `GET /api/v1/openapi.json` (OpenAPI 3.1). Из него генерируются
  клиенты, его открывают Swagger UI и Redoc.
- Описание, страница и маршруты не расходятся: страница строится из того же объекта
  `lib/api/openapi.ts`, а тест `lib/api/openapi.test.ts` проверяет, что каждый обработчик в
  `app/api/v1` описан и каждое описание имеет обработчик.

## 1. Состав API

| Метод | Путь | Доступ | Назначение |
|---|---|---|---|
| GET | `/api/v1/catalog` | гость | Каталог с фильтрами, поиском, сортировкой, страницами по 50 |
| GET | `/api/v1/catalog/{slug}` | гость | Карточка продукта: характеристики с источником, датой и подтверждением |
| POST | `/api/v1/catalog/import` | администратор | Импорт до 200 продуктов (`?dryRun=1` — только проверить) |
| GET | `/api/v1/norms` | гость | Нормативы модели с границами, происхождением и обоснованием |
| PUT | `/api/v1/norms` | администратор | Изменить нормативы (прижатие к границам, журнал изменений) |
| GET | `/api/v1/facility-types/{slug}/params` | гость | Параметры склада, аэропорта или медучреждения: ключи, единицы, диапазоны |
| POST | `/api/v1/calculate` | гость | Расчёт сценариев без сохранения |
| POST | `/api/v1/projects` | пользователь | Создать проект с расчётом |
| GET | `/api/v1/projects/{id}` | пользователь (владелец) | Проект с параметрами, сценариями, результатами и версиями |
| GET | `/api/v1/openapi.json` | гость | Описание API в OpenAPI 3.1 |
| GET | `/api/health` | гость | Состояние сервиса и базы для мониторинга |
| GET | `/api/templates/{facility}?format=csv\|xlsx` | гость | Шаблон файла параметров объекта |

Все ответы — JSON, денежные величины — в рублях. Ошибка всегда имеет вид
`{ "error": "…", "details": … }`: в `error` по-русски сказано, что не так и как исправить, в
`details` — ошибки по полям или позициям. Коды ответов:

- 400 — тело не JSON;
- 401 — нужен вход или токен;
- 403 — нужна роль администратора;
- 404 — не найдено;
- 413 — тело слишком большое;
- 415 — нет `Content-Type: application/json`;
- 422 — данные не прошли проверку, ничего не записано;
- 429 — превышен лимит, заголовок `Retry-After` говорит, через сколько секунд повторить;
- 503 — база недоступна.

## 2. WMS, ERP и 1С → объект и объёмы

Внешняя система передаёт параметры объекта в поле `params`. Ключи и единицы перечислены в
`GET /api/v1/facility-types/warehouse/params`, там же для каждого параметра указаны базовое
значение и диапазон организатора, пример и источник. Есть два пути:

- **`POST /api/v1/calculate`** — расчёт без сохранения, вход не нужен. Подходит для
  периодической сверки: например, WMS раз в сутки отправляет фактические объёмы и получает
  окупаемость и вывод.
- **`POST /api/v1/projects`** — проект пользователя. Он сохраняется с версиями модели и данных и
  открывается на сайте по адресу из поля `url`. Параметры проходят ту же проверку, что форма
  «Новый проект» и загрузка файла:
  - неизвестный ключ, неверный тип, единица или вариант — 422 со списком `ParamIssue`;
  - значение вне диапазона организатора принимается и возвращается в `warnings`;
  - параметры, которых нет во входе, получают базовые значения организатора.

Сопоставление полей для склада: основные ключи и откуда их взять. Полный список (52 параметра:
42 из датасета организатора и дополнения модели) отдаёт API. Столбец «В расчёте» показывает,
влияет ли ключ на экономику, парк и имитацию процесса «Перемещение паллет» — единственного
процесса склада, который в этой версии считается полностью. Остальные ключи нужны подбору по
другим процессам и схеме объекта; их экономика — прототип (раздел 8).

| Источник | Что взять | Ключ `params` | Единица | В расчёте |
|---|---|---|---|---|
| WMS | Приёмка: паллет за сутки (среднее по рабочим дням) | `inboundPalletsPerDay` | поддон/сут | да — спрос |
| WMS | Отгрузка: паллет за сутки | `outboundPalletsPerDay` | поддон/сут | да — спрос |
| WMS | Внутренние перемещения: подпитка, перестановки | `internalPalletMovesPerDay` | паллет/сут | да — спрос |
| WMS | Пиковый коэффициент: пиковый час ÷ средний час | `peakFactor` | — | да — пиковый поток и парк |
| WMS | Доля негабаритных грузов (их возят только люди) | `nonStandardCargoPct` | % | да — спрос и высвобождаемый персонал |
| WMS | Средняя масса паллеты | `avgPalletMassKg` | кг | да — подбор по грузоподъёмности, имитация |
| WMS | Отбор: строк и штук за сутки | `pickLinesPerDay`, `pickUnitsPerDay` | строк/сут, шт./сут | нет — отбор и сортировка |
| WMS | Активные SKU, паллетоместа | `activeSkuCount`, `palletPositions` | SKU, паллетомест | нет |
| ERP/1С (кадры, ЗУП) | Операторы погрузчиков: численность | `forkliftOperatorsCount` | чел. | да — ФОТ «как есть» и высвобождение |
| ERP/1С (кадры, ЗУП) | Средняя начисленная зарплата оператора погрузчика (gross) | `forkliftSalaryRubMonth` | руб./мес. | да — ФОТ |
| ERP/1С (кадры, ЗУП) | Отборщики: численность и зарплата | `pickersCount`, `pickerSalaryRubMonth` | чел., руб./мес. | нет — отбор |
| ERP/1С (график) | Смен в сутки, длительность смены, рабочих дней в году | `shiftsPerDay`, `shiftDurationH`, `workDaysPerYear` | смен, ч, дн. | да — часы работы и спрос в час |
| ИТ-ландшафт | Есть ли WMS (в датасете организатора: «Наличие WMS обязательно для роботизации») | `hasWms` | «Да» или «Нет» | да — риск «нет WMS» |
| Паспорт здания, CAD | Площадь активной зоны, ширина главных проездов и рабочих проходов | `activeAreaM2`, `mainAisleWidthM`, `rackAisleWidthM` | м², м | да — планировка, плечи цикла, проходимость, инфраструктура |
| Паспорт здания, CAD | Ворота приёмки и отгрузки (в датасете организатора их нет — базовое значение модели является оценкой) | `receivingDocksCount`, `shippingDocksCount` | шт. | да — планировка и плечи цикла |
| Бюджет | Бюджет CAPEX, горизонт расчёта | `capexBudgetMRub`, `horizonYears` | млн руб., лет | да — риск превышения бюджета, горизонт NPV и ROI |

Пример: расчёт без сохранения с фактической зарплатой из 1С (значение — верхняя граница диапазона
организатора, 170 000 руб./мес.):

```bash
curl -s -X POST https://<адрес-стенда>/api/v1/calculate \
  -H 'content-type: application/json' \
  -d '{"facility":"warehouse","params":{"forkliftSalaryRubMonth":170000}}'
```

В ответе:

- `summary` — по строке на сценарий: CAPEX, OPEX, эффект, окупаемость, ROI, NPV, TCO, состав
  оборудования, вердикт имитации, отказ с причиной;
- `conclusion` — рекомендуемый сценарий, риски и оговорка о предварительной оценке;
- `results` — полный расчёт с формулами и подстановками, тот же, что хранится в проекте;
- `versions` — версии модели, имитации и данных.

Проект на тех же параметрах даёт те же числа: API вызывает ту же функцию расчёта
(`lib/projects/recalc.resultsFromInputs`), что и кнопка «Новый проект».

**Как интеграция входит под пользователем.** Проекты принадлежат пользователям, поэтому
`POST /api/v1/projects` требует cookie сессии. Серверная интеграция получает её стандартным
потоком Auth.js для входа по паролю: сервисная учётная запись, `GET /api/auth/csrf`, затем
`POST /api/auth/callback/credentials` с полями `csrfToken`, `email`, `password`, и cookie
сохраняется в хранилище cookie клиента. Личные API-ключи пользователей не построены (раздел 7).

## 3. Обновление каталога

- **Данные организатора** обновляет синхронизация: `npm run db:seed` или кнопка «Обновить
  каталог» в админке. Она обновляет по запросу, а не по расписанию.
- **Внешние источники** — например, реестр решений ФЦ БАС или карточки производителей —
  загружаются методом `POST /api/v1/catalog/import`. Доступ: администратор по сессии или токен
  (раздел 6).

Правила импорта:

1. Тело — список `ProductSeed` (до 200 продуктов, до 4 МБ). Это та же форма, в которой записаны
   данные организатора (`lib/data/organizer/catalog.generated.json`). Каждая карточка присылается
   целиком.
2. Проверка всё-или-ничего: при ошибке в любой позиции ничего не пишется, ответ 422 с ошибками по
   позициям. Неизвестные поля — ошибка.
3. У каждой характеристики должен быть провенанс (ТЗ §3.3.4):
   - `organizer` — нужен `sourceRef`;
   - `research` — нужны ссылка http(s) `sourceUrl`, цитата `asInSource` и дата;
   - `estimate`, `derived`, `choice` — нужно обоснование `basis`;
   - `derived` — нужна формула `formula`;
   - оценка (`estimate`) не бывает подтверждённой.

   Тип источника должен соответствовать происхождению. Дата проверки пишется в формате
   ГГГГ-ММ-ДД.
4. Продукт записывается с `origin: ADMIN`, как продукт, заведённый администратором:
   - синхронизация данных организатора его не трогает и не архивирует;
   - в каталоге он не выдаётся за данные организатора;
   - удалить его можно в админке.
5. Slug продукта из данных организатора не принимается. Такой продукт обновляет синхронизация, и
   правка через API откатилась бы при следующем обновлении. Дополнять его нужно в админке, где
   правка помечается и сохраняется.
6. Характеристику, исправленную администратором в админке (`origin: admin`), импорт не
   перезаписывает. В отчёте такие характеристики указаны в поле `adminCharacteristicsKept`.
7. Повторный импорт той же карточки ничего не меняет (`unchanged`). Характеристики, которых больше
   нет во входе, удаляются. Вынесенные колонки (цена, производительность, полнота,
   «требует проверки») пересчитываются по тем же правилам, что при синхронизации.
8. Карточки уровня `identification` видны только в каталоге. Карточки уровня `enriched` и
   `examples` участвуют в подборе и расчёте.

Рекомендуемый порядок работы: сначала `?dryRun=1` (проверка без записи), затем тот же запрос без
него.

```bash
curl -s -X POST 'https://<адрес-стенда>/api/v1/catalog/import?dryRun=1' \
  -H "authorization: Bearer $ADMIN_API_TOKEN" \
  -H 'content-type: application/json' \
  --data @products.json
```

Готовый пример тела — в `/api-docs`, раздел «Каталог». Это карточка уровня identification, её
характеристики скопированы из данных организатора вместе с источниками.

## 4. Нормативы

- `GET /api/v1/norms` отдаёт все нормативы модели. У каждого указаны значение, значение по
  умолчанию, итоговое значение в расчёте (после границ и взаимных ограничений), границы,
  происхождение, обоснование и источник.
- `PUT /api/v1/norms` (администратор) с телом `{"values":{"utilization":0.85},"reason":"…"}`
  работает так же, как страница «Нормативы» в админке:
  - значение вне [min, max] прижимается к границе, в ответе `clamped: true`;
  - зафиксированный организатором норматив не меняется;
  - строка помечается правкой администратора, и синхронизация её значение не перезаписывает;
  - каждое изменение пишется в журнал `ChangeLog`: сущность `norm`, было, стало, значение по
    умолчанию, кто и почему. Для входа по токену пользователь пустой, а причина помечена «через
    API (токен администратора)».

Новые и пересчитанные проекты считаются с новыми значениями. Сохранённые проекты хранят снимок
нормативов и открываются с прежними числами. Баннер на странице проекта сообщает, что данные
изменились с момента расчёта, и предлагает кнопку «Пересчитать на актуальных данных». Через API
то же видно по полю `dataChanged` в `GET /api/v1/projects/{id}`.

## 5. Мониторинг

`GET /api/health` предназначен для Docker healthcheck, CI и внешнего мониторинга (Zabbix, Prometheus
blackbox exporter, uptime-сервисы).

- 200 `{"ok":true,"db":true,"modelVersion":"tz-1.0.0","simModelVersion":"sim-1.0.0"}` — сервис и
  база доступны.
- 503 `{"ok":false,"db":false,…}` — база не ответила за 3 с. Причина пишется только в журнал
  сервера.
- Версии моделей в ответе показывают, какая сборка отвечает. Их же сохраняет каждый проект.
- Ошибки обработчиков пишутся в stdout и stderr контейнера (`docker compose logs app`). Наружу
  они не уходят.

## 6. Аналитика ФЦ БАС

- **Выгрузка каталога.** Обходите `GET /api/v1/catalog?page=1…pageCount`, при необходимости с
  фильтрами `facility`, `process`, `status`, `level`. Строки содержат вынесенные колонки: цену,
  ставку RaaS, производительность, грузоподъёмность, полноту карточки, долю подтверждённых
  характеристик и признак «требует проверки». Это готовая витрина качества данных. Провенанс
  каждой характеристики (источник, дата, подтверждение, альтернативные значения) отдаёт
  `GET /api/v1/catalog/{slug}`. `dataRelease` в ответе показывает, на каком выпуске данных
  организатора собран каталог.
- **Расчёты.** `POST /api/v1/calculate` воспроизводим: в `versions` указаны модель, имитация и хэш
  данных. Одинаковые входы на одном выпуске данных дают одинаковые числа. Проект пользователя
  отдаёт `GET /api/v1/projects/{id}`, а полный отчёт выгружается в XLSX и CSV со страницы
  проекта.
- **Клиенты.** По `GET /api/v1/openapi.json` генерируются клиенты на Python, TypeScript, Java,
  C# и т. д.

## 7. Безопасность

- **Роли** (ТЗ §3.1.1):
  - гость читает каталог, нормативы и параметры и считает без сохранения;
  - пользователь работает со своими проектами;
  - администратор импортирует каталог и меняет нормативы.
- **Сессия.** Cookie Auth.js (`authjs.session-token`, при HTTPS — `__Secure-authjs.session-token`),
  `HttpOnly`, `SameSite=Lax`. Роль администратора перечитывается из базы на каждый запрос: у
  пониженного администратора права пропадают сразу, а не после истечения сессии.
- **Токен администратора** — для серверных интеграций без браузера:
  - задаётся переменной окружения `ADMIN_API_TOKEN`, не короче 16 символов, например
    `openssl rand -hex 32`;
  - если переменная не задана или токен короче, вход по токену выключен целиком;
  - сравнение идёт в постоянном времени (SHA-256 и `timingSafeEqual`);
  - если заголовок `Authorization` передан, решает только он: неверный токен даёт 401, и запрос
    не проверяется по сессии;
  - токен даёт права администратора API, но не открывает страницы сайта.
- **Подделка запросов (CSRF).** Методы с телом принимают только `Content-Type: application/json`.
  HTML-форма с другого сайта не может отправить такой запрос без предварительного CORS-запроса, а
  CORS не включён. Cookie `SameSite=Lax` не уходят с кросс-сайтовыми POST.
- **Изоляция проектов** (§4.4.2). Проект читается только владельцем, чужой неотличим от
  несуществующего (404).
- **Ограничение частоты.**
  - `POST /api/v1/calculate`: 60 запросов за 15 минут с одного IP.
  - `POST /api/v1/projects`: 30 проектов за 15 минут на пользователя.
  - Счётчик хранится в Postgres и работает на нескольких экземплярах.
  - IP берётся из первого `X-Forwarded-For`. Обратный прокси обязан перезаписывать этот
    заголовок (DEPLOY.md).
- **Размер тела.** Расчёт и проект — до 200 КБ, нормативы — до 20 КБ, импорт каталога — до 4 МБ.
  Предел проверяется и по `Content-Length`, и по фактически прочитанным байтам.
- **HTTPS.** На стенде API работает через тот же обратный прокси с TLS, что и сайт. Сайт отдаёт
  `Strict-Transport-Security`. В docker-compose TLS не входит (ТЗ §4.4.4 закрывается на уровне
  прокси стенда).
- **Кеширование.** Ответы API идут с `Cache-Control: no-store`.
- **Загруженные файлы** не хранятся: файл параметров разбирается в памяти и отбрасывается
  (§4.4.6).

## 8. Что не построено

Метки по ТЗ §5.7:

| Возможность | Статус |
|---|---|
| Готовые коннекторы к конкретным WMS, ERP и 1С (адаптеры форматов, выгрузка по расписанию) | Не реализовано: API готов, интеграции описаны (раздел 2) |
| Вебхуки и уведомления внешних систем о пересчёте | Не реализовано |
| Личные API-ключи пользователей и OAuth для внешних приложений | Не реализовано: пользователь входит сессией, администратор — сессией или общим токеном |
| Список, изменение, копирование и удаление проектов через API | Не реализовано: в интерфейсе сайта есть, в API — создание и чтение |
| CORS для вызова API из браузера с других доменов | Не включено намеренно: API рассчитан на серверные интеграции |
| Плановое автообновление каталога | Частично: обновление по запросу (кнопка в админке, `db:seed`, импорт через API) |
| Импорт каталога в формате таблицы организатора (XLSX) через API | Не реализовано: API принимает JSON `ProductSeed`, таблица организатора загружается генератором данных |
| Проверка по государственным реестрам и расчёт мер господдержки | Не реализовано |
| Экономика и имитация через API для аэропорта и медучреждения | Прототип: расчёт возвращает сценарии с отказом `calc_not_supported` и объяснением, подбор и параметры работают |

Версия API — v1 в пути. Несовместимые изменения выйдут под `/api/v2`, а v1 останется на время
перехода. Изменения, которые меняют числа расчёта, повышают `modelVersion`, и это видно в каждом
ответе.
