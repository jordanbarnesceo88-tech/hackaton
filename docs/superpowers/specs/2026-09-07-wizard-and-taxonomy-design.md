# Пошаговый подбор + расширение таксономии (подпроекты A + B)

> Статус: черновик на вычитку, 2026-09-07. Ветка `wizard-taxonomy` (от `refactor-pass`).
> Объединяет два подпроекта из декомпозиции: **A** — каркас пошагового подбора и визуальный
> язык, **B** — расширение таксономии и классы решений. Третьим куском вошли сами классы
> решений: без них расширение отраслей ведёт в пустые ветки.
>
> **Этот документ не меняет ни одного выходного числа экономики.** Движок `lib/economics`
> не трогается. Изменение входов расчёта (ручное количество роботов, CAPEX, свои значения)
> вынесено в отдельную спеку D и требует отдельной подписи — как A1–A3.

## Зачем

Развёрнутое приложение работает, но пользователь видит четыре отрасли, четыре типа объектов
и экран сравнения, которому нечем ранжировать решения, кроме «цены за единицу годовой
производительности» — абстракции, ничего не говорящей про конкретный склад. Причина
структурная: **решение выбирается до того, как система узнала хоть что-то об объекте.**

Отсюда три следствия, которые чинятся вместе, а не по отдельности:

1. Порядок шагов переворачивается: параметры объекта спрашиваются **до** сравнения, и
   сравнение начинает отвечать на вопрос «что окупится у меня», а не «что дешевле вообще».
2. Опрос получает форму опроса — экран за экраном, с «Далее» и «Назад», а не одна форма.
3. Таксономия расширяется втрое, и вместе с ней появляются классы решений, иначе новые ветки
   упираются в пустой экран.

## Что входит и что не входит

| Входит | Не входит |
|---|---|
| Каркас пошагового подбора, 5 шагов | Дашборд сравнения (спека C) |
| Визуальный язык + правило ширин | Ручной ввод количества/CAPEX (спека D — меняет числа) |
| ~12 отраслей / ~45 типов объектов | Новые вендорские модели с ценами |
| ~12 классов решений с диапазонами | Изменения `lib/economics` |
| Разворот связи категорий | |

## Зафиксированные решения

| Вопрос | Решение |
|---|---|
| Порядок работ | A и B одной спекой |
| Ветки без решений | Добавить классы решений с диапазонами, помеченные «оценка» |
| Порядок шагов | Параметры объекта **до** сравнения |
| Масштаб данных | ~12 отраслей / ~45 типов / ~12 классов |
| Каркас | Шаги в URL, переходы навигацией (подход 1) |

## 1. Каркас подбора

### Route group вместо новых маршрутов

Группа `(wizard)` в Next не влияет на URL — она даёт общий layout. Существующие адреса
остаются прежними и получают оболочку подбора:

```
app/(wizard)/
  layout.tsx                     ← прогресс, «Далее»/«Назад», переходы
  onboarding/page.tsx            /onboarding            шаг 1 — отрасль
  onboarding/facility/page.tsx   /onboarding/facility   шаг 2 — тип объекта
  onboarding/params/page.tsx     /onboarding/params     шаг 3 — параметры объекта
  compare/[type]/page.tsx        /compare/warehouse     шаг 4 — решения с вашим ROI
  calculate/[solutionId]/page.tsx /calculate/abc        шаг 5 — детальный расчёт
```

`/compare/[type]` и `/calculate/[solutionId]` **сохраняют свои URL**. Это жёсткое требование:
на них ссылаются сохранённые расчёты, а `/report/[analysisId]` уже мог быть разослан клиентам.
Ломать чужие ссылки на выданный отчёт нельзя.

### Состояние в query-строке

Ответы накапливаются по шагам:

```
/onboarding/facility?industry=warehouse
/onboarding/params?industry=warehouse&facility=warehouse-retail
/compare/warehouse-retail?industry=warehouse&area=1000&ops=500&staff=10
```

Начиная с шага 4 тип объекта живёт в пути (`[type]`), а не в query — дублировать его в двух
местах значит завести два источника правды, которые разъедутся.

Свойства, которые это даёт бесплатно: обновление страницы ничего не теряет; любой шаг можно
скинуть ссылкой; браузерная кнопка «Назад» работает без нашего кода.

**Query-строка — это пользовательский ввод, и ей нельзя доверять.** Каждая страница-шаг
прогоняет параметры через существующие `withParamDefaults()` и `clampAssumption()` — те же,
что защищают путь сохранения. Никакого второго пути валидации не заводится.

### Навигация

- «Далее» неактивна, пока текущий шаг не заполнен. Это единственная блокировка.
- «Назад» доступна всегда и сохраняет уже введённое.
- Перепрыгнуть вперёд по прямому URL можно; страница сама определяет, хватает ли ей данных,
  и мягко возвращает на первый недостающий шаг, а не падает.
- Прогресс: тонкая полоса и «3 из 5».

### На чём считается шаг 4

Шаг 4 прогоняет движок по всем применимым решениям. Использует: **параметры объекта из
query-строки** + **`DEFAULT_ASSUMPTIONS`, прочитанные из БД** (те же, что уже грузит страница
расчёта), без пользовательских правок — правки допущений живут на шаге 5.

Это не деталь реализации, а условие паритета: шаг 5 для выбранного решения **стартует ровно с
тех же входов**, поэтому его первое отображённое число совпадает с тем, что пользователь видел
в списке. Как только пользователь правит допущения на шаге 5, числа расходятся законно — и
именно поэтому паритет-тест сверяет их **до** первой правки.

### Два режима layout

Пришли по подбору — видны прогресс и кнопки. Пришли из «Мои расчёты» прямо на
`/calculate/…` — оболочки нет: вы не в опросе, вы открыли сохранённый расчёт. Признак —
наличие параметров подбора в query-строке.

### Переходы

React `<ViewTransition>`; в Next 16 App Router работает **без конфигурации** (подтверждено в
`node_modules/next/dist/docs/01-app/02-guides/view-transitions.md`). Направленный сдвиг:
вперёд — влево, назад — вправо. Полностью отключается при `prefers-reduced-motion` — в
приложении уже есть рабочий приём для этого (`useSyncExternalStore` в визуализации).

## 2. Визуальный язык

Стиль и паттерн взаимодействия — разные слои. Паттерн «один экран — один раздел вопросов»
применяется к шагам 1–3. Стиль применяется везде, включая плотные экраны.

### Система

- **Крупная типографическая шкала.** Вопрос набран как заголовок 32–40px против текста 16px.
  Сейчас контраст 20/14 — отсюда ощущение скудости. Нужна гарнитура с характером; текущий
  Geist нейтрален по замыслу.
- **Один насыщенный акцент на мягком тонированном фоне** (не чистый белый), почти чёрный текст.
- **Поля с подчёркиванием, а не в рамке**, крупная активная зона. Кнопки — сплошная заливка
  акцентом, умеренное скругление.
- **Крупная шкала отступов**: воздух — часть языка.
- **Микродетали:** буквенные бейджи на вариантах выбора (A/B/C) с выбором с клавиатуры,
  подсказка «Enter ↵», тонкая полоса прогресса, мягкие ease-out переходы.

На плотных экранах — та же гарнитура, шкала, акцент, форма полей и кнопок; меняется только шаг
сетки. Разная плотность, одна система.

### Ширины по назначению поверхности

Не «везде 100vw», а по роли экрана:

| Поверхность | Ширина | Почему |
|---|---|---|
| Шаги опроса | ~600px, по центру | Вопрос во всю ширину монитора не читается |
| Сравнение, расчёт | во всю ширину с полями | Сейчас `max-w-3xl` (768px) и `max-w-5xl` — на мониторе 1440 пустуют две трети |
| Отчёт | остаётся узким | Он печатается на A4 |

### Цена смены палитры

Текущие токены не случайны: бренд-проход дал категориальную палитру графиков, проверенную
валидатором на цветовую слепоту и контраст; тёмная тема выверена на AA на всех страницах;
отчёт печатается светлым при любой теме. **Смена акцента и фона требует повторного прогона
тех же проверок**, а не замены значений. Это работа внутри спеки, а не побочный эффект.

## 3. Данные: таксономия, классы решений, схема

### Проблема, которая ломается на масштабе

`SolutionCategory` привязана к одному типу объекта (`facilityTypeId`; slug уникален внутри
типа — в схеме есть комментарий, почему). При 4 типах это нормально. При 45 категорию «AMR»
пришлось бы завести 45 раз, а каждый класс — продублировать в каждую: 12 классов → ~500 строк,
которые надо держать синхронными.

### Разворот связи

| Сейчас | Становится |
|---|---|
| `SolutionCategory` принадлежит одному `FacilityType` | Категория глобальная: каталог видов решений |
| Решение видно только в своём типе объекта | Join `FacilityTypeCategory`: какие виды применимы к какому объекту |

Рост становится линейным: новый тип объекта — несколько строк связи, а не копия каталога.

**Намеренное следствие:** сегодня AutoStore виден только под одним типом объекта, хотя
шаттловое хранение применимо к нескольким. После разворота вендорское решение видно везде, где
применима его категория. Это меняет то, что видит пользователь, и это улучшение, а не побочный
эффект — но оно должно быть замечено при ревью.

### Классы решений почти не требуют новой схемы

Механика достоверности уже есть: `priceEstimated`, `priceLowUsd`/`priceHighUsd`, `priceBasis`,
`sourceUrl`, `lastVerified`. **Класс — это строка `Solution`** с `priceEstimated = true`,
диапазоном и ссылкой на источник диапазона. Движок принимает её через тот же
`toSolutionCapacity()` — математика не трогается.

Добавляется минимум:

- `isClass Boolean @default(false)` — чтобы интерфейс говорил «класс решений, не конкретная
  модель», и чтобы сравнение могло отделять одно от другого.
- `capacityLow Float?` / `capacityHigh Float?` — диапазон производительности, зеркально
  ценовому, с серединой в существующем `capacityPerUnit`. Та же конвенция, что уже применяется
  к CAPEX «по середине диапазона».
- `Solution.vendor` для класса — не имя вендора, а прочерк; интерфейс не выдаёт класс за
  продукт.

### Достоверность: что можно и чего нельзя

Правило остаётся жёстким и не смягчается ради объёма:

- **Отрасли и типы объектов** — классификатор, у них нет цены. Расширяем свободно.
- **Классы решений** — диапазоны из открытых источников, каждый помечен «оценка», у каждого
  `sourceUrl` и `lastVerified`. Диапазон честнее точки: он и есть признание неопределённости.
- **Конкретные вендорские модели с ценами** — только из проверяемых источников. Массовый
  импорт спек из интернета не делается ни при каких условиях.

`docs/data-provenance.md` расширяется на классы; `npm run check:sources` начинает следить и за
их источниками с тем же порогом 180 дней.

### Типовые параметры уже есть где хранить

Модель `FacilityExample` с `params: Json` существует и не используется в полную силу. Это
готовое место для типовых параметров каждого из ~45 типов объектов — шаг 3 получает
осмысленные значения по умолчанию вместо пустых полей.

### Единицы и базис

У каждого типа объекта должны быть когерентные единицы: решения одного объекта обязаны
говорить на одном языке («заказов/сутки», «паллет/час», «мест хранения»), иначе сравнение
бессмысленно. `capacityBasis` (`PER_HOUR_FLOW` / `PER_DAY_FLOW` / `CONCURRENT_STOCK`) выбирается
осознанно для каждого типа: от него зависит вся математика сортировки. Сорок пять типов — это
сорок пять таких решений, каждое из которых можно принять неправильно; они вычитываются
поштучно, а не генерируются пачкой.

## 4. Тестирование и миграция

### Главный инвариант

**Ни одно выходное число не меняется.** Гейт: 238 существующих тестов остаются зелёными
**без правок**. Если экономический тест приходится подкрутить — значит мы залезли в модель, и
это повод остановиться, а не поправить тест.

### Новый паритет-тест

В репозитории уже есть спека, ловящая расхождение панели расчёта и сохранённого отчёта — она
существует потому, что расхождение однажды дошло до клиентского отчёта (4 425 300 ₽ против
2 267 100 ₽ на экране); поймали его на разборе, до выкатки. Новый поток создаёт такой же риск в другом месте: **шаг 4 показывает срок окупаемости
для каждого решения, шаг 5 — для выбранного, и эти числа обязаны совпадать.** Тест проходит
поток до сравнения, запоминает NPV решения, открывает его расчёт и сверяет.

### Покрытие

- **Слой запросов после разворота категорий** — решение видно во всех типах объектов, к которым
  привязана его категория, и не видно в остальных. Это ядро изменения схемы.
- **Валидация шагов** — мусор в query-строке не роняет страницу и не проникает в расчёт;
  проходит через `withParamDefaults`/`clampAssumption`.
- **Сохранность входов** — сохранённый расчёт открывается по своей ссылке, отчёт по своей.
  Это ограничение, ради которого выбрана route group; тест его и держит.
- **E2E нового потока** — отрасль → объект → параметры → сравнение → расчёт → сохранение,
  включая «Назад» и обновление страницы на середине.
- **Доступность** — шаги проходятся с клавиатуры целиком (буквенные бейджи, Enter); проверки
  контраста на новой палитре в обеих темах.

### Миграция

Разворот категорий двигает существующие строки, а не только меняет столбцы. Прецедент есть:
FK-миграция чистит сирот перед добавлением ограничения и проверялась на базе, эти сироты
содержавшей. Здесь так же — миграция идемпотентна и проверяется **на копии боевой базы**, не
только на пустой. Боевая база уже существует (Neon, подключена к развёрнутому приложению), и в
ней есть посевные данные, на которые ссылок из `SavedAnalysis` пока нет; это не повод считать
миграцию безопасной по умолчанию.
