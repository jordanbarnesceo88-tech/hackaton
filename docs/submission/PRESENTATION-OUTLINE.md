Это исходник презентации для сдачи по ТЗ §8.2.3 (PPTX или PDF). По нему T5.2 собирает `docs/submission/presentation.pptx`: 14 слайдов, формат 16:9, с заметками докладчика. Живой показ идёт по отдельному документу [docs/DEMO-SCRIPT.md](../DEMO-SCRIPT.md).

## Правило чисел (ТЗ §5.6)

Числа на слайдах должны воспроизводиться в сданной сборке, поэтому действуют три правила.

1. **Числа результата расчёта** берутся только из [demo-numbers.md](./demo-numbers.md). Этот файл печатает сборка командой `npx tsx scripts/print-demo-numbers.ts --markdown`. Число копируется из файла, а не набирается заново. В файле разряды разделены неразрывным пробелом, а знак минуса записан дефисом, и копия должна совпадать с файлом побайтно. У каждого числа в этом плане указано, где оно лежит в файле.
2. **Числа требований** — 8 шагов, 10 с, 60 с, 1366×768, горизонт TCO не меньше пяти лет — помечены пунктом ТЗ. Это условия задачи, а не результаты.
3. **Чего нет в demo-numbers.md**, на слайд вписывать нельзя, это можно показать только скриншотом сборки. Сюда относятся:
   - CAPEX и OPEX по статьям;
   - числа в причинах исключения;
   - время расчёта в миллисекундах.

   Время расчёта измеряет финальная проверка T6.1 и записывает в `docs/submission/RELEASE-CHECKLIST.md`. Отсюда же ограничение: номера шагов, таймкоды и номера пунктов ТЗ данными не считаются.

**Если числа изменились**, порядок такой:
1. Перезапустить генерацию в Git Bash, на Linux и macOS — в обычном терминале: `npx tsx scripts/print-demo-numbers.ts --markdown > docs/submission/demo-numbers.md`. Из PowerShell файл не перегенерировать: там `>` перекодирует вывод, меняет кодировку (UTF-8 с BOM или UTF-16, по настройкам) и концы строк на CRLF.
2. Сравнить файл с версией в репозитории: `git diff docs/submission/demo-numbers.md`.
3. Обновить значения в этом плане, в DEMO-SCRIPT.md и в презентации.
4. Записать изменение в CHANGELOG с пометкой «МЕНЯЕТ ЧИСЛА» и значениями «было / стало».

Числа подписаны владельцем 2026-09-25, вариант «А»: новый проект получает сценарии, которые выбрал подбор.

## Слайд 2. Задача, пользователи и путь ТЗ

**Ключевая мысль.** Роботизацию склада часто оценивают по паспортным цифрам производителя, а они верны для идеальных условий. Платформа проходит весь путь ТЗ на данных объекта и показывает, где паспорт расходится с планировкой.

**Визуал.**
- Лента из восьми шагов с подписями, как в навигации сборки: «1 Объект · 2 Параметры · 3 Подбор · 4 Сравнение · 5 Экономика · 6 Сценарии · 7 Имитация · 8 Отчёт». Под каждым шагом одна строка результата из ТЗ §2.2.

  - финансист — CAPEX, OPEX, NPV и TCO;
  - администратор ФЦ БАС — актуальный каталог и нормативы;

## Слайд 3. Архитектура и воспроизводимый запуск

**Ключевая мысль.** Одна команда поднимает базу, запускает миграции с загрузкой данных и стартует приложение. Каждый расчёт помечен версиями модели и данных, поэтому число со слайда воспроизводится в сдаваемой сборке (ТЗ §5.6).

**Визуал.** Схема в четыре слоя:
1. **Браузер.** Рабочая область проекта. Модель и имитация считаются той же функцией, что на сервере.
2. **Next.js 16.** App Router, серверные действия, API v1 с описанием OpenAPI.
3. **Ядро.** `lib/tz` — экономика в рублях с трассировкой формул и подбор. `lib/sim` — детерминированная имитация.
4. **PostgreSQL 16 через Prisma 7.** Каталог с провенансом, параметры и нормативы, проекты и сценарии, журнал корректировок, выпуски данных.

Справа — полоса запуска compose:
- `db` → `migrate` (`prisma migrate deploy` и загрузка данных) → `app`;
- проверка здоровья: `GET /api/health`;
- CI на GitHub: тесты и e2e, затем сборка compose и проверка `/api/health`, `/` и `/demo`.

**Числа на слайде**

| Что | Значение | Где |
|---|---|---|
| Версии в каждом расчёте | модель tz-1.0.0 · имитация sim-1.0.0 | ДЧ·шапка |
| Версия данных расчёта нового проекта | 7be2cba2 | ДЧ·шапка; ДЧ·Ж, абзац под заголовком раздела |
| Выпуск данных организатора в БД | 72eb7f93 | ДЧ·шапка |

Версии Next.js, PostgreSQL и Prisma — это названия технологий, их источник — `package.json` и `docker-compose.yml`.

**Заметки докладчика.** Запуск для жюри — `docker compose up --build`. Поднимаются база, миграции с загрузкой данных организатора и демо-аккаунтов, затем приложение. Проверка здоровья отдаёт версии модели. Ядро расчёта — чистые функции на TypeScript, только рубли и без скрытых коэффициентов. Та же функция работает в браузере, поэтому пересчёт мгновенный и совпадает с сервером бит в бит.

Проект хранит входы и снимки использованных продуктов, нормативов и параметров. Повторное открытие восстанавливает расчёт из снимка. Если данные с тех пор изменились, появляется баннер «Пересчитать на актуальных данных». У расчёта нового проекта версия данных 7be2cba2, у выпуска данных — 72eb7f93. Файл с числами презентации печатает сама сборка одной командой.

## Слайд 5. Подбор с причинами и объяснимый балл

**Ключевая мысль.** Подбор не прячет исключённые решения. У каждого решения есть:
- статус;
- причины с числами объекта и продукта;
- ограничения;
- недостающие данные;
- балл, разложенный по факторам.

**Визуал.** Скриншот шага 3 «Перемещение паллет»:
- верхние строки со статусами «Рекомендуется», «Подходит», «Недостаточно данных» и полосой балла с вкладом факторов;
- раскрытый блок «Исключённые решения»:
  - DMR 600 — грузоподъёмность ниже массы паллеты;
  - Робот-тягач и Робот-штабелёр RoboCV — ширина прохода или разворота больше ширины рабочих проходов объекта;
- открытая форма «Добавить вручную…» с предупреждением и обязательной причиной.

Числа из текстов причин видны на скриншоте. Набирать их на слайде нельзя: в demo-numbers.md их нет, см. правило 3.

**Числа на слайде:** только со скриншота сборки.

**Заметки докладчика.**

Жёсткие правила исключают решение и пишут причину с числами:
- статус НИОКР;
- модель не найдена у производителя;
- грузоподъёмность ниже массы груза;
- проход уже, чем нужно роботу;
- температурный режим;
- решение не предназначено для процесса.

Мягкие правила дают ограничения:
- малый запас грузоподъёмности;
- подъём только по горизонтали;
- пилотный статус;
- спорная цена.

Если нет ни производительности, ни скорости, статус — «Недостаточно данных», а не молчаливый ноль.

Балл складывается из пяти факторов: экономика, полнота и подтверждённость данных, зрелость, запас по грузоподъёмности и проходу, кейсы. Вклад каждого виден на полосе.

Исключённое решение можно добавить вручную, только с причиной. Оно получает значок ⚠ везде — в сравнении, в отчёте и в Excel — и запись в журнале.

Подбор ранжирует продукты. Вывод по сценариям выбирает сценарий по NPV среди жизнеспособных. Поэтому в подборе «Рекомендуется» Ronavi H1500 — он в эксплуатации, а не в пилоте, и данные о нём полнее, — а в выводе — покупка AMR 1500 с явными рисками. Это две разные задачи, и обе объяснены на экране.

## Слайд 6. Формулы ТЗ без скрытых коэффициентов

**Ключевая мысль.** CAPEX, OPEX, годовой эффект, окупаемость, ROI и TCO считаются по зависимостям ТЗ §3.5.2. У каждой статьи есть формула, подстановка чисел и бейдж источника.

**Визуал.**

Слева блок формул, как на странице `/methodology/tz`:
- Парк:
  - Nточн = λпик / (thrэфф × U × A) × (1 + резерв);
  - N = max(1; ⌈Nточн⌉);
  - thrэфф = min(thrнорм; thrцикл).
- CAPEX = оборудование + зарядки + инфраструктура + ПО + интеграция + пусконаладка + обучение + резерв.
- OPEX покупки = сервис + лицензии + электроэнергия + связь + расходные материалы + ремонт + замена АКБ + персонал эксплуатации + оставшийся ФОТ.
- OPEX услуги = подписка + электроэнергия + связь + персонал эксплуатации + оставшийся ФОТ.
- Эффект и окупаемость:
  - E = OPEXкак есть − OPEXсценария;
  - PB = CAPEX / E при E > 0;
  - ROI = Σ CFt (t = 1…H) / CAPEX × 100 %.
- TCO = CAPEX + Σ (OPEXt + докупкаt), горизонт не меньше пяти лет. Дополнительно считаются NPV и дисконтированная окупаемость.

Справа скриншот шага 5 для «Покупка — Ronavi H1500»: «CAPEX по статьям» с бейджами источников и раскрытое «Как посчитано».

**Числа на слайде:** пример «Покупка — Ronavi H1500».

PDF получается печатью браузера. В Excel формулы живые, поэтому финансист может проверить NPV сам. CSV — с BOM и разделителем «;», поэтому открывается в русском Excel без настройки. PNG имитации хранит сцену, KPI, сценарий, seed, дату и оговорку.

API v1:
- чтение каталога, нормативов и параметров объекта;
- расчёт тем же движком: `POST /api/v1/calculate` с телом `{"facility":"warehouse"}` возвращает те же сценарии и числа, что новый проект (ДЧ·Ж); API отдаёт суммы без округления, поэтому сравнивать нужно после округления до рубля;
- импорт объекта в проект;
- для администратора — импорт каталога и правка нормативов.

Описание — `/api/v1/openapi.json`, документация — `/api-docs`. Подключение WMS, ERP, 1С и мониторинга описано в `docs/INTEGRATIONS.md`.

## Слайд 14. План развития

**Ключевая мысль.** Следующий шаг — не новые экраны, а проверка двух самых чувствительных допущений на реальном объекте вместе с ФЦ БАС.

**Визуал.** Три колонки «Ближайший шаг / Затем / Дальше» и внизу строка просьбы.

- **Ближайший шаг.** Пилотное обследование склада.
  - Замерить долю автоматизируемого труда. Это сильнейший рычаг рекомендуемой покупки AMR 1500: NPV от -28,1 млн ₽ до 36,1 млн ₽ (ДЧ·Ж-вывод).
  - Подтвердить цену AMR 1500 — 2 200 000 ₽ — и его производительность по коммерческому предложению (ДЧ·Ж-вывод).
- **Затем.**
  - Остаточная стоимость в TCO. Сейчас докупка оборудования в конце срока службы входит в расчёт без учёта остаточной стоимости. Пример — покупка H1500 из дополнительного примера (ДЧ·В): с горизонта 8 лет в расчёт входит докупка на 29,7 млн ₽ в год 7, и при горизонте 8–10 лет вывод там снова меняется.
  - Экономика и имитация аэропорта, медучреждения и других процессов склада.
  - Модель заторов в проходах.
- **Дальше.**
  - Плановое автообновление каталога.
  - Роль поставщика.
  - Лизинг.
  - Серверный PDF.
  - Живые интеграции с WMS, ERP, 1С и мониторингом через готовый API.

**Числа на слайде**

**Заметки докладчика.** Модель уже говорит, что проверять в первую очередь. Во-первых, долю труда, которую реально снимают роботы: от неё NPV покупки AMR 1500 гуляет от -28,1 до 36,1 млн ₽. Во-вторых, цену и производительность AMR 1500 по коммерческому предложению.

## Сверка чисел перед сдачей

1. Сгенерировать файл заново и сравнить с файлом в репозитории. Выполнять в Git Bash, на Linux и macOS — в обычном терминале:

   ```bash
   npx tsx scripts/print-demo-numbers.ts --markdown > /tmp/dn.md
   git diff --no-index --ignore-cr-at-eol --exit-code docs/submission/demo-numbers.md /tmp/dn.md
   ```

   Пустой вывод и код выхода 0 значат, что числа совпадают. Концы строк не сравниваются намеренно: Git для Windows с `core.autocrlf=true` выписывает файл с CRLF, и побайтное сравнение дало бы ложное расхождение. Из PowerShell не запускать: `>` там перекодирует вывод, и сверка покажет расхождение, которого нет.

3. В заметках докладчика в презентации те же числа записываются так же, как в файле. Округлять их можно только голосом.
