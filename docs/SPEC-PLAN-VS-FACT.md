## 1. Суть задачи

Паспортная производительность роботов систематически завышена относительно фактической. Платформа должна считать **два сценария параллельно**, показывать их рядом и объяснять, из чего складывается разница.

| Сценарий | Источник чисел | Назначение |
|---|---|---|
| **План** | паспорт вендора | показать, что обещано; база для сравнения |
| **Факт** | замеры или коэффициент класса | **подбор парка и вся экономика считаются только по нему** |

Паспортные значения в подборе парка **не участвуют** — только в колонке «план» и в разложении причин. Платформа не обещает больше, чем подтверждено.

Задача не привязана к конкретным моделям: работает для любого решения каталога через справочник классов и импорт замеров.

## 3. Блокер схемы — решить первым

У `ProductCharacteristic` в `prisma/schema.prisma` стоит:

```prisma
@@unique([productId, key])
```

Это **не даёт хранить паспортное и замерное значение под одним ключом** — вторая вставка падает на индексе.

- **Вариант A (предпочтительный):** расширить до `@@unique([productId, key, origin])`, где `origin` различает `passport` / `measured`. Значение «в расчёт» не хранить, вычислять на чтении — иначе появится третья копия, которая рассинхронизируется.
- **Вариант B:** разнести по ключам (`productivity`, `productivity_measured`). Проще в миграции, но плодит ключи и ломает выборки по `key`.

Перед миграцией проверь upsert-ы в `scripts/seed.ts`, `scripts/gen-organizer-seed.ts`, `lib/catalog/`. Прогони `npm run test:db`.

## 4. Модель данных

### 4.1. Паспорт хранится интервалом

Вендоры публикуют производительность вилкой. Пример с карточки официального дистрибьютора:

```
Производительность 700-1000 м²/час
Рекомендуемая площадь уборки 2 000 м²
Функционал: влажная уборка, сухое подметание, пылесос
```

```
passport_min = 700
passport_max = 1000
range_width  = (passport_max − passport_min) / passport_max = 0,30
```

**Запрещено** схлопывать интервал в среднее при импорте. Среднее вычисляется на лету, хранится интервал. Если в существующих данных интервалы уже схлопнуты — завести отдельной задачей на исправление импорта.

При `range_width > 0,20` уровень доверия к паспорту понижается на ступень, в интерфейсе: «паспорт дан широким интервалом, вероятна зависимость от режима».

Поля решения:

```
passport_min          Float?
passport_max          Float?
passport_point        Float?     // только если вендор даёт одно число
range_width           Float?     // вычисляемое
anchor_rule           String     // max | min | mid | mode_matched | mode_heuristic | single
recommended_area_m2   Float?     // собственная дератировка вендора, см. §6
functions             String[]   // режимы решения
```

Характеристики, участвующие в расчёте: `productivity` (единица по классу), `cycle_work_hours` (часов работы в одном подходе), `charge_hours`, `cycles_per_day`. У паспорта вместо `cycle_work_hours` допускается `autonomy_hours`.

### 4.2. Таблица замеров


`measurement_basis` и `measured_mode` — см. §5.2 и §5.3, оба обязательны при импорте.

Поля: `robot_class`, `factor` (`prod` / `cycle` / `cycles`), `cause_text`, `trigger`.

`trigger` хранить **машиночитаемо (JSON-условие)**, не свободным текстом — иначе его нельзя вычислить и подстановка причин превращается в ручной выбор.

| Класс | factor | cause_text | trigger |
|---|---|---|---|
| Робот-уборщик | prod | Паспорт измерен на прямой без препятствий; на объекте — обход людей и предметов, повороты, узкие места, разгон и торможение, повторные проходы | всегда |
| Робот-уборщик | prod | Узкие проходы снижают скорость и заставляют делать повторные заходы | ширина прохода < ширина робота + 0,5 м |

| AMR / FMR / тягач | cycle | Опережающая (opportunity) зарядка, деградация АКБ, плановое ТО | всегда |

## 5. Методика коэффициента отклонения

### 5.1. Коэффициент — интервал, а не точка

```
k_vs_max = measured / passport_max
k_vs_min = measured / passport_min
```

Для замера 600 м²/ч при паспорте 700–1000:

```
k_vs_max = 600 / 1000 = 0,600     →  −40,0%
k_vs_min = 600 /  700 = 0,857     →  −14,3%
```

**Оба значения хранятся и показываются.** Одно число скрывает суть: это одна реальность, отсчитанная от разных обещаний.

**Точечная оценка для подбора парка — `k_vs_max`, по умолчанию.** Обоснование печатается в отчёте: это число вендор ставит в коммерческое предложение, и именно его процитирует заказчик. Администратор меняет якорь без релиза; применённый якорь записывается рядом с коэффициентом.

### 5.2. Базис замера — обязателен

| `measurement_basis` | Что измерено | Что уже внутри числа |
|---|---|---|
| `productive_hour` | час чистой работы, щётка опущена / робот выполняет операцию | ничего лишнего |
| `shift_hour` | выработка за час смены: переезды, заправка, слив, ожидание, зарядка | потери на цикл и простои **уже включены** |

Итоговая выработка раскладывается как `k_prod × k_cycle × k_cycles`, и множители обязаны быть независимыми. Если замер в базисе `shift_hour`, потери уже сидят в `k_prod`, и умножение на `k_cycle` вычитает их **второй раз** — коэффициент занижается вдвое, а результат выглядит правдоподобно и на глаз не ловится.

**Требования:**
- импорт без `measurement_basis` отклоняется с внятной ошибкой;
- при `shift_hour` движок **принудительно** ставит `k_cycle = 1` и `k_cycles = 1` и печатает в разложении: «замер сделан за час смены, потери на цикл уже учтены в производительности»;
- тест падает, если при `shift_hour` в произведение попал `k_cycle ≠ 1`.

### 5.3. Сопоставление режимов

Если у решения несколько функций, замер обязан указывать режим (`measured_mode`). Список допустимых значений берётся из `functions` решения, не зашивается в код.

1. Паспорт даёт производительность по режимам → сравнивать с цифрой того же режима, `anchor_rule = mode_matched`.
2. Паспорт даёт общий интервал, режим замера известен → эвристика: **влажная уборка соотносится с нижней границей, сухое подметание — с верхней**. Помечать `anchor_rule = mode_heuristic`, `confidence` не выше `medium`. Это допущение, не факт.
3. Режим неизвестен → считать по `k_vs_max`, `confidence = low`, пояснение «режим замера неизвестен».

Замер влажной уборки, делённый на паспортную цифру сухого подметания, даёт заниженный коэффициент: робот не хуже заявленного, просто сравнили мойку с подметанием.

### 5.4. Агрегация по классу

```
k_class = median(k_1 … k_n)
k_min   = min(k_1 … k_n)
k_max   = max(k_1 … k_n)
k_conservative = k_min
```

**Медиана, а не среднее** — выборки малы (3–10 замеров), один аномальный замер уводит подбор парка.

`k_conservative` — нижняя граница фактически наблюдённого, не экспертная подстановка.

**Валидация в сидере:** `k_conservative ∈ [k_min, k_max]` того же измерения. Падать с ошибкой, если нет. Эта проверка ловит подстановку суточного коэффициента в часовое поле.

Часовые и суточные коэффициенты хранятся **раздельно** и не взаимозаменяемы: суточный ниже часового, потому что вбирает заправку, зарядку и окно работы.

### 5.5. Уровень доверия

| `confidence` | Условие |
|---|---|
| `high` | есть замеры самого решения, `n ≥ 3` |
| `medium` | замеров решения нет, есть замеры класса на этом типе объекта, `n ≥ 3` |
| `low` | `n < 3`, либо перенос с другого типа объекта, либо экспертное допущение |

`n` хранится вместе с коэффициентом и показывается. «0,70» при `n = 1` и при `n = 12` — разные по смыслу числа.

### 5.6. Классы без замеров

Пока замеров нет: `source_kind = expert` или `analogy`, `analogy_from` = класс-донор, `confidence = low`, в интерфейсе «замеров по классу нет, коэффициент перенесён с <класс>». При появлении трёх замеров пересчитывается автоматически, флаг снимается — **без правки кода**.

## 6. Проверка по рекомендуемой площади

`recommended_area_m2` — собственная дератировка вендора. Он одновременно заявляет 700–1000 м²/ч и рекомендует зону 2 000 м²:

```
implied_hours_max  = 2000 / 1000 = 2,0 ч
implied_hours_min  = 2000 /  700 = 2,9 ч
implied_hours_fact = 2000 /  600 = 3,3 ч
```

Вендор сам закладывает 2–3 часа чистой уборки в сутки, а не 5 часов паспортной автономности.

**Обязательная проверка модели:**

```
если perDay_model > recommended_area × 1,5 → предупреждение
```

Текст: «расчётная суточная выработка превышает рекомендованную вендором зону обслуживания в N раз — проверьте окно работы и число подходов».

Ловит завышение парка до попадания в экономику. Если `recommended_area_m2` не опубликована — проверка пропускается, в отчёт: «независимая проверка недоступна, вендор не публикует рекомендуемую зону».

## 7. Два сценария расчёта

**План (по паспорту):**
```
perDay_plan = productivity_passport × autonomy_passport × floor(window / (autonomy_passport + charge_passport))
N_plan      = Σ_этажей ⌈need_floor / perDay_plan⌉
```

**Факт:**
```
perDay_fact = productivity_used × cycle_work_used × cycles_used
N_fact      = Σ_этажей ⌈need_floor / (perDay_fact × max_load)⌉
```

CAPEX, OPEX, эффект, окупаемость, ROI, TCO считаются для обоих `N` **по единой модели** — меняются только количество роботов и выработка. Расчётный модуль не форкать.

Объекты с этажами: робот считается поэтажно (сам этаж не сменит), минимум 1 на этаж с площадью > 0. Без этажей — по зонам.

---

## 8. Правило выбора значения «в расчёт»

1. Есть замер этого решения → `measured × safety` (`safety = 0,9`), `confidence = high`.
2. Иначе есть замеры класса на этом типе объекта → `passport_anchor × k_class × safety`, `confidence = medium`.
3. Иначе → `passport_anchor × k_conservative`, `confidence = low`.

Ручное переопределение разрешено, пишется в `ChangeLog` (кто, когда, старое, новое) — ТЗ §3.5.4.

---

## 9. Консервативный режим (по умолчанию)

1. Коэффициент класса — нижняя граница `k_conservative`, не среднее.
2. Замер × 0,9 — запас на новый объект, сезон, износ щёток и АКБ.
3. Парк на загрузку не выше 85% (`max_load = 0,85`) — резерв на простои, ТО, инциденты.
4. Округление вверх, минимум 1 робот на этаж.
5. В экономике каждое допущение с консервативной стороны: ЗИП с первого года в CAPEX, внеплановые выезды инженера заложены, замена АКБ в TCO, интернет и электроэнергия сверх аренды.
6. Паспортные значения в подборе не участвуют.

Переключатель «Консервативный (по умолчанию) / Ожидаемый (без запасов)». В отчёте печатается режим и все применённые запасы.

## 10. Почему факт отличается — разложение на причины

Это ядро ценности продукта: платформа не просто даёт меньшее число, она объясняет, из чего оно сложилось.

```
perDay   = производительность × часов в подходе × подходов в сутки
k_prod   = productivity_used / productivity_passport_anchor
k_cycle  = cycle_work_used   / autonomy_passport
k_cycles = cycles_used       / cycles_passport
k_total  = k_prod × k_cycle × k_cycles        // тождественно perDay_fact / perDay_plan
```

Время зарядки показывается информационно и **в произведение не входит** — учтено через число подходов. Юнит-тест обязан проверять, что `k_total` сходится с отношением выработок.

**Карточка «Паспорт vs факт — из-за чего разница»:**

- три KPI: по паспорту, по факту, главная причина (множитель с наименьшим значением < 1);
- таблица множителей с подсветкой главного и текстом причины из `deviation_causes` — подставляются причины, чей `trigger` сработал по параметрам робота и объекта;
- строка «Роботов по паспорту → по факту»;
- при `measurement_basis = shift_hour` — пояснение, что цикловые множители равны 1 намеренно.

Пользователь может дополнить причину вручную, правка журналируется.

## 11. Интерфейс

**Карточка решения, блок производительности:**

```
Паспорт:      700–1000 м²/ч        источник: сайт дистрибьютора, дата
Замер:        600 м²/ч             влажная уборка, час чистой работы, n=3
Отклонение:   −40% от максимума
              −14% от минимума
Якорь:        максимум (по умолчанию)
Проверка:     вендор рекомендует 2 000 м² — это 2,0–2,9 ч при паспортной
              производительности и 3,3 ч при замеренной
```

**Сравнение решений:** колонки «Паспорт», «Факт», «Отклонение %», «Источник факта», бейдж confidence.

**Расчёт экономики:** режим «План / Факт / Оба рядом» — количество роботов, CAPEX, OPEX, эффект, окупаемость, ROI, TCO в две колонки плюс строка «Разница».

**Дашборд:** «Индекс доверия расчёта» = доля ключевых входов с confidence high или medium; список допущений с влиянием на окупаемость (пересчёт при `k_min` и `k_max` через `lib/economics/sensitivity.ts`).

**Отчёт (PDF / Excel):** таблица «паспорт vs факт», разложение причин, справочник коэффициентов с источниками, режим расчёта и применённые запасы — ТЗ §3.5.8, §3.7.2. Excel через подключённый `exceljs`.

## 12. Импорт замеров

Форма и CSV. После импорта:

1. пересчитать `k_class`, `k_min`, `k_max` по всем замерам класса на этом типе объекта;
2. обновить значения «в расчёт» у решений без собственных замеров;
3. пересчитать `confidence` и `n`;
4. записать `updated_at`.

Замеры хранятся с источником и датой — ТЗ §3.3.4.

## 13. Контрольные примеры для тестов

Тесты рядом с кодом, `*.test.ts`. Запуск: `npm run test:unit`, для БД `npm run test:db`.

### Пример 1. Робот-уборщик, паспорт интервалом

Паспорт 700–1000 м²/ч, рекомендуемая площадь 2 000 м², функции `[wet, dry_sweep, vacuum]`, автономность 5 ч, зарядка 3 ч. Замеры `productive_hour`, режим `wet`: 600, 640, 520 м²/ч. Объект 3 этажа × 4 000 м².

```
range_width = 0,30                          → флаг «широкий интервал»
k_vs_max: 0,600 / 0,640 / 0,520 → медиана 0,600    −40,0%
k_vs_min: 0,857 / 0,914 / 0,743 → медиана 0,857    −14,3%
k_min = 0,520   k_max = 0,640   k_conservative = 0,520
confidence = medium
implied_hours = 2,0 (max) / 2,9 (min) / 3,3 (замер)
```

### Пример 2. Робот-уборщик, паспорт точкой (регрессия старого кейса)

Паспорт 1 000 м²/ч, автономность 5 ч, зарядка 3 ч. Замер: 500 м²/ч, подход 2 ч, зарядка 2 ч, 6 подходов. Объект 3 этажа × 4 000 м².

```
план  = 15 000 м²/сут, 1 робот на этаж
факт  =  6 000 м²/сут по замеру, 5 400 в расчёт с запасом 0,9
        1 робот на этаж при загрузке 74% ≤ 85%
отклонение −60%
разложение 0,50 × 0,40 × 2,0 = 0,40
главная причина — часов работы в подходе (×0,40)
```

### Пример 3. AMR без замеров

Паспорт 80 паллет/ч → в расчёт `80 × 0,65 = 52` паллет/ч, `confidence = low`. После импорта трёх замеров класса коэффициент пересчитывается **без правки кода** — тест падает, если значение зашито в константу.

### Обязательные проверки

1. интервал не схлопнут: `passport_min` и `passport_max` доступны после импорта;
2. оба коэффициента (`vs_max`, `vs_min`) считаются и хранятся;
3. смена `anchor_rule` меняет точечную оценку и записывается в выдачу;
4. `k_conservative ∈ [k_min, k_max]`;
5. `range_width > 0,20` поднимает флаг и понижает confidence;
6. импорт без `measurement_basis` отклоняется;
7. при `shift_hour` принудительно `k_cycle = k_cycles = 1`;
8. `perDay > recommended_area × 1,5` выдаёт предупреждение;
9. при `n = 1`: `confidence = low`, `k_min = k_max = k_class`;
10. добавление замера пересчитывает медиану без правки кода;
11. `k_total` равен `perDay_fact / perDay_plan`; `charge_hours` на произведение не влияет;
12. у каждого числа в обоих сценариях есть источник, дата и confidence;
13. ручное изменение коэффициента попадает в `ChangeLog` и в отчёт;
14. переключение «Консервативный / Ожидаемый» меняет `N` и экономику и печатается в отчёте.
