# Фоновые расчёты и worker

## Область действия

Фоновый контур обслуживает авторизованные операции CREATE, SAVE, RECALCULATE и CALCULATE. Принятый вход и справочники сохраняются до начала вычислений. После ответа 202 операция не зависит от HTTP-запроса и открытой вкладки. Результат доступен владельцу в `/calculation-jobs`.

Авторизованные расчёты проектов и их имитацию выполняет отдельный worker. Интерфейс и API передают задания в очередь; `POST /api/v1/projects` принимает создание проекта с ответом `202` и адресом операции.

Гостевая рабочая область использует `POST /api/v1/demo-calculation` и получает новый серверный результат по актуальному публичному каталогу и нормативам. Три учебных примера задают входы для этого расчёта; предварительная оценка до его завершения не считается готовым результатом. Пользовательский гостевой ввод в засеянные проекты не записывается.

## Гостевой расчёт

`POST /api/v1/demo-calculation` принимает только `{ facility, params?, scenarios? }` и возвращает `{ results, ms }`. `results` имеет ту же структуру полного результата, что и авторизованный расчёт; `ms` — серверное время, включая загрузку справочников. Проверки параметров и сценариев общие с проектами. Для поддомкрачивающих роботов `closed-pod-1` сервер связывает экономику полного цикла мобильного стеллажа с одной фактической пространственной сводкой; отдельный 2D-прогон не подменяет и не дублирует это подтверждение. Для вилочных роботов и тягачей `single-leg-pallet-1` действует аналитика одиночной перевозки без 3D-подтверждения подхвата стеллажа. Полученные PARTIAL, FAIL и NOT_EVALUATED не заменяются на OK.

Гостевой расчёт выполняется внутри HTTP-запроса без долговременной очереди. Проект, архив, CalculationJob и CalculationRun не создаются; введённые данные и результат не сохраняются. Служебный счётчик частоты обновляется в БД. Отмена запроса передаётся движку, поэтому закрытие вкладки не имеет гарантий продолжения, предусмотренных для принятого фонового задания.

Тело JSON ограничено 4 МиБ. Посторонний Origin и неизвестные поля, включая идентификаторы проектов и владельцев, отклоняются. Лимит — 30 попыток за 5 минут на IP; точность определения IP зависит от настройки доверенного прокси. Web-процесс допускает не более двух одновременных расчётов. Общий дедлайн расчётного контура — 60 секунд, общий бюджет пространственных проверок — до 45 секунд внутри оставшегося времени. Конфигурация обработчика допускает до 75 секунд; это не гарантия общего сетевого времени ответа.

Все ответы имеют `Cache-Control: no-store`. Ошибки входа возвращают 400/413/415/422, чужой Origin — 403, частота запросов — 429 с `Retry-After`. Занятый расчётный допуск или исчерпанный дедлайн возвращают 503 с `Retry-After: 2`; отмена — 499. Другие временные ошибки возвращают 503 без внутренних диагностических данных. Контракт доступен в `/api-docs` и `/api/v1/openapi.json`.

## Запуск

Docker Compose запускает сервис `worker` вместе с `app`, после успешных миграций и сева. Без Compose:

```bash
npm ci
npx prisma migrate deploy
npm run db:seed
npm run build
```

Запустите `npm start` и отдельно `npm run worker`, с одинаковыми DATABASE_URL и переменными выпуска. Для разработки — `npm run dev` и `npm run worker:dev`. Production worker — отдельный CJS bundle `dist-worker/calculation-worker.cjs`, а не фоновый callback Next.js.

Логи `calculation_worker_started` подтверждают старт процесса и доступность таблиц очереди в этот момент. Отдельного регистра живых idle-worker и readiness endpoint worker пока нет. `GET /api/health` подтверждает доступность web и БД, но не наличие исполнителя. Состояние QUEUED означает ожидание; при остановленном worker задания остаются в очереди. Проверяйте состояние процесса и `docker compose logs worker`.

## Контракты

| Endpoint | Назначение |
|---|---|
| POST `/api/v1/calculation-jobs` | Принять операцию, вернуть 202 и job receipt; обязателен Idempotency-Key |
| GET `/api/v1/calculation-jobs` | Операции текущего пользователя; опциональный projectId |
| GET `/api/v1/calculation-jobs/:id` | Компактное состояние и этап |
| GET `/api/v1/calculation-jobs/:id/result` | Завершённый результат и разрешённые поля отправленной формы; pending возвращает 202 |
| POST `/api/v1/calculation-jobs/:id/cancel` | Запросить отмену |
| DELETE `/api/v1/calculation-jobs/:id` | Явно удалить технический результат завершённого запуска |

Cookie-авторизация обязательна; чтение, отмена и удаление проверяют владельца. При cookie POST/DELETE чужой Origin запрещён. Идентификатор задания сам по себе не предоставляет доступа.

Обратный прокси должен сохранять исходный `Host` и передавать доверенный протокол запроса. Проверка использует адрес назначения браузера, а не внутренний адрес привязки Next.js; произвольный `X-Forwarded-Host` не считается источником доверия.

Пример тела SAVE:

```json
{
  "operation": "SAVE",
  "projectId": "project-id",
  "expectedRevision": 4,
  "params": {},
  "scenarios": [],
  "changes": []
}
```

Пустые параметры/сценарии в примере обозначают места для фактического проверяемого ввода, а не готовый валидный расчёт. CREATE принимает name, facility, params, scenarios и optional objectName/paramsSource. RECALCULATE — projectId и expectedRevision; использует актуальные на момент подготовки согласованного снимка справочники. CALCULATE — facility, params, scenarios без публикации в проект.

## Снимки и идемпотентность

Приём состоит из двух этапов. Read-only транзакция Repeatable Read формирует согласованный снимок проекта и справочников, проверяет ввод и ограничение размера. Глобальная блокировка допуска в это время не удерживается. Короткая транзакция Read Committed затем получает общий admission lock и заново проверяет идемпотентность, квоты, существование владельца, принадлежность/режим demo и редакцию проекта перед записью run/job. Ожидающий запрос не переносит старый MVCC-снимок в проверку квот.

Тяжёлая имитация не выполняется внутри этих транзакций. Для SAVE сохраняются соответствующие продукты и нормативы прежнего снимка; RECALCULATE явно берёт актуальные данные. Изменение каталога после подготовки не меняет принятый расчёт. Изменение или удаление проекта до admission отклоняется повторной проверкой; конфликт при более поздней публикации обрабатывает CAS. Повтор короткого допуска не пересобирает уже принятый снимок по изменившемуся каталогу.

Идемпотентность ограничена владельцем и ключом отправки. Одинаковый ключ и поданное тело возвращают прежнюю операцию; другой ввод с тем же ключом — 409. Хэш поданного тела отделён от хэша разрешённого сервером снимка, поэтому сетевой повтор не меняется вслед за каталогом. Клиент сохраняет ключ до отправки и повторяет его после потери подтверждения.

CREATE резервирует ID проекта при принятии, но не создаёт пустой проект. Проект появляется вместе с завершённым результатом в финальной транзакции. Маленькая запись CalculationSubmission сохраняет ключ и хэш независимо от последующего удаления проекта/run/job. После удаления исходной операции прежний ключ возвращает 410, а не создаёт проект заново.

## Исполнение и восстановление

Состояния: QUEUED → RUNNING → SUCCEEDED / FAILED / CANCELLED. Восстановление потерянного worker переводит RUNNING обратно в QUEUED, пока не исчерпан лимит попыток. Попытки всегда используют тот же сохранённый вход.

- Один worker-процесс исполняет одно CPU-задание одновременно.
- Claim через PostgreSQL row lock и SKIP LOCKED; действующих lease допускается не более двух на БД под transaction-level advisory lock.
- Lease — 20 секунд, heartbeat — каждые 5 секунд. Часы истечения берутся из PostgreSQL.
- Бюджет исполнения — до 60 секунд на попытку; ожидание в очереди в этот бюджет не входит. Общий бюджет всех 3D-перепроверок — до 45 секунд внутри этих 60 секунд, с отсечением по оставшемуся общему времени. Это часть единого бюджета, а не дополнительные 45 секунд после остальных расчётов.
- Потерянный worker восстанавливается максимум до трёх попыток; между повторными claim предусмотрена задержка. Ошибка валидации/движка или исчерпание расчётного бюджета не порождает бесконечные CPU-повторы.
- Этапы отражают реальный код: preparing, spatial-check, simulation, fleet-search, finalizing, publishing. Процент может отсутствовать, когда объём оставшейся работы заранее неизвестен.

Лимит действующих lease — логический предел полномочий и новых claim, **не жёсткая гарантия физического количества потребляющих CPU процессов**. Зависший или приостановленный старый процесс может некоторое время продолжать работу после истечения lease. Кооперативная отмена останавливает его после обнаружения потери полномочий, а fencing запрещает публикацию.

Graceful stop прекращает наблюдение и исполнение; незавершённая lease истекает и восстанавливается новым worker. При недоступности БД worker не может продлить полномочия и не публикует результат. После восстановления БД повторный claim выполняется на прежнем снимке.

## Публикация и отмена

Проект остаётся неизменным, пока считается submitted-версия. Финальная короткая транзакция проверяет актуальный token, неистёкшую lease и отсутствие отмены, затем CAS по revision проекта. После SQL-публикации lease проверяется ещё раз; её истечение откатывает всю транзакцию.

Если revision совпала, проект, сценарии, журнал, завершённый run и статус job сохраняются атомарно: publicationState=PUBLISHED. Если проект успели изменить, результат сохраняется отдельно: SUCCEEDED + STALE. Такой статус не означает сохранение поверх новой редакции. Владелец может посмотреть и выгрузить отдельный результат; автоматической принудительной перезаписи нет.

При одновременной отмене и финализации побеждает операция, первой получившая соответствующие row locks. Принятая отмена запрещает дальнейшую публикацию; уже committed результат отмена задним числом не удаляет. Удаление проекта/пользователя не позволяет позднему worker воскресить данные. Порядок блокировок финализации и очистки учитывает каскады БД: владелец → проект → run → job.

## Выпуски движка

`npm run build:worker` выпускает bundle и `dist-worker/engine-release.json` с SHA-256 fingerprint исходников. Production Next и worker встраивают один fingerprint при сборке; произвольная строка CALCULATION_ENGINE_RELEASE добавляется только как метка и не заменяет идентичность кода. В production отсутствие встроенного fingerprint считается ошибкой конфигурации.

Fingerprint учитывает точные байты исходного графа. Его пути закреплены в
`.gitattributes` с `-text`, чтобы Git не менял CRLF/LF при checkout на другой ОС.
При добавлении зависимости движка обновите этот список по `sources` из
`engine-release.json`. Приёмка выпуска сверяет рабочие файлы, Git-индекс и чистый
checkout; одинаковая логика с другими байтами не выдаётся за прежний fingerprint.

Собирайте web и worker из одной рабочей копии и устанавливайте их одним выпуском. При несовпадении engineRelease сохранённая задача получает ENGINE_VERSION_UNAVAILABLE, без публикации чужим движком. Строка версии в JSON не является способом выполнить старый код. Перед обновлением остановите приём новых задач/дождитесь завершения очереди либо сохраняйте реально исполнимый старый worker до завершения совместимых заданий. Текущий механизм не выбирает автоматически разные версии движка для одной очереди.

Хэш входа нужен для целостности и идентичности; это не цифровая подпись результата и не доказательство корректности физической модели. Завершённые результаты хранятся, а не пересчитываются при чтении. Ограниченный последовательный перебор минимального парка в аналитике `single-leg-pallet-1` зависит от wall-clock бюджета; отсутствие ответа в бюджете не означает доказанную невыполнимость. Он не выдаёт минимум или вторую сводку для `closed-pod-1`.

## Хранение и явное удаление

Лимиты: до двух активных операций на владельца, до 100 активных в общей очереди; до 200 сохранённых технических запусков на владельца и 2000 в общей истории. Admission атомарен. Повтор ранее принятого ключа проверяется до квот и не расходует новую запись. Переполнение истории возвращает 429/HISTORY_FULL.

Входной HTTP JSON ограничен 4 MiB, серверный развёрнутый снимок — 16 MiB. Ограничение количества запусков не является точной квотой дисковых байтов; объём JSONB, резервных копий и свободное место надо контролировать отдельно.

Автоматического удаления истории по возрасту нет. Владелец явно удаляет технический результат завершённой операции: очищаются сохранённый input/result, а проект и его архивный отчёт остаются. Pending-операцию сначала нужно отменить. Маленькие tombstones ключей сохраняются до удаления аккаунта, чтобы поздний сетевой повтор не создавал новую операцию. Список и endpoints результатов удалённые технические данные не возвращают. Срок хранения ключей и автоматическая ретенция — отдельная политика, сейчас не применяются молча.

Резервировать нужно всю БД согласованно: Project, CalculationRun, CalculationJob и CalculationSubmission. Восстановление только Project не восстанавливает очередь и защиту повторной отправки. После restore остановите прежние worker, проверьте engine fingerprint и истёкшие lease, затем запускайте совместимый worker. Проверяйте restore на отдельной БД; не проверяйте тесты или принудительное истечение lease на пользовательской базе.

## Проверка перед эксплуатацией

Проверяйте конкурентный claim, потерю ответа enqueue, отмену, истёкшую и повторно захваченную lease, поздний zombie-result, CAS-конфликт, удаление проекта и историю ключей. Отдельно остановите настоящий production worker после claim и убедитесь, что новый процесс завершает тот же job без частичной записи. Проверяйте запуск собранного bundle и Compose-контура, а не только tsx.

Этот контур не добавляет автоматически отдельную очередь экспортов, staging/publish каталога, единую трассу 2D/3D, аппаратную изоляцию каждого задания или промышленный мониторинг. Они требуют самостоятельных требований и проверки.

## Нагрузочная проверка: методика и область

Нагрузка HTTP-очереди проверяется отдельно от скорости имитации и отрисовки в браузере.
Начальный burst — 50 разных заранее авторизованных пользователей, по одному настоящему
полнооконному `CALCULATE` на каждого. Первичная отправка не повторяется автоматически.
После допуска измеряются чтение статуса, получение и сверка результата. Исторические
серии также включали отдельные идемпотентные повторы и отрицательные проверки доступа;
в текущем burst первоначальные POST не повторялись. Подготовка пользователей и сессий исключена
из времени burst. Один worker выполняет одно задание; при трёх процессах глобальный
лимит остаётся равным двум действующим lease.

Первый прогон на fingerprint e937 выявил реальный дефект приёма: из 50 первых запросов
21 вернул `202`, 29 — `503`; серверные логи связали ошибки с исчерпанием повторов
Serializable-конфликта `P2034`. Все 21 принятых задания завершились и были сверены;
это не делает сам burst успешным. Исходный неуспешный отчёт сохраняется отдельно и
не заменяется результатами исправленного выпуска. Изменение RR/RC выше исправляет
механизм допуска; успешность повторной нагрузки подтверждается только завершёнными
отчётами текущего fingerprint в [сдаточном комплекте](./submission/current/README.md).

### Разделение времени

| Метрика | Измерение | Что исключает |
|---|---|---|
| Подтверждение HTTP | От первого POST клиента до ответа с receipt | Выполнение задания после `202` |
| Ожидание очереди | `startedAt − createdAt` для одной попытки | Подготовку до сохранения и собственно вычисление |
| Вычисление и запись | `finishedAt − startedAt` для одной попытки | Ожидание до claim; это не таймер одной формулы |
| Полный серверный путь | `finishedAt − createdAt` | Время до создания задания и сетевое получение результата |
| Ожидание клиента в историческом runner | От начала POST до обнаружения terminal-статуса polling | Не включает последующее получение полного результата |
| Получение результата клиентом в текущем a944 | От начала POST до получения и разбора result JSON | Не включает последующую независимую проверку сохранённого JSON в БД |
| Опрос / health | Отдельные HTTP-задержки и ошибки во время burst | Отрисовку и работу 50 вкладок браузера |

Время в очереди не входит в бюджет 60 секунд на попытку вычисления. Оно входит в
ожидание пользователя. Поэтому короткое service-время не доказывает, что все 50 клиентов
получили итог за 10/60 секунд. Целевые задержки конкретного runner задаются до повторного
прогона и не объявляются универсальным SLA или полным подтверждением §4.3 ТЗ.

### Текущий прогон a944: 19.10.2026

На engine `alfa-robot/sha256:a944224406e9bd5e40de9bffeccc8da0f55bd79c85b982f97ff0e5c935648c9b/alfa-durable-calculation-1`
выполнен один заранее объявленный burst 50 разных авторизованных HTTP-клиентов.
Вход — текущий N6/C2, seed 1, цель 51,818 пал./ч, исходные каталог и нормативы;
каждый расчёт включал номинальный и отдельный контролируемый тест мощности.
Перед burst прошли один настоящий reference и smoke двух пользователей. Этот полный
профиль не эквивалентен историческому более лёгкому входу ниже.

Все 50 первых POST получили `202`; все 50 заданий завершились с одной попытки.

### Исторический runner и команды

Исторический runner — [scripts/check-queue-load.mjs](../scripts/check-queue-load.mjs).
Он содержит прежние ожидания OK/52 и удаляет spatialEvidence: его нельзя выдавать за
runner текущего полного nominal + controlled профиля a944. Команды ниже описывают
историческую методику. Текущий эксперимент выполнен отдельным исследовательским
runner с SHA, указанным выше, без переноса старых ожиданий на новый результат.
Нужен отдельный
локальный Compose-проект с собственной БД, пустой активной очередью и одинаковыми
app/worker images. Используйте иной порт и volume, чем у проверяемой пользовательской
платформы. `DATABASE_URL` задаётся окружением для этой отдельной БД; пароль не пишется
в команду или отчёт. Значение `QUEUE_LOAD_PROJECT` должно совпадать с Compose project.

```powershell
$env:QUEUE_LOAD_ISOLATED = "1"
$env:QUEUE_LOAD_ORIGIN = "http://127.0.0.1:3086"
$env:QUEUE_LOAD_PROJECT = "alfa-queue-benchmark"
$env:QUEUE_LOAD_WORKERS = "1"
$env:QUEUE_LOAD_LABEL = "one-worker"
$env:QUEUE_LOAD_REPORT_DIR = "$PWD/reports/queue-one"
# DATABASE_URL — отдельная БД этого контура, переданная через окружение.
node scripts/check-queue-load.mjs
```

После полного завершения первой серии масштабируйте только worker этого же контура до
трёх процессов, проверьте engine fingerprint и контейнеры. Повторите runner с
`QUEUE_LOAD_WORKERS=3`, другой меткой и каталогом отчёта; не меняйте глобальный cap 2.
Отдельный [scripts/check-queue-recovery.mjs](../scripts/check-queue-recovery.mjs)
с теми же переменными изолированного контура проверяет настоящий kill/restart worker
после claim, восстановление принятого CREATE и однократную публикацию. Его результат
не выводится из теста 50 CALCULATE.

Runner создаёт собственные случайные fixture-аккаунты. После PASS удаляются только его
завершённые fixtures; при ошибке они остаются для диагностики. Сессии и случайный пароль
не сохраняются в отчёт. Runner использует вход из текущего calculation-source.json. Отчёт включает железо,
images, fingerprint заданий, времена, число попыток и границы проверки. Доступность health не заменяет проверку
результатов, а число действующих lease не измеряет реальное использование CPU zombie-процессом.
