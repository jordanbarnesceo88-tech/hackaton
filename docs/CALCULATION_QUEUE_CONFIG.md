# Общий лимит вычислительной очереди

Один worker-процесс выполняет одно задание. Число одновременно действующих lease на всю БД задаёт единственная строка `CalculationQueuePolicy`, `id=1`. Миграция создаёт её с `maxActive=2`. PostgreSQL ограничивает cap целыми числами 1–100; лимит 100 совпадает с максимальной общей очередью, но не означает, что сервер имеет ресурсы для ста параллельных расчётов.

Каждый claim под общим transaction-level advisory lock читает актуальную политику из БД и считает действующие lease по часам PostgreSQL. Локальный ENV, количество контейнеров и прежний аргумент `maxActive` не могут повысить этот предел. Политика не кешируется как источник допуска. Разные процессы с разными локальными настройками используют один DB cap.

Отсутствующая или некорректная строка означает отказ от claim с `CalculationQueuePolicyError`. Worker завершает процесс с ошибкой настройки; он не подставляет default и не помечает ожидающие задания FAILED. При недоступной БД claim также не выполняется. После удаления строки её нужно восстановить осознанно через администратора БД: CLI не создаёт её по принципу «первый worker побеждает».

## Изменение cap

Сначала закройте приём новых операций в целевом контуре и дождитесь завершения QUEUED/RUNNING. Отдельный API переключения maintenance-режима не предусмотрен; ограничение приёма задаётся вашим reverse proxy/порядком развёртывания. После этого выполните с DATABASE_URL именно целевой БД:

```bash
npm run queue:cap -- 12
```

При работающем Compose после применения миграций команду можно выполнить в одноразовом контейнере сервиса `migrate`, где доступны исходники, tsx и CLI:

```bash
docker compose run --rm --no-deps migrate npm run queue:cap -- 12
```

Эта команда заменяет штатную команду сервиса и сама не запускает сев. Используйте тот же Compose project и те же override/env-файлы, что и целевой контур. Production-образ `worker` содержит bundle исполнителя; исходного TS CLI в нём нет. Пароли и DATABASE_URL не указывайте в опубликованных командах и отчётах.

CLI принимает ровно одно целое число 1–100 и меняет строку в короткой транзакции Read Committed. Порядок блокировок: сначала общий admission lock, затем общий claim/recovery lock. Если есть хотя бы одно QUEUED или RUNNING задание, включая RUNNING с уже истёкшей lease, изменение отклоняется с `QUEUE_NOT_IDLE`. Сначала дайте восстановлению закончиться или явно завершите/отмените работы обычным механизмом.

При гонке с отправкой задания возможны два корректных исхода: admission записывает работу первым, и CLI отказывает; либо CLI меняет политику первым, а admission записывает работу уже после commit новой политики. CLI не обнуляет очередь, не отзывает lease и не меняет принятые входы. Уже подключённые совместимые worker увидят новое значение при следующем claim.

## Число процессов и ресурсы

Повышение cap не создаёт CPU. Запустите нужное число реплик, например:

```bash
docker compose up -d --scale worker=12
```

При cap=12 и трёх worker одновременно исполняются максимум три задания; при двенадцати worker и cap=2 — максимум два. Один worker использует отдельный пул PostgreSQL максимум на два соединения. Он не создаёт дополнительный web-клиент. Web сохраняет собственный пул; в общий бюджет соединений также входят миграции, мониторинг и другие приложения.

До нагрузки задайте и сохраните CPU/RAM limits всех сервисов и проверьте их через фактический Docker inventory. Пример отдельного override для worker:

```yaml
services:
  worker:
    cpus: 1.0
    mem_limit: 1536m
```

Это пример настройки, а не подтверждённая достаточность 1,5 GiB для любого входа. Квота CPU не закрепляет физическое ядро. Нельзя автоматически назначать cap по 32 логическим CPU или только по `os.cpus()`: учитывайте физические ядра/SMT, Docker VM/cgroup limits, web с гостевыми расчётами, PostgreSQL, RAM и другие процессы. Гостевой HTTP-допуск не входит в worker cap.

Worker пишет в startup-log engine fingerprint, instance, local concurrency=1, прочитанный globalCap и dbPoolMax=2. Startup cap — снимок в этот момент; текущим источником остаётся DB policy. CLI пишет предыдущий и новый cap. Логи запуска и web health не доказывают последующую живость idle-worker: сверяйте процессы, контейнеры и реальные smoke-операции.

## Первое обновление с версии без DB policy

Старые worker используют константу и не соблюдают новую строку. Новая политика не делает их совместимыми автоматически.

1. Закройте admission и дождитесь пустой очереди, сохранив данные БД.
2. Остановите **все** legacy worker, подключённые к этой БД. Проверьте inventory, включая процессы вне Compose.
3. Примените миграции и разверните app/worker одной новой сборки с одинаковым engine fingerprint.
4. При необходимости измените cap на пустой очереди, запустите объявленное число реплик, проверьте startup и ресурсы.
5. Выполните настоящие smoke-расчёты и откройте приём.

Не оставляйте разные engine параллельно выбирать одну очередь: текущий claim не маршрутизирует работы между версиями и отклоняет несовместимый сохранённый запуск. При откате сначала завершите принятые новой сборкой работы совместимым исполнителем. Не используйте `down -v` для изменения лимита.

## Границы гарантии

DB cap ограничивает действующие lease у совместимых worker. Он не измеряет фактический CPU zombie-процесса, не отзывает его аппаратно и не защищает от администратора, который вручную обходит протокол прямыми SQL-правками. Срок lease, heartbeat, отмена, CAS и проверка токена при публикации сохраняются.

Бюджет попытки остаётся 60 секунд; все пространственные replay делят до 45 секунд внутри этого бюджета. Время в очереди входит в ожидание клиента. Увеличение cap не является подтверждением клиентского SLA: это проверяется отдельным заранее объявленным нагрузочным прогоном с настоящими результатами. Финансовые и физические входы, безопасность, циклы возврата пустой тары и полнота replay из-за настройки очереди не меняются.
