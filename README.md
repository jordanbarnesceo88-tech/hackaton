# Платформа оценки роботизации

Платформа помогает сравнить роботизированные решения, рассчитать экономику и подготовить пилот на объекте. Основные сценарии — перевозка паллет на складе и уборка. Для склада, аэропорта и медучреждения доступны параметры объектов и подбор по поддерживаемым процессам.

## Возможности

- Параметры объекта вручную или из Excel/CSV: единицы, диапазоны, источники и предупреждения о недостаточных данных.
- Сравнение текущего процесса, покупки и RaaS: CAPEX, OPEX, ROI, NPV, TCO, окупаемость и чувствительность. Высвобождение труда отделено от денежной экономии; калькулятор ФОТ показывает состав затрат.
- Явные условия комплектации и услуги: первый месяц, запуск, платформа, ТО, расходники, ремонт, АКБ и доставка. Включённые статьи не начисляются повторно; неизвестные цены не заменяются нулём.
- Уборка: сравнение CC1, C5 и SC80 на общей площади, кратности и рабочем окне; конечные циклы работы и зарядки, ежедневный уход, трудовой ресурс. Смешанный парк можно распределить по непересекающимся зонам и этажам с учётом существующих машин.
- Перевозка паллет: аналитическая проверка нагрузки; для подхвата мобильного стеллажа — пространственная модель полного цикла с подачей, перевозкой, возвратом, зарядкой и взаимодействием роботов. Доступны 3D-просмотр, история работы и разбор инцидентов.
- План пилота: выбранная модель, участок, подготовка, бюджет, критерии приёмки и недостающие сведения. Руководства, кейсы и материалы внедрения привязаны к моделям и сохраняются с проектом.
- Проекты и отчёты PDF, XLSX, CSV и JSON. Архив хранит использованные входы, версии и результаты; открытие не пересчитывает его текущими справочниками.
- Фоновые расчёты с этапами, отменой и восстановлением после остановки исполнителя. Поздний результат не перезаписывает новую редакцию проекта.

Финансовая привлекательность, выполнение нагрузки и готовность к пилоту оцениваются отдельно. Положительный NPV не является подтверждением работоспособности на реальном объекте.

## Каталог и производительность

После синхронизации каталог содержит **191 карточку: 188 решений организатора и 3 дополнительных уборщика — Pudu CC1, Agibot C5 и Viggo SC80**. Карточки организатора содержат **3950 исходных характеристик**. Импорт исследования включает 2860 находок для 185 моделей; цитаты, условия и альтернативы сохранены, расхождения отмечены. Проверка автора исходной таблицы указана отдельно от измерений платформы.

Карточка показывает заявленную производительность с её единицей и ограничениями. **Отображаемая характеристика и выработка для финансового расчёта — разные данные:** площадь за сутки или заряд, максимальная скорость и результат целого парка не превращаются автоматически в часовую выработку одного робота. Для расчёта требуется применимый процесс и достаточные параметры; для уборки — явный эксплуатационный профиль. Непривязанные карточки можно включить отдельным фильтром.

Отчёты эксплуатации и подтверждённые замеры имеют модель, режим, период и базис времени. Просмотр отчёта не применяет его к сценарию автоматически. Рабочие оценки CC1/C5/SC80 редактируются и отделены от паспортов. Условное расписание уборки не является телеметрией, проверкой качества уборки или 3D-подтверждением.

Правила: [происхождение данных](./docs/data-provenance.md), [эксплуатационные профили и замеры](./docs/OPERATING-EVIDENCE.md), [границы расчётов](./docs/LIMITATIONS.md).

Гостевая рабочая область получает серверный результат по текущим справочникам; изменение условий требует пересчёта. Сохранение проекта доступно после входа. Демо-аккаунты создаются при первоначальном севе; настройки и локальные реквизиты описаны в [быстром запуске](./docs/DEPLOY-QUICKSTART.md).

## Устройство приложения

Next.js, React и TypeScript; Prisma и PostgreSQL; отдельный Node.js worker. PostgreSQL хранит каталог, проекты, неизменяемые входы расчётов и очередь. Worker использует тот же движок, что и серверный расчёт. Публикация результата проверяет владельца, редакцию проекта, отмену и действующую аренду задания в одной транзакции.

Авторизованные фоновые операции доступны через `/api/v1/calculation-jobs`, их состояние — на `/calculation-jobs`. Закрытие вкладки не отменяет принятое задание. Гостевой пересчёт использует `/api/v1/demo-calculation` и не сохраняет проект.

Версии: [экономика](./lib/tz/version.ts), [аналитическая модель](./lib/sim/types.ts), [пространственная модель](./lib/sim/spatial-version.ts). Веб и worker должны быть собраны из одного выпуска с одинаковым `engineRelease`; инструкции по очереди и обновлению — в [CALCULATION_JOBS.md](./docs/CALCULATION_JOBS.md).

Для необязательных пояснений ИИ задаются серверные `AI_API_URL`, `AI_API_KEY` и `AI_MODEL`. Ключ не передаётся браузеру. Рекомендация привязана к редакции расчёта; численные результаты определяет расчётный движок. Автоматическая проверка ответа не гарантирует правильную смысловую связь каждого числа и показателя.

## Запуск

### Docker Compose

```bash
docker compose up --build
```

Откройте http://localhost:3000. Compose поднимает PostgreSQL, выполняет миграции и первоначальный сев, запускает веб и worker. Порты хоста настраиваются через `APP_PORT` и `DB_PORT`.

Перед публичным размещением задайте собственный `AUTH_SECRET`, замените демонстрационные пароли через `DEMO_USER_PASSWORD` и `DEMO_ADMIN_PASSWORD` и настройте HTTPS. `docker compose down` сохраняет том БД; вариант `down -v` удаляет его данные.

### Локальный PostgreSQL

Нужны PostgreSQL 16+ и Node.js 20.19+ в ветке 20, 22.12+ в ветке 22 либо 24+. Скопируйте `.env.example` в `.env`, задайте `DATABASE_URL` и `AUTH_SECRET`.

Для первоначальной установки:

```bash
npm ci
npx prisma migrate deploy
npm run db:seed
npm run build
npm start
```

Во втором терминале с тем же окружением:

```bash
npm run worker
```

Для разработки: `npm run dev` и отдельно `npm run worker:dev`. Production-сборка собирает 3D-страницы, worker и Next.js. После изменения движка пересоберите и согласованно обновите оба процесса.

### Vercel и обновление существующей установки

На Vercel принятые задания выполняются через `after`: ответ `202` отправляется до расчёта, а исполнитель использует сохранённый вход, общий лимит PostgreSQL и ту же защиту lease/CAS. Авторизованная проверка состояния повторно подхватывает прерванное задание после истечения lease. Время одного вызова ограничено 300 секундами, внутренний срок — 280 секунд. Для непрерывной обработки очереди независимо от посещения сайта можно запустить отдельный worker с доступом к той же БД и совместимым выпуском.

Production Build Command из `vercel.json` выполняет **миграции → безопасную синхронизацию каталога → сборку**. Синхронизация сохраняет правки администратора, добавляет только отсутствующие карточки трёх уборщиков и не изменяет пользователей, проекты или существующие карточки поставщиков. Это не полный сев; исходные типы объектов должны уже существовать. Ошибка миграции или синхронизации останавливает сборку. Preview не выполняет этот шаг записи в БД.

Для миграций и синхронизации используется прямое соединение: `DIRECT_URL`, затем `DATABASE_URL_UNPOOLED`, `POSTGRES_URL_NON_POOLING` или `DATABASE_URL`. Runtime-подключение веба и worker остаётся неизменным. Точный порядок и правила Neon описаны в [разделе Vercel](./docs/DEPLOY.md#4a-раздельное-размещение-vercel-web-и-отдельный-worker).

Вне Vercel после миграций текущие справочники можно обновить отдельно, без полного сева:

```bash
npx prisma migrate deploy
npx tsx scripts/sync-runtime-catalog.ts
npm run build
```

Перед обновлением сделайте резервную копию, завершите или согласованно остановите прежнюю очередь и worker. На пользовательской БД не используйте `migrate reset` или `db push` вместо миграций.

## Проверки

```bash
npm run test:unit
npm run test:db
npm run lint
npx tsc --noEmit
npm run build
npm run check:3d
npx playwright install chromium
npm run test:e2e
```

Тесты БД и браузера запускайте **на отдельной тестовой БД** с применёнными миграциями и тестовыми данными. Playwright запускает собственные веб и worker, но наследует `DATABASE_URL` и сам не создаёт изолированную базу.

Для проверки установленного контура: `/api/health` подтверждает веб и БД, а `npm run check:worker` выполняет вход, отправляет контрольный расчёт, дожидается сохранённого результата и удаляет своё техническое задание. По умолчанию используется http://localhost:3000; другой адрес задаётся через `APP_URL`. Для проверки нужны действующие реквизиты тестового пользователя.

После обновления подтвердите выпуск созданием, сохранением, повторным открытием и экспортом контрольного проекта. Доступность сайта, обновлённый каталог и успешный health не подтверждают выполнение новых заданий. Локальные проверки не заменяют приёмку конкретной установки; результаты имитации требуют проверки и калибровки на объекте.
