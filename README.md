# Платформа оценки роботизации

Платформа помогает выбрать роботизированное решение, сравнить экономику и проверить нагрузку перед пилотным внедрением. Основной демонстрационный сценарий — перевозка паллет на складе по исходным данным ФЦ БАС. Для аэропорта и медучреждения доступны параметры объектов и каталог подходящих решений; полнота расчёта зависит от поддерживаемых процессов и исходных данных.

## Возможности

- Ввод параметров объекта вручную или из Excel/CSV, единицы измерения, диапазоны, источники и предупреждения о качестве данных.
- Каталог с происхождением характеристик, причинами включения и исключения решений, недостающими сведениями.
- Сравнение «Как есть», покупки и услуги RaaS: CAPEX, OPEX, ROI, NPV, TCO, окупаемость и чувствительность к допущениям.
- Раздельный учёт высвобождения труда и денежной экономии, вариантов организации эксплуатации и услуг, включённых в комплектацию.
- Пространственная проверка замкнутого цикла мобильного стеллажа: плотная планировка, препятствия, подхват, перевозка, возврат носителя, взаимодействие роботов, зарядка, телеметрия и ретроспектива. Одиночная перевозка паллеты вилочным роботом или тягачом рассчитывается отдельно в аналитической 2D-модели.
- В складском 3D-просмотре робот заезжает под пятиъярусный мобильный стеллаж, поднимает его, перевозит, устанавливает и выезжает. Общая сцена, увеличенная модель и история показывают постоянный идентификатор стеллажа и этапы работы. Внутренние подачи и возвраты занимают время, но не прибавляются к клиентскому потоку. Геометрия — реконструкция по фотографиям с явно указанными допущениями.
- План пилота: участок, состав оборудования, подготовка объекта, бюджет, критерии успеха и неизвестные параметры.
- Сохранённые проекты, отчёты PDF/Excel/CSV и JSON; защита от перезаписи изменений из параллельных вкладок.
- Фоновые расчёты для создания и сохранения проектов: серверная очередь, просмотр этапов, отмена и восстановление после остановки worker. Закрытие вкладки не отменяет принятое задание.

Финансовая привлекательность и выполнение нагрузки оцениваются отдельно. Положительный NPV сам по себе не означает готовность к внедрению. Имитационная модель требует калибровки по реальному объекту, а неизвестные цены и характеристики не подменяются подтверждёнными данными. [Границы решения](./docs/LIMITATIONS.md), [архивные экономические примеры прежней модели tz-1.0.4 / spatial-1.4.0](./docs/ECONOMICS-2026-10-18.md). Числа этих примеров не описывают текущий полный цикл носителя.

## Архитектура

Next.js / React / TypeScript, Prisma и PostgreSQL. Единый расчётный движок обслуживает интерфейс, API, сохранение проектов и отдельный Node.js worker. PostgreSQL хранит принятый вход расчёта, снимок справочников, очередь и завершённый результат. Публикация результата проверяет редакцию проекта, отмену и действующую lease worker в одной транзакции.

Текущие версии определяются в исходниках: [экономика](./lib/tz/version.ts), [аналитика](./lib/sim/types.ts), [пространственная модель](./lib/sim/spatial-version.ts). Версии записываются в результат. Для поддомкрачивающих роботов процесс `closed-pod-1` связывает экономику полного цикла на плотной планировке с одной фактической пространственной сводкой; отдельная 2D-модель не даёт ему второе подтверждение. Для вилочных роботов и тягачей процесс `single-leg-pallet-1` сохраняет аналитику одиночной перевозки без 3D-подтверждения подхвата стеллажа. Результаты относятся к указанным входам, seed, процессу и версии.

Начало обработки клиентской заявки включает назначенную подачу носителя для этой заявки. Доля начатых заявок, очередь и p95 ожидания до начала этой работы не означают завершённую доставку: выходной поток учитывает только завершённые клиентские перевозки, а внутренние подачи и возвраты не добавляют паллет к результату.

Авторизованные расчёты выполняются worker через `/api/v1/calculation-jobs`. Гостевая рабочая область получает актуальный серверный результат через `POST /api/v1/demo-calculation`: экономика и проверка поддерживаемого транспортного процесса. Этот запрос не создаёт проект или запись в очереди; сохранение проекта доступно после входа. [Контракты, восстановление и ограничения](./docs/CALCULATION_JOBS.md).

Три учебных примера задают воспроизводимые входные параметры. Открытие гостевого примера запускает расчёт по текущим справочникам; после изменения условий пользователь нажимает «Пересчитать». Сохранённый пример не заменяет новый результат. До завершения расчёта предварительная оценка обозначается отдельно. Карточка поддерживаемого продукта передаёт его в пару сценариев покупки и RaaS; неизвестный или неприменимый продукт не заменяется роботом по умолчанию.

Методика текущей HTTP-нагрузки очереди, исходный неуспешный burst и воспроизводимый runner описаны в [CALCULATION_JOBS](./docs/CALCULATION_JOBS.md#нагрузочная-проверка-методика-и-область). Подтверждение приёма, ожидание очереди и вычисление измеряются отдельно; этот тест не заменяет отрисовку 50 браузерных сессий.

Два текущих прогона по 50 HTTP-клиентов завершились с 50/50 принятыми и сверенными результатами. При одном worker p95 ожидания клиента составил 152,35 с, при трёх процессах с глобальным cap 2 — 82,90 с. Отдельный kill/restart подтвердил восстановление CREATE после истечения lease и однократную публикацию проекта. Это локальные измерения конкретного входа, а не промышленный SLA.

## Запуск через Docker

Нужны Docker с Compose v2 и сеть для первоначальной сборки.

```bash
docker compose up --build
```

Откройте http://localhost:3000. Compose запускает PostgreSQL, применяет миграции и сев, затем поднимает веб-приложение и worker. Проверка веба: `GET /api/health`; состояние worker: `docker compose logs worker`. В интерфейсе список операций доступен после входа на `/calculation-jobs`.

Для локальной работы используйте `localhost`; для доступа по сети — HTTPS. Отправка фоновых расчётов использует браузерную криптографию защищённого контекста.

Порты настраиваются через `APP_PORT` и `DB_PORT`. На публичном стенде задайте собственный `AUTH_SECRET`, замените демонстрационные пароли и используйте HTTPS. `docker compose down` сохраняет том БД; `docker compose down -v` удаляет данные.

## Запуск с локальным PostgreSQL

Нужны Node.js 20.19+ в ветке 20, 22.12+ в ветке 22 либо 24+, а также PostgreSQL 16+. Эти семейства версий соответствуют требованиям установленного Prisma. Скопируйте `.env.example` в `.env`, задайте `DATABASE_URL` и `AUTH_SECRET`.

```bash
npm ci
npx prisma migrate deploy
npm run db:seed
npm run build
npm start
```

Во втором терминале, с тем же окружением:

```bash
npm run worker
```

`npm run build` собирает автономные 3D-страницы, worker и Next.js из одной рабочей копии. Для разработки запускайте `npm run dev` и отдельно `npm run worker:dev`. Веб и worker должны использовать одинаковый выпуск движка; production-сборки содержат fingerprint исходников. После изменения расчётного кода пересоберите и перезапустите оба процесса.

Основной 3D-сценарий доступен по адресу `/demo/warehouse`, дополнительный сценарий уборки — `/demo/cleaning`.

## Демонстрационные аккаунты

| Роль | Почта | Демонстрационный пароль |
|---|---|---|
| Пользователь | `demo@demo.local` | `demo-user-2026` |
| Администратор | `admin@demo.local` | `demo-admin-2026` |

Аккаунты создаёт сев. Пароли задаются переменными `DEMO_USER_PASSWORD` и `DEMO_ADMIN_PASSWORD`; приведённые значения предназначены для локальной демонстрации. Общий демо-проект доступен для чтения; для сохранения правок создайте копию.

## Проверки

```bash
npm run test:unit
npm run test:db
npm run lint
npx tsc --noEmit
npm run build
npm run check:3d
npm run test:e2e
```

Тесты БД требуют отдельного PostgreSQL с применёнными миграциями и тестовыми данными. Не запускайте их на пользовательской базе. Для браузерных тестов предварительно выполните `npx playwright install chromium`. Сценарии очереди проверяют идемпотентность, конкурентный claim, истечение lease, отмену, CAS-конфликт и атомарность публикации; остановку и перезапуск production worker следует проверять отдельно от unit-тестов.
